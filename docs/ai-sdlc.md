# AI-SDLC — 為什麼這條流程長這樣

這份文件記錄**本專案的主張**：一條給 AI 協作用的開發生命週期，為什麼需要
六步、每一步為什麼存在、哪幾段是 BDD、哪幾段不是。

它跟 [bdd.md](./bdd.md) 的分工：那份轉述 BDD 這套方法本身，
不提本專案；這份是本專案的立場，會隨實跑演進。要建什麼、什麼順序見
[PLAN.md](../PLAN.md)。

---

## 為什麼需要一條生命週期

如果寫程式的是一個人，很多東西可以留在腦子裡：上週為什麼那樣決定、這個欄位
是誰要求的、那個看起來多餘的判斷擋的是什麼。**換成 agent，這些全部留不住。**

三件事會壞，而且壞的方式不一樣：

| 壞的東西 | 為什麼 | 補法 |
| --- | --- | --- |
| **脈絡活不過一個 session** | context window 會結束、會被壓縮、會被清空 | 產物就是記憶。沒寫進檔案的決定等於沒發生 |
| **agent 會漂移** | 它會為了讓流程往前走而補一個合理的猜測，而猜測看起來跟事實一樣 | 審查是結構的一部分，不是選配 |
| **無邊界的工作做不完** | 一次交付太大的任務，agent 會在中途失去脈絡然後開始猜 | 工作要切到「一個全新 session 做得完」 |

BDD 三個實踐一個都沒解決這三件事——**它們不是 BDD 的缺口，是 BDD 的範圍之外**。
BDD 談的是人跟人之間怎麼建立共識，這裡多出來的問題是**協作對象換成了會失憶的
機器**。

## 六步，以及哪幾段是 BDD

```
DISCOVERY  →  SPEC  →  PLAN  →  IMPLEMENT  →  REVIEW  →  VERIFY
└──── BDD ────┘       ✗       └─ BDD ─┘        ✗          ✗
（brainstorming）（to spec）（to plan）                （未實作）  （未實作）
```

**帶 BDD 的那三格不等於 BDD。** DISCOVERY 的開場在對 `## 原文` 掃隱含假設——這件事
本身不是 Discovery，卻是 Discovery（把需求逼成規則與例子）真正要用的輸入；SPEC 除了
`formulation` 產的 `.feature`，還要把問答寫成 `spec.md`、判就緒。只有 IMPLEMENT 跟
Automation 重合，因為 Automation 的產物本來就是程式碼而不是膠水層（見
[bdd.md](./bdd.md) §③）。BDD 的覆蓋也不連續：**PLAN 是夾在中間的洞**。

| 步驟 | 存在的理由 | BDD 對應 |
| --- | --- | --- |
| **DISCOVERY** | brainstorming：開場把需求方的話逐字收進 `spec.md` 的 `## 原文`、粗切 story（不是 BDD，BDD 假設 story 已經存在）＋對 `## 原文` 掃隱含假設（不是 BDD）＋把每則 story 一題一題問到規則與例子都有人答過（BDD 的 Discovery）。**只記問答，不寫規則**——每個答案記原話與誰答的，最後要需求方對意圖陳述說 yes。需求進來時是模糊的，而 agent 對模糊的預設反應是猜 | Discovery ＋ 額外 |
| **SPEC** | to spec：把已答的問答在同一份 `spec.md` 寫成規則（FR／AC 每一條行尾指回 `## 原文` 或 `## Open Questions` 的已答題，`spec`）＋業務語意的驗收旅程（`acceptance/*.feature`，不執行，`spec-by-example`）＋流程與四色卡診斷（`feature-mapping`、`example-mapping`）＋就緒判定（`example-mapping`）＋可執行規格（BDD 的 Formulation，`formulation`，`已對焦` 之後由使用者叫） | Formulation ＋ 額外 |
| **PLAN** | to plan：執行計畫（風險、要不要並行、接合點）＋把工作切到一個 fresh session 做得完，並宣告誰卡誰、誰能同時做（`plan` 寫 `plan.md`，`task-breakdown` 拆成 `tasks.md`） | **無**——BDD 明確沒有排序指引 |
| **IMPLEMENT** | 用外迴圈驅動內迴圈，把行為做出來；一張票一個 session，做完把 `.feature` 翻到 `@review`（`implement`） | Automation |
| **REVIEW** | 這變更真的滿足它宣稱的情境嗎？鏈斷了嗎？全新的 reviewer 對照 `spec.md`／`.feature` 審整批 | **無**——治理不在三個實踐裡 |
| **VERIFY** | 最後一次驗證：閘門、全部情境、鏈稽核都有輸出當證據才算交付；紅的是 bug 還是規格過期？ | Automation 之後的持續活動 |

REVIEW 排在 VERIFY 前面：review 抓到的修完，最後一次驗證才算數。反過來的話，驗證完再改
就沒有人驗了。

**六塊不屬於 BDD 的東西（DISCOVERY 的建檔與 story 粗切、DISCOVERY 的隱含假設掃描、
PLAN 的技術設計與切票、REVIEW、VERIFY 的交付證據）都不是補丁。** 它們回答的是「協作對象
會失憶」帶來的問題，而 BDD 從來沒有那個問題要解。

## 三種模式，三條紀律

六步之所以站得住，是因為前三步各自只有一種主要的工作模式：

| 步驟 | 模式 | 只做 | 不做 |
| --- | --- | --- | --- |
| **DISCOVERY**（`discovery`） | agent 問、需求方答（開場建檔那一回合是需求方說、agent 記） | 原文逐字、粗切 story、一次問一題、記答案原話與誰答的、意圖陳述 | 不寫 FR／AC、不寫 Gherkin、不設計、不自己填答案 |
| **SPEC**（`spec`／`spec-by-example`／`formulation`） | agent 寫、需求方審 | `spec.md` 的已答題 → FR／AC（`待對焦`）→ `acceptance/` 驗收旅程 →（`已對焦`）→ `.feature` | 不訪談、不寫技術決定，有洞就在 `## Open Questions` 開一題、狀態改回 `澄清中`、停 |
| **PLAN**（`plan`／`task-breakdown`） | agent 定與切、工程師確認 seam、審計畫 | `spec.md` ＋ `.feature` → 技術決定 → 風險與接合點 → tracer bullet ＋ blocking edges | `plan` 不改 `spec.md` 與 `.feature`、`task-breakdown` 不改設計，有洞記進 `## 缺口` 並交回 `spec`／`formulation`／`plan` |

三條互相支撐：SPEC 能「不訪談」是因為 DISCOVERY 把每個答案連原話記下來了；PLAN 能
「不改需求」是因為 SPEC 寫下了需求方點過頭的規則；DISCOVERY 能只問不寫，是因為 SPEC
會逐條指回它的紀錄。任何一條破了，下一條就守不住。

出處是 Matt Pocock 的 `to-spec`：「The spec is a record of decisions already
made, not a place where new ones get made.」

**這條紀律對人是選配，對 agent 是必需。** 人在寫規格時發現有洞，會停下來去問；
agent 會補一個合理的答案然後繼續，而那個答案看起來跟真的一樣。擋這件事的是「每條
FR／AC 必須指得出來源」——`check_spec.py` 第 14 項機械地抓沒有 `← Q-<n>` 或 `← PRD §n`
的規則，並確認 `← Q-<n>` 在同一份檔的 `## Open Questions` 找得到、而且是已答。

### 為什麼 discovery 只記問答

2026-11-14 之前 DISCOVERY 邊問邊把答案寫成 `spec.md` 的 FR／AC。改成只記問答，有兩種做法：

- **完全不寫檔，問完一次交給 SPEC**：對話最乾淨，但 session 中途斷掉或被壓縮，前面的答案就
  沒了——「脈絡活不過一個 session」是這份文件開頭的第一條；`← Q-<n>` 也沒有東西可以指，
  第 14 項得拿掉
- **只寫問答紀錄**（採用）：規則只在 SPEC 寫一次，問答落檔所以 session 斷了
  接得上，`← Q-<n>` 有地方指

代價是 SPEC 要從紀錄重建規則，紀錄裡沒寫下的例子它寫不出 AC。所以 DISCOVERY 的記錄紀律
從「當場寫成規則」換成「當場記下答案原話與例子」。

問答紀錄起初是另一份 `discovery.md`。2026-11-18 併進 `spec.md`：`## Open Questions`（問答表與每題小節）
與 `## 原文`（附錄）。分開的是**誰問**（`discovery`）與**誰寫規則**（`spec`），不必分開的是**檔案**——
試跑時退回 discovery 三次，每次都在兩份檔之間改狀態；而擋「寫規格時順手補答案」的防線早已是第 14 項，
不是檔案邊界。兩個參考也都沒有獨立的問答檔：aixbdd 的 `specify` 寫 `spec.md`、遇到高影響缺口委派 `clarify`
去問；addyosmani 的 `interview-me` 的產物是一段需求方明說 yes 的意圖陳述。

同一天 `clarify`（逐題收斂紅卡）併進 `discovery`：兩個 skill 都在問需求方，分成兩個只多一次交接。
`discovery` 改成 interview-me 的問法——一次一題、每題附上下文與猜測的答案、問到猜得中需求方的反應為止——
`clarify` 留下來的是答不出來時的三堆（可解／阻塞／失效）。現在它是唯一會問需求方的 skill。

### 為什麼是這幾個 skill，不是一個

建檔與追問曾經是兩個 skill（2026-10-02 到 11-13 的 `bdd-capture`）。拆開的理由是
**方向相反的工作模式**：建檔是需求方說、模型記；追問是模型問、需求方答。合在一起，
模型會在記的時候順手補規則——那正是 2026-09-09 到 09-11 三個版本都犯的事，每一次
都靠措辭掩飾。後來擋這件事的防線換了：不再靠 skill 邊界，靠 `check_spec.py` 第 14 項
機械地抓沒有來源的 FR／AC。防線換成機械的之後，PRD 就不必再是流程自己維護的產物——
它是需求方帶來的輸入，建檔只是把它逐字收進 `## 原文`——所以 2026-11-13 把建檔併回
DISCOVERY 的開場，當成它的第 0 件事。

Discovery 與 Formulation 相鄰，卻是**方向相反的工作模式**：Discovery 是模型
不停追問、使用者回答；Formulation 是模型書寫、使用者審閱。

合成一個 skill 會讓模型在兩種模式間搖擺，而實務上的結果幾乎總是**跳過追問直接
開始寫**——因為書寫比追問「看起來更有生產力」。跳過 Discovery 正是 BDD 最常見
的失敗模式：付出了膠水層的維護成本，卻沒得到任何發現價值。

SPEC 底下還要再拆成兩個 skill，理由又不一樣：`.feature` 是三方真正**拿來對
答案**的那一份，需要一個從頭到尾負責的擁有者；封閉步驟文法、tag、覆蓋盤點
這三件事，全部只服務這一份產物。把它跟「把問答寫成 `spec.md`」塞進同一個
skill，等於要求同一次判斷既收斂**語意**（這句話夠不夠、對不對）又收斂**語法**
（這句話能不能跑），兩者混在一起，語法細節會拖著語意判斷跑。

技術決定放在 PLAN（2026-11-18 起）。2026-11-15 曾照 mattpocock 的 to-spec 把技術設計搬進 `spec.md`，
靠**順序**守界線：技術部分在需求方說「就緒」之後才寫。試跑之後需求方改回：「我這邊也覺得不應該有技術
部分」。界線改靠**檔案**守：`spec.md` 只寫要做成什麼，需求方判就緒時整份都讀得懂；用什麼做、seam、
契約、schema 寫在 `plan.md` 的前半。seam 仍是工程判斷，所以由 `plan` 攤給使用者確認。

順帶的好處：`plan` 在 `.feature` 之後跑，定 seam 時看得到每一個場景，能把 seam 上驗不到的 Then
（設備端的退錢、畫面顯示）攔下來交回 `formulation`——試跑時這類場景是一路寫到 PLAN 都沒人擋。

**沒有任何 skill 呼叫下一個。** 每個 skill 都設了 `disable-model-invocation`，每一步由使用者打
`/<skill>`；試跑時 `spec` 照它當時的指示自己接著跑了 `formulation`，繞過了這個決定。

SPEC 的診斷有兩張圖，方向相反：`feature-mapping` 看整個 feature 的**寬度**——流程有沒有斷、
每一步的替代流程與規則的反例寫了沒；`example-mapping` 看一則 story 的**深度**——每條規則有沒有
例子撐住。先寬後深（2026-11-18 起）：寬度找到的洞會改動 story 與 FR，先找出來，四色卡才不會攤
一張馬上要重畫的。兩者都只印地圖、不另寫檔案，因為圖上每張卡都已經住在 `## User Stories` 與
`acceptance/`；它們新增的是找洞的方法，洞在 `spec.md` 的 `## Open Questions` 開成待答題。Feature Mapping 原本是工作坊
裡當場追問，這裡把問題開成補問題交給 `discovery`——SPEC 不訪談，當場問到的答案沒有原話與誰答的，`← Q-<n>` 指不了。

PLAN 的後半是**執行**：哪裡危險、能不能並行、合回時哪些檔會相撞，以及把工作切到一個 fresh
session 做得完。實作者讀 `plan.md` 的技術決定與自己那張票節就夠（票由 `task-breakdown` 拆到
`tasks.md`，一張票一節，做票的 session 只改自己那一節，讓幾張票能同時做而不互相覆寫）。

## agent 能替代什麼，不能替代什麼

| 實踐 | agent 能做 | agent 不能做 |
| --- | --- | --- |
| **Discovery** | 扮演提問者，針對每條規則追問邊界、例外、空值、權限、併發。把「使用者可以上傳檔案」逼成「10MB 剛好／10MB+1 byte／0 byte／副檔名偽裝」。手法是 Example Mapping，四色卡怎麼對應 `spec.md`、四條診斷在這裡各自代表什麼 → `example-mapping` skill | **取代三方對話。** 它沒有業務脈絡的最終裁量權——它問得出問題，答不了 |
| **Formulation** | 草擬 Gherkin、稽核是否命令式化、統一詞彙、找出重複情境 | **確認共識。** 定義裡的 check for agreement 需要一個真的會反對的人 |
| **Automation** | 產 step 骨架、優先比對既有 step 避免重複、指出該拆的 conjunction step | — |

第一列與第二列的界線是這條流程的設計依據：**agent 負責窮盡與稽核，人負責裁量。**
把裁量交給 agent，它不會拒絕，它會給你一個看起來合理的答案。

## 可追溯鏈

```
需求方的話（spec.md ## 原文）→ Story → FR → AC → Scenario → Ticket → Step → 程式碼
```

每個箭頭都是一個意圖遺失點。保住這條鏈是這套流程存在的理由——因為鏈的完整性
檢查**幾乎全是機械性的，人只是懶得做**，而機械性的事正好是 agent 做得比人好的。

**產物格式就是介面。** 下游讀的是上游實際吐出什麼，所以格式一改，鏈就斷。
這也是為什麼每一步的產物格式都要先定案再往下做——在紙上設計那個格式是猜的。

## AI 特有的四條

這四條不是從 BDD 推出來的，是實跑撞出來的：

### 1. 一張票 ＝ 一個 fresh context window

撿起這張票的東西沒看過 spec。這是切分的上界；下界是「票要能自己 demo」。

反面教材有實測紀錄：26 張票依層切，每張票平均跑 20 次 agent，其中四分之三
是返工。

### 2. Fail loud

找不到輸入時要指名說出缺什麼並非零離開碼，**絕不可以從零輸入推導出結論**。

理由是不對稱的：**壞掉的儀表板會被發現然後修好；安靜說「一切正常」的儀表板
會被相信。**

2026-10-02 起多一條機械防線：`check_spec.py` 第 14 項拒絕沒有來源的 FR／AC——
一條規則標 `推論` 就是 agent 自己補的，而它在文件上跟問出來的長得一模一樣。

### 3. 這條鏈的特徵性失敗是「靜默地錯」，不是「壞掉」

實跑撞過的四個例子，全部 exit 0、全部看起來健康：

- 儀表板找不到任何產物，卻回報六則 story「已就緒」
- 問題檔全部歸錯 story，覆蓋表照樣有 ✓ 和 —，只是掛在錯的地方
- 重排 Rule 編號不會報錯，只會讓 `@example-1.1` 指向另一條規則
- 解析器靠比對內文剛好加粗的文字，把一行已經壞掉的狀態列讀成有效

**要防的從來不是崩潰。**

### 4. 要驗「請外人看一眼」的機制，就必須真的有外人

流程裡的檢查點（例如切完票攤給人確認）不能由同一個 agent 自己扮演——它會同意
自己的切法。實跑中那個檢查點抓到的是**接縫劃錯位置**（同一個公式出現在兩張票的
內迴圈），而那只有把清單並排讀才看得見；一張一張看，每張都合理。
