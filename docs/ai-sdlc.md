# AI-SDLC — 為什麼這條流程長這樣

這份文件記錄**本專案的主張**：一條給 AI 協作用的開發生命週期，為什麼需要
六步、每一步為什麼存在、哪幾段是 BDD、哪幾段不是。

它跟 [bdd-workflow.md](./bdd-workflow.md) 的分工：那份轉述 BDD 這套方法本身，
不提本專案；這份是本專案的立場，會隨實跑演進。要建什麼、什麼順序見
[PLAN.md](../PLAN.md)。

---

## 為什麼需要一條生命週期

如果寫程式的是一個人，很多東西可以留在腦子裡：上週為什麼那樣決定、這個欄位
是誰要求的、那個看起來多餘的判斷擋的是什麼。**換成 agent，這些全部留不住。**

三件事會壞，而且壞的方式不一樣：

| 壞的東西 | 為什麼 | 補法 |
| --- | --- | --- |
| **脈絡活不過一個 session** | context window 會結束、會被壓縮、會被清空 | 產物就是記憶。沒寫進檔案的決定等於沒發生 |
| **agent 會漂移** | 它會為了讓流程往前走而補一個合理的猜測，而猜測看起來跟事實一樣 | 審查是結構的一部分，不是選配 |
| **無邊界的工作做不完** | 一次交付太大的任務，agent 會在中途失去脈絡然後開始猜 | 工作要切到「一個全新 session 做得完」 |

BDD 三個實踐一個都沒解決這三件事——**它們不是 BDD 的缺口，是 BDD 的範圍之外**。
BDD 談的是人跟人之間怎麼建立共識，這裡多出來的問題是**協作對象換成了會失憶的
機器**。

## 六步，以及哪幾段是 BDD

```
CLARIFY → SPEC → PLAN → IMPLEMENT → VERIFY → REVIEW
└ Discovery ┘  └Formu-┘         └ Automation ┘
               └lation┘
```

| 步驟 | 存在的理由 | BDD 對應 |
| --- | --- | --- |
| **CLARIFY** | 需求進來時是模糊的，而 agent 對模糊的預設反應是猜 | Discovery |
| **SPEC** | 兩件事：把例子寫成可執行規格（BDD 的 Formulation）＋**把技術決定記下來**（不是 BDD） | Formulation ＋ 額外 |
| **PLAN** | 把工作切到一個 fresh session 做得完，並宣告誰卡誰 | **無**——BDD 明確沒有排序指引 |
| **IMPLEMENT** | 用外迴圈驅動內迴圈，把行為做出來 | Automation |
| **VERIFY** | 綠了嗎？紅的是 bug 還是規格過期？ | Automation 之後的持續活動 |
| **REVIEW** | 這變更真的滿足它宣稱的情境嗎？鏈斷了嗎？ | **無**——治理不在三個實踐裡 |

**三塊不屬於 BDD 的東西（PLAN、REVIEW、SPEC 的技術決定那半）都不是補丁。**
它們回答的是「協作對象會失憶」帶來的問題，而 BDD 從來沒有那個問題要解。

## 三條紀律

六步之所以站得住，是因為前三步各自只做一件事：

| 步驟 | 只做 | 不做 |
| --- | --- | --- |
| **CLARIFY** | 問問題，問到收斂 | 不寫規格 |
| **SPEC** | 綜合已經有答案的東西 | **不訪談**——憑空長出來的內容是缺陷 |
| **PLAN** | 切 tracer bullet | 不設計——API、schema、seam 在 SPEC 就定完了 |

三條互相支撐：SPEC 能「不訪談」是因為 CLARIFY 做完了決定；PLAN 能「不設計」
是因為 SPEC 寫下了技術決定。任何一條破了，下一條就守不住。

出處是 Matt Pocock 的 `to-spec`：「The spec is a record of decisions already
made, not a place where new ones get made.」

**這條紀律對人是選配，對 agent 是必需。** 人在寫規格時發現有洞，會停下來去問；
agent 會補一個合理的答案然後繼續，而那個答案看起來跟真的一樣。

### 為什麼是三個 skill，不是一個

Discovery 與 Formulation 相鄰，卻是**方向相反的工作模式**：Discovery 是模型
不停追問、使用者回答；Formulation 是模型書寫、使用者審閱。

合成一個 skill 會讓模型在兩種模式間搖擺，而實務上的結果幾乎總是**跳過追問直接
開始寫**——因為書寫比追問「看起來更有生產力」。跳過 Discovery 正是 BDD 最常見
的失敗模式：付出了膠水層的維護成本，卻沒得到任何發現價值。

PLAN 要獨立的理由不同：它是唯一一個**不需要領域知識**的步驟。切票靠的是依賴
關係與規模判斷，不是懂不懂停車場怎麼收費——把它混進 SPEC，等於讓一個正在做
領域判斷的模型順手做工程排序，兩種判斷會互相污染。

## agent 能替代什麼，不能替代什麼

| 實踐 | agent 能做 | agent 不能做 |
| --- | --- | --- |
| **Discovery** | 扮演提問者，針對每條規則追問邊界、例外、空值、權限、併發。把「使用者可以上傳檔案」逼成「10MB 剛好／10MB+1 byte／0 byte／副檔名偽裝」 | **取代三方對話。** 它沒有業務脈絡的最終裁量權——它問得出問題，答不了 |
| **Formulation** | 草擬 Gherkin、稽核是否命令式化、統一詞彙、找出重複情境 | **確認共識。** 定義裡的 check for agreement 需要一個真的會反對的人 |
| **Automation** | 產 step 骨架、優先比對既有 step 避免重複、指出該拆的 conjunction step | — |

第一列與第二列的界線是這條流程的設計依據：**agent 負責窮盡與稽核，人負責裁量。**
把裁量交給 agent，它不會拒絕，它會給你一個看起來合理的答案。

## 可追溯鏈

```
商業目標 → 批次 → Story → 規則 → 例子 → Scenario → Ticket → Step → 程式碼
```

每個箭頭都是一個意圖遺失點。保住這條鏈是這套流程存在的理由——因為鏈的完整性
檢查**幾乎全是機械性的，人只是懶得做**，而機械性的事正好是 agent 做得比人好的。

**產物格式就是介面。** 下游讀的是上游實際吐出什麼，所以格式一改，鏈就斷。
這也是為什麼每一步的產物格式都要先定案再往下做——在紙上設計那個格式是猜的。

## AI 特有的四條

這四條不是從 BDD 推出來的，是實跑撞出來的：

### 1. 一張票 ＝ 一個 fresh context window

撿起這張票的東西沒看過 spec。這是切分的上界；下界是「票要能自己 demo」。

反面教材有實測紀錄：26 張票依層切，每張票平均跑 20 次 agent，其中四分之三
是返工。

### 2. Fail loud

找不到輸入時要指名說出缺什麼並非零離開碼，**絕不可以從零輸入推導出結論**。

理由是不對稱的：**壞掉的儀表板會被發現然後修好；安靜說「一切正常」的儀表板
會被相信。**

### 3. 這條鏈的特徵性失敗是「靜默地錯」，不是「壞掉」

實跑撞過的四個例子，全部 exit 0、全部看起來健康：

- 儀表板找不到任何產物，卻回報六則 story「已就緒」
- 問題檔全部歸錯 story，覆蓋表照樣有 ✓ 和 —，只是掛在錯的地方
- 重排 Rule 編號不會報錯，只會讓 `@example-1.1` 指向另一條規則
- 解析器靠比對內文剛好加粗的文字，把一行已經壞掉的狀態列讀成有效

**要防的從來不是崩潰。**

### 4. 要驗「請外人看一眼」的機制，就必須真的有外人

流程裡的檢查點（例如切完票攤給人確認）不能由同一個 agent 自己扮演——它會同意
自己的切法。實跑中那個檢查點抓到的是**接縫劃錯位置**（同一個公式出現在兩張票的
內迴圈），而那只有把清單並排讀才看得見；一張一張看，每張都合理。
