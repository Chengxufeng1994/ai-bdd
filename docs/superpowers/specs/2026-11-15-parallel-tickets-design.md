# 讓票真的能並行：接合點分類與合回主線

**狀態**：已批　**日期**：2026-11-15

## 意圖

需求方要幾張票能同時做。`bdd-tasks`（`2026-11-15-bdd-tasks-design.md`）把票拆成一張一個檔，
但 `runs/go-parking-tasks` 的試跑證明這還不夠：7 張票沒有任何兩張能同時開始。

### 試跑看到什麼

- **條件永遠不成立。** 每張票都往同一份 `api/openapi.yaml` 加 operation、重新產生內嵌整份
  spec 的 `api.gen.go`、在同一個 `ParkingService` 加方法。「共用檔案沒有交集」在單一契約的
  架構下不可能成立
- **建議的解法行不通。** `tasks-format.md` 說「把共用的那段切成一張前置票」；但 strict server
  介面要求契約裡每個 operation 都有實作，只加契約的前置票得自己發明 stub
- **硬並行的衝突幾乎都是無害的。** 02 與 06 合回時 5 個檔衝突，全是兩邊各加一段（取聯集）
  或產生出來的檔（重新產生）；真正讓編譯壞掉的只有一個：兩張票各自新建同一個
  `usecase/command` package，測試輔助函式宣告了兩次
- **預測漏掉的正是出事的。** 漏列的是長大的介面（連帶它的測試 stub）、兩邊都新建的 package、
  `go.mod`；`plan.md` 只寫模組不寫路徑，路徑全是 worker 編的
- **沒有人負責合併。** 誰合、照什麼順序、產生檔怎麼解、合完要不要重跑閘門、誰翻 `@review`，
  都沒寫；編譯錯誤是合完才出現的

結論：「有交集就不能並行」太粗。共用檔案分三種，只有一種真的擋住並行；擋住並行的是**沒有人
合併**。

## 決定

### D1. 接合點分三種（`tasks-format.md`）

`共用檔案` 改名 `接合點`，每一列標種類：

| 種類 | 是什麼 | 例子 | 擋不擋並行 | 合回時怎麼解 |
| --- | --- | --- | --- | --- |
| `產生` | 由工具產生、不手寫的檔 | `api.gen.go`、mock、`go.sum` | 不擋 | **不手動合**：合完原始檔後重新產生 |
| `追加` | 每張票各加一段、不改別人那段 | 契約加 operation、介面加方法、組裝函式加一行接線、store 加欄位 | 不擋 | 取聯集，再跑閘門 |
| `爭用` | 兩張票要改**同一段**既有邏輯 | 兩張票都改同一個函式的分支 | **擋** | 不該發生——排成先後 |

**新建的 package 或共用輔助函式**不屬於三種任何一種：誰建它由切票時指定一張票擁有
（通常是 `00` 前置整理），其他票 `Blocked by` 它。前置票建的是 package 骨架與共用的測試輔助
函式，不需要假實作，所以 D1 取代掉那句行不通的「把契約切成前置票」。

列 `接合點` 時要涵蓋試跑漏掉的三類：會長大的介面**連同實作它的測試 stub**、會新建的
package、依賴檔（`go.mod` 這類標 `產生`）。

可以同時做的條件改成：`Blocked by` 都完成，而且**沒有共同的 `爭用` 接合點、沒有兩張都要新建
的東西**。

### D2. 要不要並行，由 `bdd-plan` 問（`plan-format.md` 新增 `## Parallel Work`）

接合點是技術設計的產物——哪些檔是產生的、哪些介面會長大，`bdd-plan` 定模組與契約時就知道。
`plan.md` 新增一節：

- **要不要並行**：`Ask user`，記成 `要 ← 使用者 <日期>` 或 `不要 ← 使用者 <日期>`。預設不要——
  並行換到的是時間，代價是合回的工作
- 要的話，列出這批的接合點（路徑與種類），並指出哪些地方是 `爭用`、或哪個新 package 會被
  多張票需要——那些交給 `bdd-tasks` 排成先後或前置票

`bdd-tasks` 照這一節標每張票的 `接合點`，不自己編路徑；這一節沒寫到、切票時才發現的，進
`plan.md` 的 `## 缺口`。選了「不要」時，`index.md` 的「可以同時開始」寫「不適用」。

### D3. 合回主線歸 `bdd-implement`（新增〈合回主線〉一節）

不新增 skill，也不設協調者：**每張在 worktree 做的票，由做它的那個 session 自己合回。**

1. **一票一 commit。** 開工前工作區要乾淨；做完只 stage 這張票動到的檔
2. 合回前先把主線拉進來（rebase 或 merge 主線），在 worktree 裡解衝突：`產生` 重新產生、
   `追加` 取聯集；碰到 `爭用` 或 D1 沒列到的衝突 → 停下來回報，不自己判
3. **在合併後的程式碼上重跑閘門**，加上主線上所有已勾完的票的場景（不只這張）——綠了才合
4. 合回之後判斷 `@review`：涵蓋這個 `.feature` 的票是不是全都勾完。合回是一張一張發生的，
   **讓最後一張完成的那次合回翻 tag**；判斷的依據是 `index.md` 列出的票檔勾選，不是記憶
5. 同時有兩張票要合回時，依票號小的先合

`state-tags.md` 的 `@review` 一列跟著改成「由讓最後一張涵蓋票完成的那次合回寫入」。

## 非目標

- 不改架構去追求零交集（契約拆檔、介面按 use case 拆）——D1 讓單一契約也能並行，拆不拆是
  專案自己的技術決定，`bdd-plan` 可以寫進技術節，但這份設計不要求
- 不做自動派工、不寫計算波次的腳本
- 試跑的四個小洞先不處理：`bdd-tasks` 確認步驟沒有代演規則、「已有骨架就跳過」的判準、
  `plan.md` 殘留舊票號沒人能修、票檔缺口裡的技術猜測要不要用測試釘住

## 考慮過的做法

| 做法 | 取捨 | 結果 |
| --- | --- | --- |
| A. 維持「共用檔案零交集」，要求 `bdd-plan` 把架構拆到不共用 | 衝突最少；但每個專案都得為了並行改架構，而 `bootstrap.go` 這類組裝點永遠共用 | 捨棄 |
| **B. 接合點分種類，只有 `爭用` 擋並行；做票的 session 自己合回**（本文件） | 單一契約也能並行；多一套合回規則 | **建議** |
| C. 另設一個合併 skill 或協調者 | 合併責任集中；但多一個交接點，而且它看不到每張票做時的脈絡 | 捨棄 |

## 會動到的檔案

- `skills/bdd-tasks/references/tasks-format.md`：D1，取代〈共用檔案與同時跑〉
- `skills/bdd-tasks/SKILL.md`：第 3 步、Verification 跟著 D1／D2
- `skills/bdd-plan/SKILL.md`、`references/plan-format.md`：D2
- `skills/bdd-implement/SKILL.md`：D3
- `skills/bdd-formulation/references/state-tags.md`：`@review` 的寫入者
- README 產物表、CLAUDE.md、PLAN.md 提到 `共用檔案` 處

## 怎麼驗

從試跑的 baseline（`runs/go-parking-tasks` 的 `65082b6`）重來一次，再派 worker 跑：選「要並行」，
預期 `index.md` 至少有一波可以同時開始，兩張並行的票合回時只出現 `產生`／`追加` 的衝突、
照規則解完閘門綠，`@review` 由最後一次合回翻。

## 最不確定的地方

- **`追加` 與 `爭用` 的界線靠預測。** 兩張票都在同一個 service 檔「加方法」是追加；若其中一張
  順手改了共用的 helper，就變成爭用。D3 第 2 步的「停下來回報」是唯一的保險
- **重跑閘門的範圍**：「所有已勾完的票的場景」要有一個能跑它們的命令，取決於 tag 的組法；
  試跑用的是 `-godog.tags` 與 `-godog.paths`，還沒驗過多張票合起來跑
