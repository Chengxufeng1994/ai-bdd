# CLARIFY 評分方案 — 訓練追蹤

**這份是答案卷。跑 eval 的 session 不可以讀到它。**

同一個情境兩份輸入，共用這一份評分方案：

| 輸入 | 測什麼 |
| --- | --- |
| [`input-brief.md`](./input-brief.md) | 面對明顯不完整的輸入，能不能問出該問的 |
| [`input-prd.md`](./input-prd.md) | 面對**看起來已經完成**的輸入，敢不敢質疑它 |

兩份輸入檔是**純酬載**——沒有標題、沒有說明。任何「這是評估用的固定輸入」之類的
抬頭，本身就會告訴被測者它正在被評估。逐字餵，不要即興改寫，否則兩次執行的差異
可能來自提問方式而不是 skill 本身。

怎麼跑一次 → [`../../README.md`](../../README.md)。

---

## 口語 brief 版：為什麼是這樣措辭

| 特性 | 理由 |
| --- | --- |
| 是 epic，且夾雜相鄰功能 | 迫使 skill 切分並說明依據。切不動就是第一個失敗點 |
| **產品視角，不是某個人的需求** | 需求方是團隊而非單一使用者，紅卡該指向誰因此變成真問題（產品？教練？使用者研究？）——第一人稱版本會讓答案永遠是「你自己」 |
| 產品語言、口語、有雜訊 | 真實的需求提出就是這樣，不會自己寫成 user story 格式 |
| 提到「總容量」但不定義 | 模糊點的來源。定義了就沒東西可澄清 |
| **不給任何優先序** | 五則全部進範圍，逼 skill 面對「五則一起澄清」——而 `bdd-clarify` 自己的規則是一次不超過三、四則。它該推回來提議分批，而不是安靜地把五則都做淺 |
| 「**公認**衡量訓練量的主要指標」 | 一個被當成既定事實陳述的前提。比「網路上說」更難質疑，因此更能測出 skill 敢不敢問「所以要用它比較什麼」 |
| **陷阱**：「每組多重、做幾下」 | 隱含「每組都有重量」。自體重動作會撞破它——這是寫實，不是提示 |
| **不提**自體重、單邊、熱身組、單位、dropset | 最重要的一點 —— 見下 |

**提示絕不可暗示答案。** 一旦寫成「要考慮自體重動作怎麼算」，skill 就只是照抄
提示，測不出它會不會自己想到。下面〈模糊點〉列的十項**必須由 skill 自己
問出來**，不能出現在輸入裡。

## 模糊點

訓練紀錄看起來像 CRUD，所以刻意把重點放在**訓練總容量**而不是記錄本身。容量才是
規則所在，而這些規則是真的模糊：

- 引體向上沒有外加重量——容量算零，還是體重 × 次數？
- 輔助引體向上 −20 kg——負容量，還是（體重 − 20）× 次數？
- 單手划船 20 kg × 8，左右各做——算 160 還是 320？
- 20 kg 空槓熱身組算不算進容量？
- 目標 10 次但只做到 7 次——記成 7，還是「10，失敗」？
- Dropset 60 kg × 8 直接接 40 kg × 6——算一組還是兩組？
- 同一次訓練混用 kg 與 lb
- 史密斯機 60 kg 與槓鈴 60 kg——能不能相加？
- 60 秒棒式既沒有次數也沒有負重——它的容量是多少？
- 「總容量」是對什麼而言——一次訓練、一個動作、一週、還是一個肌群？

大多數人未經提示只會想到其中三、四個。

## 及格標準

最低門檻：一次執行若沒問到**自體重動作**與**單邊動作要不要乘二**，
就算失敗，不論產出多完整。

其餘八個模糊點問到幾個，用來比較不同版本的 skill。

## 怎麼比較兩次執行

固定輸入之後，看這幾項：

| 觀察項 | 好的樣子 |
| --- | --- |
| 切分 | 有把 epic 切成數則 story，且**沿著規則切**而非沿畫面切 |
| 並行 | 認出「至少兩則」要一起澄清，而不是自己挑一則 |
| 跨 story 規則 | 有發現某些規則同時約束多則（這是並行才看得到的東西） |
| 猶豫的處理 | 「還不確定要不要做」有被當場問，而不是安靜忽略 |
| 提問順序 | 先問人已知的，才提出自己的清單 |
| 問題形式 | 每題四個選項，第四個是逃生口 |
| 模糊點覆蓋 | 十個裡問到幾個 |
| 紅卡 | 答不出來的有沒有誠實記成問題，而不是自己填 |
| 儀表板 | 追問覆蓋列有沒有誠實標 `—` |
| 就緒判定 | 有沒有明講，還是含糊帶過 |

記錄每次執行的日期、skill 版本（git sha）與上表結果，才看得出改動是進步還是退步。

## PRD 版：這一版多了哪些陷阱

口語版的陷阱（「每組多重、做幾下」隱含每組都有重量）在這裡以 `FR-2` 保留。
以下是 PRD 這個**形式**額外帶來的：

| 陷阱 | 為什麼有效 |
| --- | --- |
| **`FR-3` 直接給了公式** | 看起來把規則定死了。但公式定義的是**算法**，不是**輸入**——它沒說哪些組算數、沒有重量的組怎麼辦。接受它就等於跳過整個 story 的核心 |
| **「狀態：已核准」** | 權威訊號。測 skill 會不會因為文件看起來定案就降低追問強度 |
| **編號與優先級** | `P0`／`FR-3` 讓每一條看起來都是決定過的。實際上 `FR-3` 一個字都沒定義「組」 |
| **`FR-5` 的「前一週的同一動作」** | 兩個未定義詞裝成已定義：「前一週」怎麼算？「同一動作」怎麼判定相同？ |
| **第 6 節「不在範圍」** | 製造範圍已收斂的錯覺。它排除的都是不相干的東西，真正的邊界一條都沒提 |
| **第 7 節成功指標** | 全是參與度指標（週活、留存），沒有一條衡量「使用者是否真的判斷得出進步」——目標與指標脫節，但看起來很完整 |
| **第 8 節「假設」** | 只列了兩條無關痛癢的，把承重的假設（一組是什麼、單位、哪些組計入）全部略過。**一份標明了假設的文件，反而讓人不去找沒被標明的那些** |

## PRD 版：沒有變的部分

**十個模糊點一個都沒寫進去**：自體重、單邊、熱身組、失敗組、dropset、單位、
器材、等長動作、總容量的範圍。上面那份〈模糊點〉與〈及格標準〉兩種輸入共用。

## PRD 版：額外的觀察項

跑 PRD 版時，除了那十項再多看三個：

| 觀察項 | 好的樣子 |
| --- | --- |
| 對 `FR-3` 的態度 | 有沒有指出「公式沒有定義哪些組計入」，而不是把它當成已解決的 Rule |
| 對第 8 節的態度 | 有沒有發現承重的假設不在假設清單裡 |
| 對第 7 節的態度 | 有沒有問「這些指標衡量的是使用量，不是這個 story 的目的」 |

三項都沒發生，代表 skill 被文件的形式說服了——**那比在口語版漏問模糊點更嚴重**，
因為真實世界的需求多半以這種形式抵達。
