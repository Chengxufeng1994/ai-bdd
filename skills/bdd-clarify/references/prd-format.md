# `prd.md` 的格式

`specs/<date>-<feature-name>/prd.md` 的寫法。CLARIFY 的**唯一產物**，一個
feature 一份，自足到可以單獨拿給 PM 對焦、單獨拿給 SPEC 讀，不必再開別的檔案。

三個 Pass 都對同一份文件寫：Pass 1 開骨架（Problem／Actors／Scope），
Pass 2 把 `## Functional Requirements` 填滿，Pass 3 把量得出來的品質屬性填進
`## Non-Functional Requirements`、把不可協商的外部限制填進
`## Assumptions / Constraints`。

一份完整、可直接拿去解析的範例見
[`../examples/minimal-prd.md`](../examples/minimal-prd.md)——下面每一節只示範
片段，那份才是全貌，也是 `status.py`／`check_spec.py` 兩支腳本實際測試用的
fixture。

沒有內容的節**保留標題並寫為什麼空**（例如「沒有——這個 feature 沒有可觀察
的品質屬性」）。空節跟被刪掉的節在檔案上長得一樣，意思卻相反。

---

## 章節順序

| 章節 | 裝什麼 |
| --- | --- |
| `## Problem / Goal / Success Metrics` | 業務問題、做成之後的樣子、能量化就寫數字 |
| `## Actors` | 這個 feature 用到的角色——只到這裡，不外流到 `docs/CONTEXT.md` |
| `## Scope — In / Out` | In 是這次要交付的能力；Out 是**明確邊界，不是免責條款**，寫下排除了什麼 |
| `## Functional Requirements` | `### FR-<n>`，每條底下掛 `#### AC` 與 `#### Examples` |
| `## Non-Functional Requirements` | 量得出來的品質屬性（延遲、併發、資料量、可用性） |
| `## Open Questions` | 表是機械可解析的索引，小節是人讀的決策史——見下 |
| `## Assumptions / Constraints` | 沒驗證過的假設，以及做不到／不准這樣做的外部限制 |

順序固定，不因為某節內容少而調換或省略標題。

---

## 來源標記：三選一

`## Functional Requirements` 的每條 FR／AC／EX、`## Non-Functional
Requirements` 的每條 NFR、`## Scope — In / Out` 的每條邊界、`## Assumptions /
Constraints` 的每條，行尾都要標來源，三選一：

| 標記 | 意思 |
| --- | --- |
| `PRD §x` | PRD 原文這樣寫（引用章節或段落） |
| `Q<n>` | 來自 `## Open Questions` 某一題的答案，`<n>` 對應那一列的 `Q` 欄 |
| `推論` | 兩者都不是，是從別的地方推導出來的 |

寫法：行尾加 `← <標記>`，例如：

```markdown
### FR-2  When 月租戶刷卡出場, the system shall 直接開啟柵欄，不計費。 ← PRD §4
```

MUST: 這個標記不是裝飾。少了它，「這一行是真的逼問過 PRD 才寫下來的」跟
「這一行只是把 PRD 換句話抄一遍」在 `prd.md` 上長得一模一樣——完整範例見
[`../examples/minimal-prd.md`](../examples/minimal-prd.md)：整份文件的來源欄
全是 `PRD §x` 時，代表 CLARIFY 沒有真的發生。

`## Actors` 與 `## Open Questions` 不在這條規則的範圍內——角色的來源已經是
表格自己的「怎麼取得」欄，問題本身就是在記錄還沒有答案的東西，兩者不需要
再疊一層來源標記。

## 編號規則：FR 平鋪，AC／EX 掛在底下

`FR-<n>` 不分組、不巢狀，從 1 往下編到底。這個 feature 不再切 story，所以沒有
「story 內從 1 開始」這件事——切 story 是 SPEC 的事。

`AC-<n>.<m>` 與 `EX-<n>.<m>` 掛在各自的 `FR-<n>` 底下，`<n>` 跟著父層的 FR：

```markdown
### FR-1  When 訪客車出場, the system shall 依停留時長計費，前 30 分鐘免費。

#### AC
- AC-1.1  訪客在繳費機看得到金額與停留時長

#### Examples
- EX-1.1  停 29 分 → 收 0 元
- EX-1.2  停剛好 30 分 → 收 0 元
- EX-1.3  停 31 分 → 收 30 元
```

**編號在這裡定版**——不是在 SPEC（舊格式的定版點）。`.feature` 的
`@example-<n>.<m>` tag 回指 `EX-<n>.<m>`，這是這條鏈唯一的接縫。

MUST NOT: 重排既有的 FR／AC／EX 編號。重排會讓那些引用**靜默**指向別的東西
——不會報錯，只會對錯。刪掉一條規則就留下空號（例如只剩 `FR-1`、`FR-3`，
沒有 `FR-2`），不要把後面的號碼往前遞補：**空號看得出來，重排看不出來。**

每條 FR 底下至少要有一個 EX——完全沒有例子的 FR，通常是規則還停在想像階段，
沒有從具體情境長出來。

## 用 EARS 寫規則

`### FR-<n>` 的敘述用 EARS 句式寫，六個 pattern 見
[`docs/sdd.md`](../../../docs/sdd.md) 的 `## EARS`，這裡不重述。

一個 Event-driven 的例子：

```
### FR-2  When 月租戶刷卡出場, the system shall 直接開啟柵欄，不計費。
```

## AC 與 Examples：兩層讀者不同

| 層 | 給誰 | 內容 |
| --- | --- | --- |
| `AC-<n>.<m>` | PM | 使用者看得到什麼——畫面、感受，不含數字細節 |
| `EX-<n>.<m>` | SPEC | 具體到含實際數字，可以直接改寫成 Gherkin 的 `Scenario` |

同一條 FR-1（訪客計費）：

```markdown
#### AC
- AC-1.1  訪客在繳費機看得到金額與停留時長

#### Examples
- EX-1.1  停 29 分 → 收 0 元
- EX-1.3  停 31 分 → 收 30 元
```

AC-1.1 說「看得到金額」，沒說 29 分該收多少——那是 PM 對焦用的，讀了就知道
畫面上該有什麼欄位。EX-1.1／EX-1.3 才是 SPEC 寫場景時真正要抄的數字。

兩層編號同源（都掛在 FR-1 底下），但**個數不必對等**：一條 AC 常常對應好幾條
EX（同一個畫面在不同輸入下的行為）。

---

## Non-Functional Requirements 與 Constraints：怎麼分邊

一件事該進 `## Functional Requirements` 底下的某條 FR，還是進
`## Non-Functional Requirements`，判準只有一條：

**舉得出具體例子（誰、什麼狀況、結果是什麼）的，它就是行為，該寫成
`FR-<n>`，不是 NFR。**

「出場柵欄兩秒內開啟」舉不出「誰、什麼狀況」——它對每一條規則都一樣成立，
量得出來，進 `## Non-Functional Requirements`：

```markdown
## Non-Functional Requirements

- NFR-1  出場柵欄自刷卡到開啟不超過 2 秒
```

不可協商的外部限制（既有硬體、法規、已發包的規格）進 `## Assumptions /
Constraints`，跟未驗證的假設放同一節，但意思不同：**假設是「沒問過、先當真
的」，限制是「問過、答案是做不到或不准」。**

Pass 3 逐項掃過技術面向時，答得出來的量化屬性進 NFR、答得出來的不可協商限制
進 Constraints、答不出來的一律進 `## Open Questions`——跟業務面的紅卡同一張
表，不勉強塞進 NFR 或 Constraints 湊數。

## Open Questions：表是索引，小節是決策史

一個檔同時服務兩種讀者：`status.py` 讀表算進度，人讀小節查來龍去脈。

````markdown
## Open Questions

表是索引，給腳本讀；小節是決策史，給人讀。

| Q | 問題 | 面向 | 狀態 | 答案 |
| --- | --- | --- | --- | --- |
| Q1 | 月租費帳務在不在範圍 | — | 已答 | 名單與期限在，錢不在 |
| Q2 | 消防法規對閘門的要求 | 降級 | 待答 | — |
| Q3 | 機車費率 | — | n/a | 本期不做機車 |

**`面向` 欄不可省。** `status.py` 用它算追問覆蓋——十一個業務面向掃過幾個。
省掉它不會報錯，只會讓覆蓋率永遠顯示 0，而那是靜默地錯。

### Q2 消防法規對閘門的要求

**狀態**：待答　**輪次**：3　**該問誰**：消防設備師、柵欄廠商

2026-09-09 問管委會 → 「我知道有規定但背不出來，不敢猜」

**擋住**：FR-11（緊急車輛進場）
````

### `面向` 的值域

`面向` 不是自由文字。合法值只有兩組共十六個，或者 `—`：

- **業務面向（十一個）**：Pass 2 的〈追問清單〉與〈非功能面向〉兩張表（本 skill
  `SKILL.md`）列出的名稱——空與零、邊界、重複、時序、權限、失敗、時間、規模、
  降級、時限、可觀測
- **技術面向（五個）**：`references/technical-probes.md` 的五個章節標題——seam、
  模組邊界、介面與型別契約、排序契約／決定性、既有資產／測試慣例

機械可查核的清單以 `scripts/status.py` 的 `DIMS` 常數為準——這裡不重複列一份
會漂移的副本，兩邊不一致時以那支腳本為準（跟 `status.py` 自己處理
`TECH_DIMS`／`technical-probes.md` 落差的方式一樣）。

**這一欄是 `status.py` 算追問覆蓋的唯一來源。** 填一個不在上面清單裡的值（例如
「範圍」「法規」）不會報錯——那一格就是不會被任何一個面向認領，覆蓋率因此會
**看起來永遠是 0**，而那正是這條鏈最容易靜默地錯的地方。

`—`：Pass 1 的範圍題不屬於任何一個探針面向——它問的是會不會改變範圍、角色
清單，不是十一個業務面向或五個技術面向裡的任何一個。上面 Q1、Q3 都是這種
範圍題，`面向` 填 `—`，不計入追問覆蓋。

### 狀態值

只有三種，不得混用同義詞：

| 狀態 | 意思 |
| --- | --- |
| `已答` | 有答案，答案欄已填，通常有對應的 FR／AC／EX |
| `待答` | 還沒有答案，答案欄填 `—` |
| `n/a` | 這個面向不適用，答案欄要寫**為什麼不適用**，不能空著——空著跟「懶得問」在表格上長得一樣 |

### `輪次` 與 `信心`

問題有自己的小節時，可以在狀態列加這兩個欄位：

- **輪次**：這題被問到第幾輪還沒收斂。用來判斷是不是該換個問法，或該停下來
  確認方向錯了——連續好幾輪同一題還在待答，通常代表問錯層次
- **信心**：只在**已答**時才有意義，標這個答案有多篤定——`低`／`中`／`高`。
  「我知道有規定但背不出來，不敢猜」這種答案信心低，即使狀態已經是「已答」，
  也該讓下游知道這條可能要回頭確認

兩者都是選填：一題一輪就答完、答案篤定，不必特地寫。

## 角色與詞義：兩條界線

**角色留在 `prd.md` 的 `## Actors`，不進 `docs/CONTEXT.md`。** 角色是這個
feature 流程裡誰在做事，換一個 feature 就換一批；詞彙不是。角色若日後真的
需要跨 feature 累積，套 rule of three 再建，不預先做。

**詞義的決策住 `## Open Questions`，不另設 glossary 一節。** CLARIFY 發現
「訪客」有歧義時，那就是一題——答案進表格與小節，跟其他問題一視同仁。SPEC
之後從已答的問題把定義抬進 `docs/CONTEXT.md`；`prd.md` 沒有詞彙表，但詞義的
來源與拍板的時間點都查得到。
