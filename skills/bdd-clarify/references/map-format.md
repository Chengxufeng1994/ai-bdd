# `example-mapping.md` 與問題檔的格式

Pass 2 兩個產物的寫法。讀這份的時機：第一次建一份 map，或不確定某個欄位該寫什麼。

另外兩個產物的格式在別處：`brief.md` → `prd-breakdown.md`，
`actor.md` → `actor-definition.md`。

---

## 問題檔的狀態列

每個問題檔的第三行是狀態列。**紅卡靠它辨識，不是靠所在目錄**：

```markdown
**狀態**: 待答（之後再問）· **輪次**: 2
**狀態**: 已答 · **輪次**: 2 · **信心**: 中
```

檔名用描述問題的 kebab-case，不用編號：`single-arm-reps.md`。

Rule 與 Example 需要編號是因為 Gherkin tag 會引用它們；問題不進 tag，所以描述性
的名字更有用——`grep -L '狀態.*已答'` 列出還開著的那些時，看的是檔名。

---

## `<feature-slug>` 怎麼取

由 story 導出，kebab-case，描述**能力**而非動作：`total-training-volume`，
不是 `add-volume-calculation`。動作會過去，能力會留下。

---

## 循環中的 `example-mapping.md`

規則還沒抽出來時，它累積原始素材。**停在任何一輪，這份檔案都該是完整可用的**：

```markdown
# Example Mapping: 看到訓練量並判斷進步

**Story**: 作為 <角色>，我要 <能力>，以便 <價值>
**日期**: <YYYY-MM-DD>
**狀態**: 澄清中（第 2 輪）

## 已確定
- 使用者自己填重量，系統不區分自體重／器材／輔助 ← `questions/bodyweight-volume`
- 跨日訓練歸屬於開始那一天 ← `questions/cross-midnight`

## 跳過的
- 單邊動作次數怎麼填 —— 之後再問 ← `questions/single-arm-reps`

## 追問覆蓋
空與零 ✓ · 邊界 — · 重複 — · 時序 ✓ · 權限 n/a · 失敗 — · 時間 ✓ · 規模 —
降級 — · 時限 n/a · 可觀測 —
```

`## 追問覆蓋` 十一個面向缺一不可，包含最後三個非功能面向。少列一個和標 `—` 在
檔案上長得不一樣：`—` 是「知道還沒問」，沒列是「根本沒想到有這一格」，
而 `status.py` 會把沒列的印成 `?`。

標記三種：`✓` 問過、`—` 還沒問、`n/a` 不適用。**`n/a` 要在 map 裡寫理由**，
否則它跟「懶得問」分不出來。

---

## 抽規則之後

```markdown
**狀態**: 已抽規則
**就緒判定**: 未就緒（提案）—— <一句話理由>

> 就緒與否由三方投票決定。以上是提案，不是結論。

## 規則

### Rule 1. <規則敘述>
- Example 1.1 <具體例子，含實際資料>
- Example 1.2 <具體例子>

## 未解的問題
| 問題 | 一句話 |
|---|---|
| `single-arm-reps` | 單邊動作次數怎麼填 |

## 備註
<否決掉的例子與理由、對方推翻過我的哪些提案、觸發了訊號但判定不拆的理由>
```

MUST NOT: 重排既有的 Rule 與 Example 編號。下游的 Gherkin 情境回指
`Example 1.1`，重排等於讓那些引用**靜默**指向別的東西——不會報錯，只會對錯。

「切分依據」不寫在這裡，寫在 `brief.md`：依據是跨 story 的，寫進其中一則就只有
那一則看得到。

「對方推翻過我的哪些提案」值得留：那記錄的是慣例在這個專案不適用的地方，
而那正是外人最容易踩錯、文件最少提及的部分。

## 進度為什麼不存成檔案

```bash
python3 <skill>/scripts/status.py <專案根>
```

印出每個 feature 的規則數、例子數、已答／待答、就緒判定、追問覆蓋，
以及還開著的問題檔清單（含根層的 Pass 1 問題）。

MUST NOT: 另存一份儀表板檔案。

上面每一個數字都已經有來源——規則與例子數在 `example-mapping.md`、就緒判定在它的
檔頭、紅卡在 `questions/` 的狀態列、追問覆蓋在 map 的覆蓋段。存一份彙總等於
**同一個數字兩個地方**，而它們遲早不一樣：實測過一次，map 檔頭寫 21 個例子、
儀表板寫 23、實際 23。

怎麼讀它：

- **「已答／待答」就是已知與未知的比例**——澄清的進展看這個，不是看規則數。
  規則會因為某個答案消掉一整類問題而突然變少，那是進步不是退步。
- **追問覆蓋那一欄的用途是看見「還沒問的」。** 紅卡是「問了沒答案」，覆蓋是
  「根本還沒問」——後者平常完全看不見，而它才是漏掉整類邊界的原因。
