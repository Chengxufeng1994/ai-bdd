# 問題檔的格式

問題檔（`questions/*.md`）的寫法。讀這份的時機：第一次開一個問題檔，或不確定
狀態列該填什麼。

另外兩個產物的格式在別處：`brief.md` → `prd-breakdown.md`，
`actor.md` → `actor-definition.md`。

---

## 問題檔的狀態列

每個問題檔的第三行是狀態列。**紅卡靠它辨識，不是靠所在目錄**：

```
**狀態**: 待答（之後再問） · **輪次**: 2 · **story**: log-a-workout · **面向**: 邊界
**狀態**: 已答 · **輪次**: 2 · **信心**: 中 · **story**: log-a-workout · **面向**: 時序
```

| 欄位 | 值 | 為什麼要有 |
| --- | --- | --- |
| `story` | story slug，或 `全部`（這一批共通） | 一個 slice 的問題全放同一個目錄，靠這欄歸屬 |
| `面向` | 十一個業務面向或技術面向之一 | **追問覆蓋改成從這裡算**，不再另存一段 |

`n/a`（這個面向不適用）也開一個問題檔，狀態寫 `n/a`，理由寫在本文。
否則它跟「懶得問」在檔案上長得一樣。

檔名用描述問題的 kebab-case，不用編號：`single-arm-reps.md`。

Rule 與 Example 需要編號是因為 Gherkin tag 會引用它們；問題不進 tag，所以描述性
的名字更有用——`grep -L '狀態.*已答'` 列出還開著的那些時，看的是檔名。

---

## 規則與例子去哪了

規則與例子**不再是 CLARIFY 的產物**。它們的定版編號誕生在 `spec.md` 的
`## Example Mapping` 段——也就是真正要用 tag 引用它們的那一刻。

原本凍在 CLARIFY 的編號，是在最不確定的時候做最不可逆的事：那時 story 邊界
還可能合併或再切，而 `MUST NOT 重排編號` 一旦生效就改不動了。

CLARIFY 仍然會在追問過程中把規則講出來——那是問下一題的前提。
只是它們留在問答的紀錄裡，不另存一份檔案。

---

## 進度為什麼不存成檔案

```bash
python3 <skill>/scripts/status.py <專案根>
```

印出每個 feature 的規則數、例子數、已答／待答、就緒判定、追問覆蓋，
以及還開著的問題檔清單（含根層的 Pass 1 問題）。

MUST NOT: 另存一份儀表板檔案。

上面每一個數字都已經有來源——紅卡／已答數在 `questions/` 的狀態列，追問覆蓋在
每個問題檔的 `面向` 欄位。存一份彙總等於**同一個事實兩個地方**，而它們遲早不
一樣：實測過一次，map 檔頭寫 21 個例子、儀表板寫 23、實際 23——這正是追問覆蓋
改成從問題檔算、不再手寫一段彙總的理由。

怎麼讀它：

- **「已答／待答」就是已知與未知的比例**——澄清的進展看這個，不是看規則數。
  規則會因為某個答案消掉一整類問題而突然變少，那是進步不是退步。
- **追問覆蓋那一欄的用途是看見「還沒問的」。** 紅卡是「問了沒答案」，覆蓋是
  「根本還沒問」——後者平常完全看不見，而它才是漏掉整類邊界的原因。
