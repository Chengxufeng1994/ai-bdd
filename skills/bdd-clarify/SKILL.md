# CLARIFY — 把需求逼成具體例子

一段模糊的敘述進來，出去的是：**規則**、每條規則的**具體例子**、答不出來的
**問題**，以及一句「能不能開工」的判定。

不寫 Gherkin。不談實作。不設計資料表。

## 使用時機

- 拿到一段需求或一則 story，但講得太抽象，不知道要做到什麼程度
- 需要判斷這則 story 該不該進 sprint
- 準備寫規格或 `.feature` 檔之前，先確認例子夠不夠
- 懷疑需求有沒想到的邊界情況

## Skill Boundaries

- 只是要把一則太大的 story 切開 → 改用 `bdd-clarify-story-splitting`
- 已經有一疊跳過的問題要再收斂 → 改用 `bdd-clarify-loop`
- 要把例子寫成 Gherkin → 改用 `bdd-spec`
- 要決定情境跑在哪一層測試、實作順序 → 改用 `bdd-plan`
- 產出是 `example-mapping.md`，**不是**規格、程式碼或資料模型

---

## 前置確認（Ask user）

Ask user: 若以下不明確，先問清楚再開始。

**要澄清的需求**：一段描述。這是唯一必要的輸入。

產物路徑不必問，見「產物」。

NEVER: 在需求還沒拿到時自行想像一則 story 來跑流程。那會產出一份看似完整、
實則憑空的 map，而錯誤全藏在專業的格式底下。

---

## 流程

```
一段敘述（新的）        或        繼續澄清（bdd-clarify [feature]）
   ↓                                    ↓
1. 切分成數則 story          2. 續跑：預設全部未就緒的 feature
   ↓                                    ↓
   └──────────── 3. 澄清循環（每輪）───────────┘
                   ├─ 逐題問：答 → clarify/ ／ 跳 → questions/
                   ├─ 抽出本輪能抽的規則 → 更新 example-mapping
                   ├─ 更新儀表板：已知多少、未知多少
                   └─ 還有未知？ → 下一輪
                          ↓
                 4. 就緒判定（提案）
                          ↓
                 5. 收尾：標記完成，產物保留
```

### 1. 切分

拿到的通常是 epic。先切成數則可獨立驗收的 story 並**說明切分依據**，然後直接開始
——**不要問這次要跑哪幾則**，預設全部。要限定的人會自己說。

> "Rules make natural fault lines for slicing your story."
> —— [Example Mapping introduction](https://cucumber.io/blog/bdd/example-mapping-introduction/)

規則是獨立成立的約束，沿它切，每一則都還可驗收。沿使用者旅程或畫面切則容易切出
「做一半」的 story——前半段交付了，但沒有任何一條規則被完整滿足。

**一則 story 一份 map，但一次工作階段可以跑好幾則。** 約束的對象是產物不是階段：
就緒判定是 per-story 的，但**跨 story 的規則只有並排時才看得見**。

切出來很多則時不必分批：澄清是**逐題**進行的，一輪只問幾題，不會因為 feature 多
就變淺。但要在每輪結束回報進度，讓對方知道還剩幾個。

若對方給的是解法（「用總容量當指標」），先往回問到行為：**誰、想達成什麼、
為什麼**。指標是為某個目的挑的手段——後面判斷邊界時，判準是「哪一種算法比較能
達成那個目的」，而不是「哪一種比較好算」。

### 2. 續跑

輸入不是新敘述、而是「繼續澄清」時：

| 呼叫方式 | 範圍 |
| --- | --- |
| `bdd-clarify` | **預設：所有還沒就緒的 feature**，依儀表板順序逐一往下 |
| `bdd-clarify <feature>` | 只跑指定的那一個 |

**不要問對方要跑哪一個。** 預設全部，想限定的人自己會帶參數——多問一次等於把
決定推回去，而多數時候答案就是「都繼續」。

開始每一個 feature 之前，讀三樣東西：`example-mapping.md`（已確定什麼、抽出哪些
規則）、`questions/`（上次跳過什麼、為什麼跳）、`clarify/`（答過什麼）。

IMPORTANT: 重問一題已經答過的，比漏問一題更傷信任——它證明你沒有讀既有產物。

換 feature 時明講「現在開始 X」，並在每一輪結束回報還剩幾個。跑多個 feature 時，
**跨 feature 的共用規則會浮現**——那是一次跑完全部的主要收穫，單獨跑一個看不到。

### 3. 澄清循環 —— 一次一題，每輪抽規則

從敘述裡找模糊點，**一題一題問**，不要一次列出全部。

逐題是刻意的：問題是樹不是清單。一個答案常會消掉三個問題、長出兩個新的——
一次列完會產生一批**本來不該存在的問題**，然後有人真的去回答它們。

#### 值不值得問

MUST: 問之前先過這一關——**這題的不同答案，會不會導致不同的規則？**

不會，就不要問。這條篩掉的通常是最多的：追問清單掃出來的候選裡，有一大半的答案
其實不影響任何行為。**問題少而準，比多而全有用得多**——三十個平等攤著的問題，
人的反應是一個都不動。

**追問清單**（找模糊點用，不是待辦清單）

| 面向 | 問法 |
| --- | --- |
| 空與零 | 沒有資料、空字串、零筆、第一次使用時？ |
| 邊界 | 剛好等於上限？超過 1 個單位？ |
| 重複 | 同一個動作做兩次？重送？ |
| 時序 | 兩件事同時發生？順序顛倒？ |
| 權限 | 換一個角色來做？沒登入？ |
| 失敗 | 外部系統掛掉？逾時？做到一半斷線？ |
| 時間 | 跨日、跨時區、日光節約？過期的定義？ |
| 規模 | 一次一萬筆？ |

清單是起點不是全部——這個領域有什麼特有的失敗模式，一併找。

#### 一題長什麼樣

**4 ＋ 1**：四個具體答案，加一個逃生口。

```
單手啞鈴划船 20 kg，左右各做 8 下。次數欄要填多少？

  1. 填 8 —— 一邊算一組，另一邊不另計
  2. 填 16 —— 兩邊加總成一組
  3. 填 8，系統自動 ×2 —— 使用者不必自己換算
  4. 左右各記一組，共兩組 —— 分開記錄
  5. 不知道／先跳過

為什麼問：這直接讓總容量差兩倍，而幾種填法在畫面上長得一樣。
```

MUST: 1–4 **互斥且涵蓋光譜**，第 5 個永遠是逃生口。

四個具體選項比三個涵蓋得完整，但也更容易出現**湊數的那一個**。檢驗方法：
**把任一個選項拿掉，會不會少掉一種真實會發生的做法？** 不會，那它就是湊數的——
寧可只給三個，也不要用近義詞填滿版面。湊數的選項會稀釋真正的選擇，讓人隨便挑。

沒有逃生口時，人在不確定會挑一個看起來最合理的——而**被記成決定的猜測比開著的
問題更糟**：它看起來已解決，之後沒有人會回頭質疑。

選項本身是提案。對方回「都不是」時，那個更正比四個選項加起來更有資訊量——它往往
消掉一整類原本要問的問題，而不只是回答這一題。

#### 答了：三件事一起做

MUST: 一題確定，三件事同時發生，缺一個就是不一致狀態：

| # | 動作 |
| --- | --- |
| 1 | 寫成 `<feature>/clarify/<問題名稱>.md`：問題、選項、答案 |
| 2 | **`example-mapping.md` 立刻更新**——把答案記進「已確定」區 |
| 3 | 若這個答案消掉了其他還沒問的問題，說出來並跳過它們 |

第 2 項不可以留到最後一次做。剛答完那一刻你還記得為什麼；隔了二十題再回來併，
漏掉的機率高得多。而且澄清很少一次做完，**停在任何一輪，map 都該是完整可用的**。

#### 跳過：要記為什麼跳

寫成 `<feature>/questions/<問題名稱>.md`，並記下**跳過的原因**。有用的區分只有
一個：**還會不會再問**。

| 原因 | 後續 |
| --- | --- |
| 之後再問 | 下一輪重問，`bdd-clarify-loop` 會接手 |
| **這題不該問** | 抽規則時回頭確認它真的不影響任何規則。是 → 刪掉它 |

不要記「該去問誰」。使用這個 skill 的人自己知道要找誰，多一個欄位只是多一個要
維護、會過期的東西。

只記「跳過」不記原因，`questions/` 就會變成一堆分不出輕重的待辦——而那正是讓人
一個都不想動的狀態。

檔名用描述問題的 kebab-case，不用編號：`single-arm-reps.md`。Rule 與 Example
需要編號是因為 Gherkin tag 會引用它們；問題不進 tag，所以名字更好——`ls` 一眼看得
出還剩什麼。

#### 每一輪結束：抽規則、更新儀表板

MUST: 一輪問完就把**這一輪能抽的規則抽出來**，不要累積到最後。

抽規則的動作本身會暴露「這題其實沒答清楚」——一個答案在對話裡聽起來很明確，
一旦要寫成規則就會發現它缺條件。等全部答完才抽，那些漏洞會一次湧出來，而且
上下文已經冷了。

**規則抽象、例子具體。** 例子必須含實際資料：

- ✗「一個無效的使用者」—— 這是規則換句話說
- ✓「一個 token 在 3 秒前過期的使用者」

抽完更新兩處：`example-mapping.md` 的規則區，以及 `docs/bdd/dashboard.md`。

跨多則 story 的規則抽進 `glossary.md`，編號 `Shared 1`，各份 map 只回指編號
**不複製內容**——複製出去的會各自演化，半年後互相矛盾。

#### 什麼時候停

| 訊號 | 意義 |
| --- | --- |
| 一輪下來沒有新問題 | 收斂了，進就緒判定 |
| 剩下的都被標成「之後再問」 | 停，這一輪問不動了 |
| **連續兩題被跳過** | 可能問錯層次，或整組問題超出對方的知識範圍。停下來確認 |
| 問了兩三輪但問題總數不下降 | 不是問法的問題，是 story 太大 → `bdd-clarify-story-splitting` |
| **抽不出新規則** | 這一輪的答案沒有改變任何行為。問題選錯了，回頭看「值不值得問」那一關 |

倒數第二項的判準來自 Example Mapping：一則大小合適的 story，三方應該在
**25 分鐘左右** map 完；map 不完表示它太大或太不確定。

### 4. 就緒判定 —— 提出判定，票不是你投的

| 訊號 | 意義 | 出處 |
| --- | --- | --- |
| 未解的問題太多 | 不確定性過高 | 原文 |
| 規則太多 | story 太大，該沿規則切 | 原文 |
| 一條規則掛太多例子 | 規則太粗，該拆成數條 | 原文 |
| 25 分鐘內 map 不完 | 太大**或**太不確定 | 原文 |
| 有規則掛零個例子 | 這條規則其實沒被理解 | 本 skill 追加，非原文 |

IMPORTANT: **就緒與否由開發、測試、產品三方投票決定，不是由分析得出。** 你的
角色是把訊號攤開、提出一個判定，並明講「這是提案，最終由你們決定」。宣告
「未就緒」等於替團隊投了票。

未就緒有**兩條路**：規則太多、範圍太大 → `bdd-clarify-story-splitting`；
不確定性高、跳過的題還很多 → `bdd-clarify-loop`。只講後者會漏掉前者，而 story
太大時再多問幾輪也不會變就緒。

### 5. 收尾：標記完成，產物全部保留

`questions/` 為空、就緒判定通過之後：

1. **核對**：每個 `clarify/` 檔指名的規則，在 map 裡都找得到且有例子
2. `example-mapping.md` 狀態改為「已就緒」，儀表板同步
3. **`clarify/` 與 `questions/` 保留，不刪除**

核對不能跳過——它是「答了就更新 map」那條規則的驗收。若某個 `clarify/` 檔指向
map 裡不存在的規則，代表那題當時只記了答案沒有落地，**先補規則**。

#### 為什麼保留

規則記錄**決定了什麼**；`clarify/` 記錄**還考慮過什麼、為什麼否決**。後者塞不進
規則，卻正是這個 feature 下次要改時會問的第一個問題——「當初為什麼不選第二個
選項？」

每個 `clarify/` 檔實質上是一則微型 ADR：問題、考慮過的選項、選了哪個、理由。
ADR 是保存的，不是刪除的。

IMPORTANT: 保留不等於它們是規則的第二個真相來源。**規則以 `example-mapping.md`
為準**；`clarify/` 只回答「為什麼」，不回答「是什麼」。兩者衝突時以 map 為準，
並回頭修正那個 `clarify/` 檔的記載。

## 產物

```
docs/bdd/
├── dashboard.md              ← 各 feature 的進度，續跑時從這裡選
├── <feature-slug>/
│   ├── example-mapping.md    ← 規則與例子，唯一的真相來源
│   ├── clarify/              ← 答過的問題：決定與理由（微型 ADR）
│   └── questions/            ← 跳過的問題：待答與原因
└── glossary.md               ← 跨 feature 的共用規則與詞彙
```

全部保留。`clarify/` 與 `questions/` 不是暫時檔——它們是這個 feature 的決策史，
下次修改時的參考。

`<feature-slug>` 由 story 導出，kebab-case，描述**能力**而非動作：
`total-training-volume`，不是 `add-volume-calculation`。動作會過去，能力會留下。

### 循環中的 `example-mapping.md`

規則還沒抽出來時，它累積原始素材：

```markdown
# Example Mapping: 看到訓練量並判斷進步

**Story**: 作為 <角色>，我要 <能力>，以便 <價值>
**日期**: <YYYY-MM-DD>
**狀態**: 澄清中（第 2 輪）

## 已確定
- 使用者自己填重量，系統不區分自體重／器材／輔助 ← `clarify/bodyweight-volume`
- 跨日訓練歸屬於開始那一天 ← `clarify/cross-midnight`

## 跳過的
- 單邊動作次數怎麼填 —— 之後再問 ← `questions/single-arm-reps`

## 追問覆蓋
空與零 ✓ · 邊界 — · 重複 — · 時序 ✓ · 權限 n/a · 失敗 — · 時間 ✓ · 規模 —
```

### `dashboard.md`

續跑時從這裡選要接哪一個 feature：

```markdown
# 澄清進度

**更新於**: <YYYY-MM-DD>

| Feature | 規則 | 例子 | 已答 | 待答 | 狀態 |
|---|---|---|---|---|---|
| training-volume-progress | 5 | 12 | 8 | 4 | 澄清中（第 3 輪） |
| log-a-workout | 8 | 16 | 11 | 0 | 已就緒 |
| custom-exercise-library | 1 | 1 | 2 | 6 | 澄清中（第 1 輪） |
```

「已答／待答」就是**已知與未知的比例**——澄清的進展看這一欄，不是看規則數。
規則會因為某個答案消掉一整類問題而突然變少，那是進步不是退步。

**追問覆蓋那一列的用途是看見「還沒問的」。** 紅卡是「問了沒答案」，覆蓋列是
「根本還沒問」——後者平常完全看不見，而它才是漏掉整類邊界的原因。標記三種：
`✓` 問過、`—` 還沒問、`n/a` 不適用（要寫理由）。

IMPORTANT: 不要把 `—` 當待辦去硬填。標 `n/a` 並寫理由，比擠出一個假問題誠實。

### 抽規則之後

```markdown
**狀態**: 已抽規則
**就緒判定**: 未就緒（提案）—— <一句話理由>

> 就緒與否由三方投票決定。以上是提案，不是結論。

## 規則

### Rule 1. <規則敘述>
- Example 1.1 <具體例子，含實際資料>
- Example 1.2 <具體例子>

## 未解的問題
| 問題 | 一句話 |
|---|---|
| `single-arm-reps` | 單邊動作次數怎麼填 |

## 備註
<切分依據、否決掉的例子與理由、對方推翻過我的哪些提案>
```

規則與例子的編號會被下游引用（Gherkin 情境回指 `Example 1.1`），所以**編號一旦
寫出去就不要重排**。

「對方推翻過我的哪些提案」值得留：那記錄的是慣例在這個專案不適用的地方，而那正是
外人最容易踩錯、文件最少提及的部分。

## 產物隔離

文件型產物**全部住在 `docs/bdd/`**，一個目錄裝完。專案的其他地方不會多出東西。

| 規則 | 強度 |
| --- | --- |
| 只寫入 `docs/bdd/` 底下 | `MUST` |
| 不修改專案既有的任何檔案 | `MUST` |
| 沒有 `docs/` 就建一個 | `SHOULD` |
| 專案明文用別的文件根目錄就跟隨，仍加 `bdd/` 這層 | `SHOULD` |

`.feature` 是唯一例外：它同時是規格與可執行測試，**位置由測試框架決定**，留在
框架的慣例位置。鏈的完整性靠引用維繫，不是靠同目錄。
