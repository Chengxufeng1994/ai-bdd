# `prd.md` 的骨架

照抄即可。三個 skill 在不同時刻讀它：`bdd-capture` 建檔時、`bdd-discovery`
每一輪寫答案時、`bdd-formulation` 翻 `.feature` 時。`example-mapping` 讀它攤地圖。

一個 feature 一份，路徑 `specs/<date>-<feature>/prd.md`。一份 `prd.md` 裝這個
feature 的全部 story——story 由 CAPTURE 粗切、DISCOVERY 細切，見各自的 SKILL.md。

它是**一份從 draft 長到 complete 的活文件**：CAPTURE 建檔時只有開頭幾節與空的
story；DISCOVERY 每答一題就往 story 底下長一條 FR 或 AC；紅卡清空、需求方點頭，
狀態翻成 `已對焦`，`bdd-formulation` 與 `bdd-spec` 才讀它。

沒有內容的節**保留標題並寫為什麼空**，不要刪掉。空著的節跟被刪掉的節在檔案上
長得一樣，而它們的意思完全不同。

---

## 章節順序

| 章節 | 裝什麼 | 誰第一次寫 |
| --- | --- | --- |
| `## Document Overview` | 狀態、最後更新、結束方式、版本修訂歷史、核心關係人 | CAPTURE |
| `## Background` | 業務問題與現在什麼在痛 | CAPTURE |
| `## Goal` | 做成之後的樣子 | CAPTURE |
| `## Scope — In / Out` | In 是這次要交付的能力；Out 分兩類，見下 | CAPTURE |
| `## Personas` | `### P-<n>` | CAPTURE（五欄可留「（無資料）」），DISCOVERY 補 |
| `## User Stories` | `### US-<n> · <slug>`，底下三個分組 `#### FR`／`#### NFR`／`#### Q` | CAPTURE 寫標題與句子，DISCOVERY 填三個分組 |
| `## Non-Functional Requirements` | 跨 story 的品質屬性 | DISCOVERY |
| `## Assumptions / Constraints` | 沒驗證過的假設，以及做不到／不准這樣做的外部限制 | CAPTURE 抄原文的假設，DISCOVERY 改寫成問過的 |
| `## Success Metrics` | 能量化就寫數字；量不出來就寫「怎麼知道做成了」 | CAPTURE |
| `## Open Questions` | 表是機械可解析的索引，小節是人讀的決策史 | CAPTURE 填需求方自己列的開放問題，DISCOVERY 填其餘 |
| `## Further Notes` | 放不進其他節、但下一個接手的人會想知道的 | 任何一步 |
| `## 原文` | 需求方帶來的描述，逐字 | CAPTURE，之後**不得改寫** |

順序固定，不因為某節內容少而調換或省略標題。技術設計（seam、API、schema、
測試層級、風險）不在這份文件裡，那是 `spec.md`，格式見
`../../bdd-spec/references/spec-format.md`。

## Document Overview 的三個部分

```markdown
## Document Overview

**狀態**：澄清中　**最後更新**：2026-09-10　**結束方式**：—

### 版本修訂歷史

| 版本 | 日期 | 改了什麼 | 為什麼 | 誰 |
| --- | --- | --- | --- | --- |
| 0.3 | 2026-09-10 | FR-1 免費額度從「每趟 30 分」改成「一天總共 30 分」 | Q-15：早晚各來一趟的客人在舊規則下反而被多收 | 管委會主委 |

### 核心關係人

| 關係人 | 負責什麼 | 決策權 |
| --- | --- | --- |
| 管委會主委 | 需求方，日常庶務與月租帳 | 預算內、不動住戶權益的事可自行決定 |
| 區權會 | 住戶大會 | 動到住戶權益或預算外支出；兩個月開一次 |
| 消防設備師 | 消防法規 | 只答法規，不做決定 |
| 柵欄廠商 | 已發包的柵欄／繳費機 | 只答技術現況，不做決定 |
```

**狀態只有四個值**，判準是「下游能不能開工」：

| 狀態 | 意思 | 誰寫 |
| --- | --- | --- |
| `澄清中` | 還有待答問題，`example-mapping` 不該判就緒 | CAPTURE 建檔時 |
| `待對焦` | 紅卡清空了，等需求方過目 | DISCOVERY 在前沿空了時 |
| `已對焦` | 需求方同意 | `example-mapping`，依使用者的答覆 |
| `已凍結` | PLAN 已經消費過它，之後任何改動都要開新版本 | 尚無寫入者 |

這四個值講的是這份文件自己走到哪。下游的閘門：`bdd-formulation` 與 `bdd-spec`
只讀 `已對焦` 的 `prd.md`。

**結束方式**是 DISCOVERY 最近一輪怎麼停的，四選一：`收斂`／`阻塞`／`零進展`／
`喊停`，CAPTURE 建檔時寫 `—`。它跟 `狀態` 不同：`狀態` 說這份文件走到哪，
`結束方式` 說上一輪為什麼停在那裡。`阻塞` 要在 `## Open Questions` 對應小節寫清楚
卡在誰身上。

**已知弱點：沒有東西在強制這一欄。** `check_spec.py` 從不讀狀態欄，一份還停在
`澄清中` 的 `prd.md` 照樣能通過全部檢查。這一欄是給人看的宣告，不是機械閘門。

MUST NOT: 狀態欄寫題數。「9 題已答／10 題待答」是 `../../bdd-discovery/scripts/status.py` **算出來的**，
寫進文件等於同一個事實兩份，而它們遲早不一樣。

**版本修訂歷史的觸發條件**：文件到 `已對焦` 之後，任何動到 FR／AC 的改動都要
留一列——FORMULATION 可能已經照著寫了 `.feature`。`已對焦` 之前的來回不記，那是澄清過程
本身，決策史在 `## Open Questions` 的小節裡。

**「為什麼」那欄不可省。** 只記改了什麼，半年後有人會把它改回去。

**核心關係人由 CAPTURE 登記第一批（需求方自己與他點名的人），DISCOVERY 每冒出
一個新的受訪者就補一列。** `決策權` 這一格只有問的人寫得出來——`bdd-spec` 把整張表
原樣抄進 `spec.md`，不增列也不改寫。

**「決策權」不是裝飾。** 同一個人給的答案，有些是定案、有些只是提案（要開會
表決），下游要分得出來，否則會拿沒表決過的東西去寫規格。

MUST: 文件裡任何一個「該問誰」都必須指向這張表裡的某個關係人，不限
`## Open Questions`。指到表外的人＝那個人沒被登記為關係人，是文件的洞不是筆誤。

**已知弱點：這條沒有東西在檢查它。** `status.py` 只讀狀態欄與面向欄，從不讀
「該問誰」。一題點名了不在表裡的人，文件看起來完全正常。而**關係人若在事後補登，這條 MUST
會輕鬆通過卻毫無意義**——這正是關係人表必須在問的當下登記的理由：開一題就得知道
問誰，那一刻把他登記進表，`該問誰` 才指得到。

MUST NOT: 在這一節列「誰卡著哪幾題」。理由不是「那是算出來的」——沒有任何腳本
在算它；理由是**每一題自己在它的小節裡宣告掛在誰身上**，在這裡再列一份就是同一
個事實兩份，而它們遲早不一樣。

## Scope — In / Out

**In** 是這次要交付的能力。

**Out** 分兩類，因為**誰能回答**不同：

明確排除的能力：
- <這次不做什麼>

接受的風險：
- <因此接受了什麼後果>

推不出來、需要回頭問的缺口不在這裡列——它是一張紅卡，開進 `## Open Questions`。

## Personas：在三欄上加兩欄

一節開頭先寫一行，說明**這個 feature 是為誰做的**——不是「誰在流程裡出現」：

```markdown
**這個 feature 為誰做**：P-1（訪客）。P-2 出現在流程裡但不是這次的受益者 ← 推論
```

兩件事分開寫的理由：**出現在流程裡的角色，不一定是這次要讓誰過得更好。**
月租戶會刷卡出場，所以他在流程裡；但這個 feature 要解的是訪客算不出錢的問題。
不分開的話，story 會開始為「流程裡出現過的每一個人」各切一則，而其中幾則
沒有人在等它。

```markdown
### P-1  訪客

**是誰**：不在月租名單上的任何一台車 ← Q-8
**怎麼取得這個身分**：進場時未刷月租卡 ← Q-5（待答，取決於辨識方式）
**跟誰容易混**：跟「住戶的客人」不是同一件事——規約說訪客車位給住戶親友，
但實務上沒有東西在分辨 ← Q-7
**他要什麼**：出場前知道要付多少、付得掉 ← 推論
**現在什麼讓他痛**：（無資料）
```

前三欄沿用 v1 的 Actors 一節。新增的是**「他要什麼」**與**「現在什麼讓他痛」**——
FR 掛在 story、story 掛在 persona，**沒有目標的 persona 會產出沒有理由的 story**。

**「無資料」是合法的值，而且比編一個好。** 需求方常常是在轉述別人的痛（主委轉述
住戶、住戶轉述他的客人）。標「無資料」讓那件事在文件上看得見；填「訪客希望流程
順暢」則讓它消失。

## User Stories：三個分組，AC 巢狀在它的 FR 底下

### US-<n> · <slug>

`<slug>` 是這則 story 的交付識別名，**也是它的 `.feature` 檔名**。用 kebab-case，
不含空白。story 的句子寫在標題下一行，不寫進標題。

```markdown
### US-1 · visitor-billing

身為 P-1（訪客），我想在出場前知道要付多少，以便付完就能開走 ← 推論
```

MUST: slug 在一份 `prd.md` 裡唯一。`check_spec.py` 用它對應 `.feature` 檔名。

````markdown
### US-1 · visitor-billing

身為 P-1（訪客），我想在出場前知道要付多少，以便準備好再開到閘門 ← 推論

涵蓋 FR-1。沿規則切：訪客計費是一條獨立成立的約束，自己可驗收。

#### FR

**FR-1**  When 訪客車出場, the system shall 依停留時長計費，前 30 分鐘免費。 ← PRD §3
- **AC-1.1**  停 29 分 → 收 0 元 ← PRD §3
  - Given 一台訪客車已入場並抽了紙票
  - When 它在入場後 29 分鐘於繳費機結帳
  - Then 應收金額是 0 元

#### NFR

**NFR-1**  出場柵欄自刷卡到開啟不超過 2 秒 ← Q-12

#### Q

**Q-7**  跨午夜的停車怎麼算 ← 擋住 FR-1
````

**這個排版對應 Example Mapping 的桌面**：🟨 story、🟦 FR、🟩 AC、🟥 Q。怎麼跑一場
map、四條診斷怎麼讀 → `example-mapping` skill。

**為什麼 FR／NFR／Q 平輩，AC 不平輩。** 那張桌子是一棵樹：綠卡擺在它所屬的藍卡
正下方。FR、NFR、Q 都是 story 層級的東西，並排成三個分組是對的；AC 屬於某一條 FR，
平輩化會讓讀的人靠編號在腦裡把它們接回去。巢狀讓「`AC-1.1` 屬於 `FR-1`」是**結構上
不可能弄錯**的。

**為什麼用粗體項目而不是標題。** AC 底下還要掛 Given/When/Then，用標題會走到 H6。

MUST: `身為` 後面必須是一個 `P-<n>`。指到不存在的 persona＝角色沒被定義，是洞。

**已知弱點：這一條沒有東西在檢查它。**

MUST: **FR 與 NFR 的編號全域唯一。** `FR-1` 在 US-1 底下、`FR-4` 在 US-2 底下都
可以，但不得有兩個 `FR-1`——否則 `AC-1.1` 指向兩個地方，`.feature` 的
`@example-1.1` 失去意義。

**已知弱點：這一條沒有東西在檢查它。** `check_spec.py` 把重複的 `**FR-1**`
併成同一條：第二條的 AC 混進第一條，第二條本身連影子都不留——不報錯，只讓
覆蓋率看起來剛好對上。

MUST: 每條 AC 底下的 Given／When／Then 三行齊全。**Given 寫不出來就是這個例子的
前置狀態還沒被問過——那是一張紅卡，不是一句可以省略的話。**

**已知弱點：這一條沒有東西在檢查它。** 把某條 AC 的三行全刪掉，`check_spec.py`
仍然印 `1/1 例子 · 全部通過`——它只比對 `AC-<n>.<m>` 的編號有沒有對應的 tag，
不看編號底下寫了什麼。這是這一版的承重規則（這條存在就是為了擋 DISCOVERY 編造前置
狀態），而它沒有機械防線。

v2 的 AC 是「給 PM 讀、不含數字」的那一層，v3 拿掉了：一層寫不清楚的東西，兩層
只會讓它在兩個地方各寫一半。PM 對焦讀 story 那一句。

**NFR 有兩個家，判準是跨不跨 story**：只服務某一則 story 的進那則的 `#### NFR`；
跨全部的留在 `## Non-Functional Requirements`。搬家時編號不變。

### `#### Q` 只放指標

紅卡在 story 底下只寫 **編號 ＋ 問題一句話 ＋ 擋住誰**；狀態、面向、答案、決策史
全部住在 `## Open Questions`。

MUST: `#### Q` 只列**狀態為「待答」**的問題。已答的不是紅卡了——它的答案已經長成
某條 FR 或 AC，留在這裡會讓地圖上的紅卡數量永遠不歸零。**這一條 `check_spec.py`
會檢查**——它拿 `#### Q` 的題號去對 `## Open Questions` 表的「狀態」欄。

MUST: 這裡引用的每個 `Q-<n>` 都要存在於 `## Open Questions` 表。**這一條
`check_spec.py` 會檢查。**

**不是每張紅卡都屬於某則 story。** 範圍題在開場產生、技術面向的題目在前沿逐輪
產生，那時候還沒有任何 story——它們只住在 `## Open Questions`，不進任何 `#### Q`。

### 一條 FR 服務多則 story

巢狀強迫一對多，共用的 FR 只能住一個地方。**住主要的那則，其他宣告依賴**：

```markdown
### US-2 · visitor-spot-monitoring

身為 P-2（主委），我想知道訪客格有沒有被外人占走 ← Q-2

**另外依賴**：FR-3（定義在 US-1 底下）
```

**已知弱點：這行宣告沒有東西在檢查它。**

**只有一個 story 分組。** CAPTURE 沿使用者目標粗切、DISCOVERY 沿規則細切，兩者改的
是同一節，不是兩份分組——所以不需要一條規則仲裁哪個算數。

## 來源標記：三選一

`## Background`、`## Goal`、`## Success Metrics` 的每一句、
`## User Stories` 底下的每條 FR／AC 與 story 專屬的 NFR、
`## Non-Functional Requirements` 的每條 NFR、`## Scope — In / Out` 的每條邊界、
`## Assumptions / Constraints` 的每條，
行尾都要標來源，三選一：

| 標記 | 意思 |
| --- | --- |
| `PRD §x` | 同一份 `prd.md` 的 `## 原文` 這樣寫（引用它的章節或段落）——需求方帶來的原始輸入的逐字副本 |
| `Q-<n>` | 來自 `## Open Questions` 某一題的答案，`<n>` 對應那一列的 `Q` 欄 |
| `推論` | 兩者都不是，是從別的地方推導出來的 |

寫法：行尾加 `← <標記>`，例如：

```markdown
**FR-2**  When 月租戶刷卡出場, the system shall 直接開啟柵欄，不計費。 ← PRD §4
```

MUST: 這個標記不是裝飾。少了它，「這一行是真的逼問過 PRD 才寫下來的」跟
「這一行只是把 PRD 換句話抄一遍」在 `prd.md` 上長得一模一樣——完整範例見
[`../examples/minimal-prd.md`](../examples/minimal-prd.md)：整份文件的來源欄
全是 `PRD §x` 時，代表 DISCOVERY 沒有真的發生。

MUST: `## User Stories` 底下的 FR 與 AC **只准 `PRD §x` 或 `Q-<n>`**。一條規則或
例子標 `推論`，意思就是「沒有人說過這句話，是我補的」——那正是 DISCOVERY 不得
做的事。`check_spec.py` 第 14 項會抓。story 的句子、NFR、persona 的「他要什麼」
仍可標 `推論`。

`## Open Questions` 不在這條規則的範圍內——問題本身就是在記錄還沒有答案的
東西，不需要再疊一層來源標記。

`## Personas` **在**範圍內。v1 的角色只有「是誰／怎麼取得／跟誰不同」，
來源就是表格自己的欄位；v2 多了「他要什麼」與「現在什麼讓他痛」，而那兩件事
可以是問出來的，也可以是編出來的——正是這個標記存在的理由。

`## Further Notes` **也在**範圍內。它是最後手段的那一節，放進去的東西別處都
對不到，讀的人唯一能判斷的就是這句話是聽來的還是編的——「當時誰有疑慮」是
`Q-<n>`，「我猜當時的考量是」是 `推論`，兩者在紙上長得一模一樣。

唯一的豁免：**值本身就是在宣告「這裡沒有東西」（不論後面有沒有接一句為什麼
空），那就已經說明了來源狀態**——「沒問過」、「（無資料）」、「（無）」都是
這種值，不再疊 `←` 標記。其餘每一欄都要標。

`## Assumptions / Constraints` 是這條豁免的例外：那一節的「沒有」可能是
問過、確認沒有這類限制的結果（見後面「假設是『沒問過、先當真的』，限制是
『問過、答案是做不到或不准』」那句），跟真的沒人問過不是同一件事——這種
「（無）」背後如果有 `Q-<n>`，仍要標，不算落在前面的豁免裡。

## 編號規則：AC 的編號跟著它的 FR

`FR-<n>` 住在它服務的 `### US-<n>` 底下，但**編號全域唯一**——不是每則 story
各自從 1 起算。`FR-1` 在 US-1 底下、`FR-4` 在 US-2 底下都可以，但不得有兩個
`FR-1`，否則 `AC-1.1` 指向兩個地方。

NFR 的編號同樣全域唯一，而且跨越它的兩個家：story 專屬的 `#### NFR` 與
跨 story 的 `## Non-Functional Requirements`。

`AC-<n>.<m>` 掛在它的 `FR-<n>` 底下，`<n>` 跟著父層的 FR：

````markdown
### US-1 · visitor-billing

身為 P-1（訪客），我想在出場前知道要付多少，以便付完就能開走

#### FR

**FR-1**  When 訪客車出場, the system shall 依停留時長計費，前 30 分鐘免費。
- **AC-1.1**  停 29 分 → 收 0 元
  - Given 一台訪客車已入場並抽了紙票
  - When 它在入場後 29 分鐘於繳費機結帳
  - Then 應收金額是 0 元
- **AC-1.2**  停剛好 30 分 → 收 0 元
  - Given 一台訪客車已入場並抽了紙票
  - When 它在入場後 30 分鐘整於繳費機結帳
  - Then 應收金額是 0 元
- **AC-1.3**  停 31 分 → 收 30 元
  - Given 一台訪客車已入場並抽了紙票
  - When 它在入場後 31 分鐘於繳費機結帳
  - Then 應收金額是 30 元
````

**編號在這裡定版**——在 DISCOVERY 寫下的那一刻。`.feature` 的 `@example-<n>.<m>` tag 回指
`AC-<n>.<m>`，這是這條鏈唯一的接縫。

### 接縫：兩份產物各用母語

| `prd.md`（PRD 詞彙） | `.feature`（Gherkin 詞彙） |
| --- | --- |
| `FR-<n>` | `@rule-<n>` |
| `AC-<n>.<m>` | `@example-<n>.<m>` |

**兩個名字在這裡不是缺陷。** 同一份產物裡有兩個名字才是缺陷；兩份產物各自用母語、
接縫上寫明對應，那是設計。`.feature` 是 Gherkin 的產物，`@example` 是 Gherkin 的字。

MUST NOT: 重排既有的 FR／AC 編號。重排會讓那些引用**靜默**指向別的東西
——不會報錯，只會對錯。刪掉一條規則就留下空號（例如只剩 `FR-1`、`FR-3`，
沒有 `FR-2`），不要把後面的號碼往前遞補：**空號看得出來，重排看不出來。**

**把一條 FR 從一則 story 搬到另一則，編號不變。** 巢狀是給人讀的分組，編號是
給機器追的身分——搬家換分組，不換身分。搬完在版本修訂歷史留一列，因為 FORMULATION
可能已經照著舊分組寫過 `.feature` 了。

每條 FR 底下至少要有一個 AC——完全沒有例子的 FR，通常是規則還停在想像階段，
沒有從具體情境長出來。

## 用 EARS 寫規則

`FR-<n>` 的敘述用 EARS 句式寫，六個 pattern 見
[`docs/sdd.md`](../../../docs/sdd.md) 的 `## EARS`，這裡不重述。

一個 Event-driven 的例子：

```
**FR-2**  When 月租戶刷卡出場, the system shall 直接開啟柵欄，不計費。
```

## AC 就是綠卡

v2 有兩層：`AC` 給 PM（不含數字）、`EX` 給 FORMULATION（含數字）。v3 只有一層。

`AC-<n>.<m>` 同時是驗收條件與具體例子：**一行摘要 ＋ 三行 Given/When/Then**。

````markdown
**FR-1**  When 訪客車出場, the system shall 依停留時長計費，前 30 分鐘免費。 ← PRD §3
- **AC-1.1**  停 29 分 → 收 0 元 ← PRD §3
  - Given 一台訪客車已入場並抽了紙票
  - When 它在入場後 29 分鐘於繳費機結帳
  - Then 應收金額是 0 元
````

**為什麼合併。** 單行例子（`停 29 分 → 收 0 元`）把前置狀態藏起來了：車已經入場
了嗎？計時從進柵欄算還是從抽票算？單行寫法讓這些不用回答，而 `bdd-formulation` 寫
`.feature` 時**必須**回答——於是它自己編一個。那不是 FORMULATION 不守規矩，是 DISCOVERY
沒把話講完。

**為什麼叫 AC 不叫 Example。** 產物是 PRD，讀者帶著 PRD 的詞彙來。Example Mapping
是手法，PRD 是產物，手法的詞彙不覆蓋產物的詞彙。

**一個詞義衝突要知道**：Matt Wynne 把藍卡描述成 "a business rule or acceptance
criterion"——在 Example Mapping 的血統裡 **AC 是藍卡**；在主流 PRD／Jira 用法裡 AC
是那串 Given/When/Then。這裡用 PRD 的。四色卡與 PRD 術語的完整對照 →
`example-mapping` skill。

**已知弱點**：G/W/T 與 `.feature` 的 `Scenario` 有字面重複。`prd.md` 的是**談定的**，
`.feature` 的是**可執行的**（還要套封閉步驟文法與 `Rule:` 結構）。沒有東西檢查兩者
一致——`check_spec.py` 只檢查 tag 對得上編號。

## Non-Functional Requirements 與 Constraints：怎麼分邊

一件事該進 `## User Stories` 底下的某條 FR，還是進
`## Non-Functional Requirements`，判準只有一條：

**舉得出具體例子（誰、什麼狀況、結果是什麼）的，它就是行為，該寫成
`FR-<n>`，不是 NFR。**

「出場柵欄兩秒內開啟」舉不出「誰、什麼狀況」——它對每一條規則都一樣成立，
量得出來，進 `## Non-Functional Requirements`：

```markdown
## Non-Functional Requirements

- **NFR-2**  車輛進出紀錄保存至少一年 ← 推論
```

**只服務一則 story 的 NFR 不寫在這裡**，寫成那則 story 底下的 `#### NFR`。
判準是跨不跨 story，不是重不重要——「柵欄兩秒內開啟」只跟出場那則有關，
「紀錄保存一年」對每一則都成立。

不可協商的外部限制（既有硬體、法規、已發包的規格）進 `## Assumptions /
Constraints`，跟未驗證的假設放同一節，但意思不同：**假設是「沒問過、先當真
的」，限制是「問過、答案是做不到或不准」。**

前沿逐輪問到技術面向時，答得出來的量化屬性進 NFR、答得出來的不可協商限制
進 Constraints、答不出來的一律進 `## Open Questions`——跟業務面的紅卡同一張
表，不勉強塞進 NFR 或 Constraints 湊數。

## Open Questions：表是索引，小節是決策史

一個檔同時服務兩種讀者：`status.py` 讀表算進度，人讀小節查來龍去脈。

````markdown
## Open Questions

表是索引，給腳本讀；小節是決策史，給人讀。

| Q | 問題 | 面向 | 狀態 | 答案 |
| --- | --- | --- | --- | --- |
| Q-1 | 月租費帳務在不在範圍 | — | 已答 | 名單與期限在，錢不在 |
| Q-2 | 消防法規對閘門的要求 | 降級 | 待答 | — |
| Q-3 | 機車費率 | — | n/a | 本期不做機車 |
| Q-4 | 同一戶登記兩台車要不要都給月租證 | 邊界 | n/a | 現行規定一戶限一證，這次不改 |

**`面向` 欄不可省。** `status.py` 用它算追問覆蓋——十六個面向各自掃過沒有，
業務十一個與技術五個各印一欄。省掉它不會報錯，只會讓覆蓋率永遠顯示 0，
而那是靜默地錯。

### Q-2 消防法規對閘門的要求

**狀態**：待答　**輪次**：3　**該問誰**：消防設備師、柵欄廠商

2026-09-09 問管委會 → 「我知道有規定但背不出來，不敢猜」

**擋住**：FR-2（月租戶刷卡出場開柵欄）
````

小節可以多兩個選填欄位：`**誰答的**：<關係人>`，以及 `**歸屬**：<這個答案要進哪一節>`。
`歸屬` 的值域是本文件的章節名，或 `spec.md` 的章節名（`Implementation Decisions`／
`Testing Decisions`／`Risks`／`Tech Preferences & Constraints`）——技術面向的答案靠
這一欄讓 `bdd-spec` 知道該抄進哪一節，不必從問題文字猜。

### `面向` 的值域

`面向` 不是自由文字。合法值只有兩組共十六個，或者 `—`：

- **業務面向（十一個）**：〈追問清單〉與〈非功能面向〉兩張表
  （[`../../bdd-discovery/SKILL.md`](../../bdd-discovery/SKILL.md)）列出的名稱
  ——空與零、邊界、重複、時序、權限、失敗、時間、規模、降級、時限、可觀測
- **技術面向（五個）**：
  [`../../bdd-discovery/references/technical-probes.md`](../../bdd-discovery/references/technical-probes.md)
  的五個章節標題——seam、模組邊界、介面與型別契約、排序契約／決定性、
  既有資產／測試慣例

機械可查核的清單以 `../../bdd-discovery/scripts/status.py` 的 `DIMS` 常數為準——這裡不重複列一份
會漂移的副本，兩邊不一致時以那支腳本為準（跟 `status.py` 自己處理
`TECH_DIMS`／`technical-probes.md` 落差的方式一樣）。

**這一欄是 `status.py` 算追問覆蓋的唯一來源。** 填一個不在上面清單裡的值（例如
「範圍」「法規」）不會報錯——那一格就是不會被任何一個面向認領，覆蓋率因此會
**看起來永遠是 0**，而那正是這條鏈最容易靜默地錯的地方。

`—`：開場的範圍題不屬於任何一個探針面向——它問的是會不會改變範圍、角色
清單，不是十一個業務面向或五個技術面向裡的任何一個。上面 Q-1、Q-3 都是這種
範圍題，`面向` 填 `—`，不計入追問覆蓋。

### 狀態值

只有三種，不得混用同義詞：

| 狀態 | 意思 |
| --- | --- |
| `已答` | 有答案，答案欄已填，通常有對應的 FR／AC |
| `待答` | 還沒有答案，答案欄填 `—` |
| `n/a` | 這個面向不適用，答案欄要寫**為什麼不適用**，不能空著——空著跟「懶得問」在表格上長得一樣 |

### `輪次` 與 `信心`

問題有自己的小節時，可以在狀態列加這兩個欄位：

- **輪次**：這題被問到第幾輪還沒收斂。用來判斷是不是該換個問法，或該停下來
  確認方向錯了——連續好幾輪同一題還在待答，通常代表問錯層次
- **信心**：只在**已答**時才有意義，標這個答案有多篤定——`低`／`中`／`高`。
  「我知道有規定但背不出來，不敢猜」這種答案信心低，即使狀態已經是「已答」，
  也該讓下游知道這條可能要回頭確認

兩者都是選填：一題一輪就答完、答案篤定，不必特地寫。

## Further Notes

放不進其他節、但下一個接手的人會想知道的。沒有就寫「（無）」，並照開頭
「沒有內容的節」那條通則接一句為什麼空，不要刪掉標題。

```markdown
## Further Notes

（無）——沒有放棄過的做法要交代，也沒有跟其他進行中的工作撞在一起
```

典型內容：試過但放棄的做法與放棄的理由、這個 feature 跟另一個進行中的工作
會撞在哪、某個決定當時的氣氛（誰有疑慮、後來為什麼還是這樣定）。

MUST NOT: 把應該進其他節的東西丟進來。這一節是**最後手段**，不是收納箱——
一條規則進了這裡，下游沒有任何東西會去讀它。判準：說得出它該進哪一節嗎？
說得出就進那一節。

## 角色與詞義：兩條界線

**角色留在 `prd.md` 的 `## Personas`，不進 `docs/CONTEXT.md`。** 角色是這個
feature 流程裡誰在做事，換一個 feature 就換一批；詞彙不是。角色若日後真的
需要跨 feature 累積，套 rule of three 再建，不預先做。

**詞義的決策住 `## Open Questions`，不另設 glossary 一節。** DISCOVERY 發現
「訪客」有歧義時，那就是一題——答案進 `## Open Questions` 的表與小節，跟其他問題一視同仁。
`bdd-spec` 之後從已答的問題把定義抬進
`docs/CONTEXT.md`；`prd.md` 沒有詞彙表，但詞義的來源與拍板的時間點都查得到。

## 為什麼規則寫在 story 底下，不另存一份問答

`check_spec.py` 的雙向覆蓋稽核靠比對**兩份獨立的表述**工作：`prd.md`
`## User Stories` 段的 FR／AC 清單，與 `.feature` 的可執行場景。`prd.md`
有例子而對應 `.feature` 沒有 ＝ 漏做；`.feature` 指向 `prd.md` 沒有的
例子 ＝ 憑空發明。

FR／AC 在 DISCOVERY 答案回來的那一刻寫下，行尾指回它來自的 `Q-<n>` 或 `PRD §n`。
問答本身住 `## Open Questions`，形狀跟 FR／AC 不一樣——它是**來源**，不是第三份
表述。舊版另存一份 `clarify-log.md` 再由下一步抄成規則，等於自己造第三份，稽核
就有兩個可能的來源，而它們遲早不一樣。

## 原文

```markdown
## 原文

需求方 2026-10-02 口述，由 bdd-capture 逐字記錄；§ 編號是記錄時加的，原文沒有。

§1 停車場要開始收費，訪客跟月租戶分開算。
§2 前半小時免費，之後每小時 30 元。
§3 月租戶刷卡就直接出去。
```

MUST: 逐字。需求方帶著現成文件來，整份貼進來；口述的，照講的記，不潤飾、
不補主詞、不把「大概半小時」改成「30 分鐘」——那個「大概」正是下一步要問的題。

`§<n>` 是記錄時加的段落編號，給 `← PRD §n` 用。原文自己有章節編號就沿用，
不另編。

MUST NOT: 建檔之後改寫這一節。要補充就在 `## Open Questions` 開一題，答案
長成 FR；原文被改寫，每個 `← PRD §x` 從此指向一句沒人說過的話，而且不會報錯。
