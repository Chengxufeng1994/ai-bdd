## 這份最重要的一件事：`Given` 表達狀態，不執行動作

原始檔案這樣寫「不能重複取消」：

```gherkin
✗ Example: 無法取消已取消的訂單
    Given 用戶 "Alice" 取消訂單 1      ← 這是一個動作，不是狀態
    When  用戶 "Alice" 取消訂單 1
    Then  操作失敗
```

`Given` 那一行**執行了一次取消**。三個問題：

**測試會因為錯的理由變紅。** 如果取消功能本身壞了（第一次就失敗），這個例子也會
紅——但你要驗的是「已取消的訂單不能再取消」，不是「取消能不能成功」。
兩件事的失敗混在一起。

**讀者分不出那是前置還是動作。** `Given` 的位置說「這是既定事實」，內容卻是
一個要執行的操作。

**它繞過了狀態本身。** 這條規則的內容是「哪些**狀態**可以取消」，
把狀態表列出來才是直接的驗法。

改成：

```gherkin
✓ Example: 訂單已取消時再次取消失敗
    When 用戶 "Alice" 取消訂單 <一筆狀態為已取消的訂單>
    Then 操作失敗
```

`Background` 直接播一筆 `已取消` 的訂單。**規則講狀態，例子就用狀態。**

### 那什麼時候才該用兩個 `When`

這一改跟 [`3-deliver-course.md`](3-deliver-course.md) 的「無法重複交付」是同一題，
而那一份原本也寫成兩個 `When`——**同樣該改**，理由一樣：那條規則
（`課程完成後才能交付`）是狀態守衛，不是序列語意。

界線：

| 規則的內容 | 寫法 |
| --- | --- |
| **狀態守衛**（哪些狀態允許這個操作） | `Given <狀態>` ＋ 一個 `When` |
| **序列產生新行為**（累積、副作用疊加） | 多個 `When` |

`交付多個課程累積經驗值` 仍然是多個 `When`，因為 600 點經驗值與等級 5 **只有跑
完兩次才存在**——那不是任何單一狀態表達得出來的。

判準改寫成：**這條規則講的是「什麼狀態下不行」，還是「連續做會怎樣」？**

## 另外三件

### 1. 例子覆蓋整個狀態列舉

規則說「只能取消已建立或處理中」，例子就把狀態表跑完：

```
已建立  ✓ 成功    處理中  ✓ 成功
已付款  ✗ 失敗    已完成  ✗ 失敗    已取消  ✗ 失敗
```

這正是 `references/rule-taxonomy.md` 的分類窮盡稽核想產生的東西——
**規則裡的列舉，例子要逐一走過**。缺哪一個狀態，讀者馬上看得出來。

（值得順帶問：訂單有沒有「已退款」之類的狀態？沒出現在任何一份範例裡。
這是 CLARIFY 該確認的，SPEC 只負責讓缺口可見。）

### 2. `應維持` 與 `應更新為`

```gherkin
And 訂單 X 的狀態應維持 "已付款"      ← 失敗案例：沒有變
And 訂單 X 的狀態應更新為 "已取消"    ← 成功案例：變了
```

兩個動詞把「這裡在驗沒變」與「這裡在驗變了」寫在句子裡，比一律用 `應為` 清楚。
代價是多一支 step definition——**值得**，因為失敗案例的狀態斷言最容易被當成
多餘而刪掉，`應維持` 讓它的用意寫在臉上。

### 3. `null` 是字面值

```gherkin
| 已使用 | 訂單 ID |
| 否     | null    |

And 折扣券 X 的訂單 ID 應為 null
```

這是 [`6-query-product-list.md`](6-query-product-list.md)「空格 vs 填 0 vs 整欄不列」
的第四種，而且是最明確的一種：**API 真的回 `null` 時就寫 `null`**。
空格代表「不適用」，`null` 代表「有這個欄位、值是空」——兩者不同。

## 兩處次要修改

**訂單的 `ID` 與 `編號` 合併。** 原始檔案有 `訂單 ID = 1` 與
`訂單編號 = 20231215143022AB12` 兩個識別碼，前者內部、後者對外。改用 UUID 之後
兩者沒有區別了——保留兩個只會讓每個步驟都要決定用哪一個。

**「取消別人的訂單」的錯誤訊息改成 `訂單不存在`。** 原始是 `權限不足`，
理由同 [`8-query-order.md`](8-query-order.md)：回不同訊息等於確認那筆訂單存在。
