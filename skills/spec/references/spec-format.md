# `spec.md` 的骨架

照抄即可。`spec` 寫它時讀它；`discovery` 續跑時只讀它 `## Open Questions` 的待答題；`example-mapping` 讀它攤地圖、
`formulation` 翻 `.feature`、`plan` 做技術設計與切票時讀它寫出來的東西。`check_spec.py` 從它查
`← Q-<n>` 與 `← PRD §n`；`status.py` 的進度數自旁邊的 `interview-log.md`，不讀這裡。

它只寫**要做成什麼**，不寫用什麼做：Tech Stack、seam、模組、契約、測試層級由 `plan` 寫在 `plan.md`。

一個 feature 一份，路徑 `specs/ongoing/<date>-<feature>/spec.md`。一份 `spec.md` 裝這個
feature 的全部 story、全部問答與需求方的原話——起點是 `discovery` 在訪談紀錄裡粗切的 story，
`spec` 寫規則時可以用 `story-splitting` 沿規則重切（`已對焦` 之前）。

**一個寫入者，旁邊一份證據。** `discovery` 只寫 `interview-log.md`（格式
`../../discovery/references/interview-log-format.md`）：原文、每場訪談、逐題的問答原話，只追加。`spec` 是這份檔
**唯一的寫入者**：照抄紀錄的 `## 原文`、把紀錄的每一題整理成 `## Open Questions`（題號不變），再照已答的題寫規則，
不填紀錄裡沒有的答案。狀態 `待對焦`（有洞時 `澄清中`）；需求方在 `example-mapping` 的就緒問句點頭，
狀態翻成 `已對焦`，`formulation` 與 `plan` 才讀它。

**同一個答案兩處，是刻意的例外。** 紀錄是逐字的原始證據，跟 `## 原文` 一樣沒有人改；這份的 `## Open Questions`
是整理過、給規則引用的版本，`spec.md` 因此自成一體。兩處對不上時以紀錄的原話為準，`spec` 修補時照紀錄改——
一份是證據，一份是用證據寫成的規格，不是同一個事實存兩份。

2026-11-18 之前問答住在旁邊的 `discovery.md`；11-18 當天有一版是 `discovery` 直接寫進 `spec.md`、沒有紀錄。
兩種佈局 `status.py` 會擋下來並說怎麼補出紀錄（`check_spec.py` 只讀 `spec.md`，只擋前者）。

沒有內容的節**保留標題並寫為什麼空**，不要刪掉。空著的節跟被刪掉的節在檔案上
長得一樣，而它們的意思完全不同。

## 章節順序

| 章節 | 裝什麼 | 為什麼需要 |
| --- | --- | --- |
| `## Document Overview` | 狀態、最後更新、結束方式、版本修訂歷史、核心關係人 | 下游靠狀態判斷能不能開工 |
| `## Context / Problem` | 要解決的問題、現況的痛點 | 後面所有取捨都要回頭對照這裡 |
| `## Personas` | 受影響的人，`### P-<n>` 五欄 | story 的「身為」指向這裡；沒有目標的 persona 產出沒有理由的 story |
| `## Goals / Non-Goals` | `### Goals` 做成之後的樣子與要交付的能力；`### Non-Goals` 這次不做的（延後或不做、為什麼）與接受的風險 | 擋住範圍蔓延——agent 最容易在這裡自己發揮 |
| `## User Stories` | `### US-<n> · <slug>`，下一行優先級；底下 `#### FR`（AC 巢狀在它的 FR 底下）／`#### NFR`／`#### Q` | 優先級決定 plan 的切片順序；編號讓 plan、tasks 與 `.feature` 回頭引用 |
| `## Non-Functional Requirements` | 跨 story 的品質屬性，要量化 | 「要很快」不可驗證 |
| `## Domain Concepts` | `### 詞彙`（名詞與定義）；不含欄位型別 | 先對齊語言再建模；做完時 `archive` 併進 `docs/CONTEXT.md` |
| `## Edge Cases` | 失敗、併發、空值、重複、權限邊界——每一條指向涵蓋它的 AC | 規格最常漏的就是這塊 |
| `## Assumptions / Constraints` | 沒驗證過的假設，以及做不到／不准這樣做的外部限制 | 假設與限制長得像，意思相反 |
| `## Open Questions` | 問答表 ＋ 每題的小節：從紀錄整理的、寫規格時發現的洞，全部是 `Q-<n>`，題號跟紀錄同一個序列 | 每條 `← Q-<n>` 指的就是這裡；不確定的地方明確掛著，不被默默猜掉 |
| `## Success Metrics` | 上線後怎麼判斷成功 | AC 管對不對，Metrics 管值不值 |
| `## Further Notes` | 放不進其他節、但下一個接手的人會想知道的 | 最後手段 |
| `## 原文` | 需求方的話，從紀錄逐字照抄，`§<n>` 編號 | 每個 `← PRD §n` 指的就是這裡；附錄，所以放最後 |

寫入者：

| 誰 | 寫哪裡 |
| --- | --- |
| `spec` | 照抄紀錄：`## 原文`、`## Open Questions` 的列與小節、`### 核心關係人`、結束方式、修訂歷史「需求方確認建檔」那一列、`## User Stories` 的粗切；其餘各節、FR／AC、狀態 `待對焦`；寫的時候發現洞就在 `## Open Questions` 開一題 `待答`、狀態改回 `澄清中` |
| `feature-mapping`、`example-mapping`、`spec-by-example` | `## Open Questions` 開 `待答` 題（診斷出的缺口） |
| `example-mapping` | 狀態 `已對焦` |

`discovery` 不在這張表上：它只寫 `interview-log.md`，在這裡只讀待答題。

順序固定，不因為某節內容少而調換或省略標題。需求方判就緒讀的就是整份。技術決定、風險、要不要並行、
接合點都不在這份文件裡，在 `plan.md`，格式見 `../../plan/references/plan-format.md`。

## Document Overview 的三個部分

```markdown
## Document Overview

**狀態**：待對焦　**最後更新**：2026-09-10　**結束方式**：收斂

### 版本修訂歷史

| 版本 | 日期 | 改了什麼 | 為什麼 | 誰 |
| --- | --- | --- | --- | --- |
| 0.3 | 2026-09-10 | FR-1 到期日從「借出後第 14 個開館日」改成「借出當天加 14 天、遇休館日順延」 | Q-15：碰上連假時 14 個開館日會拖到快三週，熱門的書輪不到下一位 | 館長 |

### 核心關係人

| 關係人 | 負責什麼 | 決策權 |
| --- | --- | --- |
| 館長 | 需求方，日常館務與採購 | 預算內、不動讀者權益的事可自行決定 |
| 館務會議 | 全體館員 | 動到借閱規則或預算外支出；每月開一次 |
| 總館流通組 | 全縣借閱規章 | 只答規章，不做決定 |
| 讀者證系統廠商 | 已上線的讀者證系統 | 只答技術現況，不做決定 |
```

**狀態只有四個值**，判準是「下游能不能開工」：

| 狀態 | 意思 | 誰寫 |
| --- | --- | --- |
| `澄清中` | 還有該問的沒問完 | `spec` 寫規格時開了補問題 |
| `待對焦` | 前沿空了（或喊停），規則寫好了，等需求方過目 | `spec`，寫完或修補完時 |
| `已對焦` | 需求方同意 | `example-mapping`，依使用者的答覆 |
| `已凍結` | PLAN 已經消費過它，之後任何改動都要開新版本 | 尚無寫入者 |

這四個值講的是這份文件自己走到哪。下游的閘門：`formulation` 與 `plan`
只讀 `已對焦` 的 `spec.md`。

**`結束方式`** 照抄紀錄 `## Remaining Open Items` 的那一格——`discovery` 寫在那裡，講它這一次怎麼停的，四選一：
`收斂`／`喊停`／`阻塞`／`零進展`，還沒停過寫 `—`。`spec` 只收 `收斂` 與 `喊停`。

**已知弱點：沒有東西在強制這一欄。** `check_spec.py` 從不讀狀態欄，一份還停在
`澄清中` 的 `spec.md` 照樣能通過全部檢查。這一欄是給人看的宣告，不是機械閘門。

MUST NOT: 狀態欄寫題數。「9 題已答／10 題待答」是 `../../discovery/scripts/status.py` **算出來的**，
寫進文件等於同一個事實兩份，而它們遲早不一樣。

**版本修訂歷史的觸發條件**：文件到 `已對焦` 之後，任何動到 FR／AC 的改動都要
留一列——FORMULATION 可能已經照著寫了 `.feature`。`已對焦` 之前的來回不記，那是澄清過程
本身，決策史在 `## Open Questions` 的小節與紀錄裡。唯一的例外是 0.1 那一列「需求方確認建檔」：
`spec` 從紀錄建檔那場 Session 的 `**需求方確認建檔**` 抄來，是需求方點頭的紀錄。

**「為什麼」那欄不可省。** 只記改了什麼，半年後有人會把它改回去。

**核心關係人由 `discovery` 登記在紀錄的 Session。** `決策權` 這一格只有問的人寫得
出來——`spec` 原樣抄過來、不增列也不改寫，`plan` 原樣抄進 `plan.md`。

**「決策權」不是裝飾。** 同一個人給的答案，有些是定案、有些只是提案（要開會
表決），下游要分得出來，否則會拿沒表決過的東西去寫規格。

MUST: 文件裡任何一個「該問誰」都必須指向這張表裡的某個關係人，不限
`## Open Questions`。指到表外的人＝那個人沒被登記為關係人，是文件的洞不是筆誤。

**已知弱點：這條沒有東西在檢查它。** `status.py` 只讀狀態欄與面向欄，從不讀
「該問誰」。一題點名了不在表裡的人，文件看起來完全正常。而**關係人若在事後補登，這條 MUST
會輕鬆通過卻毫無意義**——這正是關係人表必須在問的當下登記的理由：開一題就得知道
問誰，那一刻把他登記進表，`該問誰` 才指得到。

MUST NOT: 在這一節列「誰卡著哪幾題」。理由不是「那是算出來的」——沒有任何腳本
在算它；理由是**每一題自己在它的小節裡宣告掛在誰身上**，在這裡再列一份就是同一
個事實兩份，而它們遲早不一樣。

## Context / Problem

要解決的問題、受影響的人現在怎麼做、哪裡在痛。後面每一個取捨——要不要做某條規則、某個邊界算不算——
都要回頭對照這一節。受影響的人本身寫在下一節 `## Personas`。

```markdown
## Context / Problem

讀者借書全靠櫃台人工登記，逾期沒有人追，熱門的書一借就是一學期。 ← PRD §2
館員每週花半天翻登記本找逾期的人。 ← Q-1
```

## Goals / Non-Goals

### Goals

做成之後的樣子，以及這次要交付的能力，一行一項，行尾標來源。

### Non-Goals

這次不做的，一行一項，寫明是**延後**還是**不做**、為什麼：

```markdown
### Non-Goals

- 電子書借閱 —— 不做：館方沒有授權 ← Q-4
- 預約排隊 —— 延後：要先有通知管道，下一版再做 ← Q-9

接受的風險：
- 熱門的書被同一人一借再借，其他讀者排不到 ← Q-9
```

**延後與不做分開寫**：延後的是下一版要撿回來的，不做的是這個系統永遠不會有的。混在一起，下一版就找不到
該撿回來的那幾項。

推不出來、需要回頭問的缺口不在這裡列——在 `## Open Questions` 開一題 `待答`（見〈寫規格時發現的洞〉）。

## Personas：受影響的人，在三欄上加兩欄

一節開頭先寫一行，說明**這個 feature 是為誰做的**——不是「誰在流程裡出現」：

```markdown
**這個 feature 為誰做**：P-1（讀者）。P-2 出現在流程裡但不是這次的受益者 ← 推論
```

兩件事分開寫的理由：**出現在流程裡的角色，不一定是這次要讓誰過得更好。**
館員會在櫃台刷書，所以他在流程裡；但這個 feature 要解的是讀者不知道哪天該還的問題。
不分開的話，story 會開始為「流程裡出現過的每一個人」各切一則，而其中幾則
沒有人在等它。

```markdown
### P-1  讀者

**是誰**：持有效讀者證、沒有被停權的人 ← Q-8
**怎麼取得這個身分**：在櫃台出示讀者證 ← Q-5（待答，取決於驗證方式）
**跟誰容易混**：跟「本鄉居民」不是同一件事——規章說讀者證發給設籍居民，
但實務上沒有東西在分辨 ← Q-7
**他要什麼**：借書時就知道哪天要還、來不及還時能延 ← 推論
**現在什麼讓他痛**：（無資料）
```

前三欄沿用 v1 的 Actors 一節。新增的是**「他要什麼」**與**「現在什麼讓他痛」**——
FR 掛在 story、story 掛在 persona，**沒有目標的 persona 會產出沒有理由的 story**。

**「無資料」是合法的值，而且比編一個好。** 需求方常常是在轉述別人的痛（館長轉述
館員、館員轉述讀者）。標「無資料」讓那件事在文件上看得見；填「讀者希望流程
順暢」則讓它消失。

## User Stories：三個分組，AC 巢狀在它的 FR 底下

### US-<n> · <slug>

`<slug>` 是這則 story 的交付識別名，**也是它的 `.feature` 檔名**。用 kebab-case，
不含空白。story 的句子寫在標題下一行，不寫進標題。

```markdown
### US-1 · due-date

身為 P-1（讀者），我想借書時就知道哪天要還，以便不會不小心逾期 ← 推論
```

MUST: slug 在一份 `spec.md` 裡唯一。`check_spec.py` 用它對應 `.feature` 檔名。

標題的下一行寫**優先級**，P1／P2／P3，再接一句為什麼：

```markdown
### US-1 · due-date

**優先級**：P1 —— 沒有它，續借與逾期都沒有日期可算 ← Q-19
身為 P-1（讀者），我想借書時就知道哪天要還，以便不會不小心逾期 ← 推論
```

優先級不寫進標題：`check_spec.py` 照 `### US-<n> · <slug>` 精確比對標題，多一個字就認不出這則 story。
它決定 `plan` 的切片順序，所以是需求方的決定：來源跟 FR 一樣只准 `← Q-<n>` 或 `← PRD §n`，問答裡沒有就寫
「（沒問過）」並在 `## Open Questions` 開一題 `待答`，不要自己排。P1 是只做這一則也能交付價值的那幾則。

````markdown
### US-1 · due-date

身為 P-1（讀者），我想借書時就知道哪天要還，以便排好時間回來還 ← 推論

涵蓋 FR-1。沿規則切：到期日怎麼算是一條獨立成立的約束，自己可驗收。

#### FR

**FR-1**  When 館員借出一本書, the system shall 把到期日定為借出當天加 14 天，遇休館日順延到下一個開館日。 ← PRD §3、Q-6
- **AC-1.1**  週四借出 → 到期日是兩週後的週四 ← PRD §3
  - Given 一位讀者持有效讀者證，2026-10-08 不是休館日
  - When 館員在 2026-09-24 借給他一本書
  - Then 到期日是 2026-10-08

#### NFR

**NFR-1**  櫃台刷書到印出借書單不超過 2 秒 ← Q-12

#### Q

**Q-11**  館方臨時公告的休館日算不算休館日 ← 擋住 FR-1
````

**這個排版對應 Example Mapping 的桌面**：🟨 story、🟦 FR、🟩 AC、🟥 Q。怎麼跑一場
map、四條診斷怎麼讀 → `example-mapping` skill。

**為什麼 FR／NFR／Q 平輩，AC 不平輩。** 那張桌子是一棵樹：綠卡擺在它所屬的藍卡
正下方。FR、NFR、Q 都是 story 層級的東西，並排成三個分組是對的；AC 屬於某一條 FR，
平輩化會讓讀的人靠編號在腦裡把它們接回去。巢狀讓「`AC-1.1` 屬於 `FR-1`」是**結構上
不可能弄錯**的。

**為什麼用粗體項目而不是標題。** AC 底下還要掛 Given/When/Then，用標題會走到 H6。

MUST: `身為` 後面必須是一個 `P-<n>`。指到不存在的 persona＝角色沒被定義，是洞。

**已知弱點：這一條沒有東西在檢查它。**

MUST: **FR 與 NFR 的編號全域唯一。** `FR-1` 在 US-1 底下、`FR-4` 在 US-2 底下都
可以，但不得有兩個 `FR-1`——否則 `AC-1.1` 指向兩個地方，`.feature` 的
`@example-1.1` 失去意義。

**已知弱點：這一條沒有東西在檢查它。** `check_spec.py` 把重複的 `**FR-1**`
併成同一條：第二條的 AC 混進第一條，第二條本身連影子都不留——不報錯，只讓
覆蓋率看起來剛好對上。

MUST: 每條 AC 底下的 Given／When／Then 三行齊全。**Given 寫不出來就是這個例子的
前置狀態還沒被問過——那是一張紅卡，不是一句可以省略的話。**

**已知弱點：這一條沒有東西在檢查它。** 把某條 AC 的三行全刪掉，`check_spec.py`
仍然印 `1/1 例子 · 全部通過`——它只比對 `AC-<n>.<m>` 的編號有沒有對應的 tag，
不看編號底下寫了什麼。這是這一版的承重規則（這條存在就是為了擋 DISCOVERY 編造前置
狀態），而它沒有機械防線。

v2 的 AC 是「給 PM 讀、不含數字」的那一層，v3 拿掉了：一層寫不清楚的東西，兩層
只會讓它在兩個地方各寫一半。PM 對焦讀 story 那一句。

**NFR 有兩個家，判準是跨不跨 story**：只服務某一則 story 的進那則的 `#### NFR`；
跨全部的留在 `## Non-Functional Requirements`。搬家時編號不變。

### `#### Q` 只放指標

紅卡在 story 底下只寫 **編號 ＋ 問題一句話 ＋ 擋住誰**；狀態、面向、答案、決策史
全部住在 `## Open Questions`。

MUST: `#### Q` 只列**狀態為「待答」**的問題。已答的不是紅卡了——它的答案已經長成
某條 FR 或 AC，留在這裡會讓地圖上的紅卡數量永遠不歸零。**這一條 `check_spec.py`
會檢查**——它拿 `#### Q` 的題號去對 `## Open Questions` 表的「狀態」欄。

MUST: 這裡引用的每個 `Q-<n>` 都要存在於同一份檔的 `## Open Questions` 表。**這一條
`check_spec.py` 會檢查。**

**不是每張紅卡都屬於某則 story。** 範圍題在開場產生、技術面向的題目在前沿逐題
產生，那時候還沒有任何 story——它們只住在 `## Open Questions`，不進任何 `#### Q`。

### 一條 FR 服務多則 story

巢狀強迫一對多，共用的 FR 只能住一個地方。**住主要的那則，其他宣告依賴**：

```markdown
### US-2 · overdue-list

身為 P-2（館員），我想每天開館時看到哪些書逾期了 ← Q-2

**另外依賴**：FR-1（定義在 US-1 底下）
```

**已知弱點：這行宣告沒有東西在檢查它。**

**只有一個 story 分組。** `discovery` 開場沿使用者目標粗切、`spec` 沿規則細切，兩者改的
是同一節，不是兩份分組——所以不需要一條規則仲裁哪個算數。

## 來源標記：三選一

`## Context / Problem`、`## Goals / Non-Goals`、`## Success Metrics` 的每一句、
`## User Stories` 底下的每條 FR／AC 與 story 專屬的 NFR、
`## Non-Functional Requirements` 的每條 NFR、`## Domain Concepts` 的每一列、
`## Assumptions / Constraints` 的每條，
行尾都要標來源，三選一：

| 標記 | 意思 |
| --- | --- |
| `PRD §x` | 本檔 `## 原文` 這樣寫（引用它的章節或段落）——需求方帶來的原始輸入的逐字副本 |
| `Q-<n>` | 來自本檔 `## Open Questions` 某一題的答案，`<n>` 對應那一列的 `Q` 欄；那一列必須是 `已答` |
| `推論` | 兩者都不是，是從別的地方推導出來的 |

寫法：行尾加 `← <標記>`，例如：

```markdown
**FR-2**  When 讀者在到期日前申請續借, the system shall 把到期日從原到期日再延 14 天。 ← PRD §4
```

一條規則依據兩個以上的來源時（常見的是修補後同時依據舊題與新題），用頓號並列在同一個 `←`
後面：`← Q-18、Q-35`。`check_spec.py` 每一個都查；不要另起第二個 `←`，也不要寫成「另見 Q-35」——
那會被當成沒有來源。

MUST: 這個標記不是裝飾。少了它，「這一行是真的逼問過 PRD 才寫下來的」跟
「這一行只是把 PRD 換句話抄一遍」在 `spec.md` 上長得一模一樣——完整範例見
[`../examples/minimal-spec.md`](../examples/minimal-spec.md)：整份文件的來源欄
全是 `PRD §x` 時，代表 DISCOVERY 沒有真的發生。`check_spec.py` 第 14 項會抓：
沒有來源的規則、指到 `## Open Questions` 沒有的題、指到還不是 `已答` 的題。

MUST: `## User Stories` 底下的 FR 與 AC **只准 `PRD §x` 或 `Q-<n>`**。一條規則或
例子標 `推論`，意思就是「沒有人說過這句話，是我補的」——那正是 `spec` 不得
做的事。`check_spec.py` 第 14 項會抓。story 的句子、NFR、persona 的「他要什麼」
仍可標 `推論`。

`## Personas` **在**範圍內。v1 的角色只有「是誰／怎麼取得／跟誰不同」，
來源就是表格自己的欄位；v2 多了「他要什麼」與「現在什麼讓他痛」，而那兩件事
可以是問出來的，也可以是編出來的——正是這個標記存在的理由。

`## Further Notes` **也在**範圍內。它是最後手段的那一節，放進去的東西別處都
對不到，讀的人唯一能判斷的就是這句話是聽來的還是編的——「當時誰有疑慮」是
`Q-<n>`，「我猜當時的考量是」是 `推論`，兩者在紙上長得一模一樣。

唯一的豁免：**值本身就是在宣告「這裡沒有東西」（不論後面有沒有接一句為什麼
空），那就已經說明了來源狀態**——「沒問過」、「（無資料）」、「（無）」都是
這種值，不再疊 `←` 標記。其餘每一欄都要標。

`## Assumptions / Constraints` 是這條豁免的例外：那一節的「沒有」可能是
問過、確認沒有這類限制的結果（見後面「假設是『沒問過、先當真的』，限制是
『問過、答案是做不到或不准』」那句），跟真的沒人問過不是同一件事——這種
「（無）」背後如果有 `Q-<n>`，仍要標，不算落在前面的豁免裡。

## 編號規則：AC 的編號跟著它的 FR

`FR-<n>` 住在它服務的 `### US-<n>` 底下，但**編號全域唯一**——不是每則 story
各自從 1 起算。`FR-1` 在 US-1 底下、`FR-4` 在 US-2 底下都可以，但不得有兩個
`FR-1`，否則 `AC-1.1` 指向兩個地方。

NFR 的編號同樣全域唯一，而且跨越它的兩個家：story 專屬的 `#### NFR` 與
跨 story 的 `## Non-Functional Requirements`。

`AC-<n>.<m>` 掛在它的 `FR-<n>` 底下，`<n>` 跟著父層的 FR：

````markdown
### US-1 · due-date

身為 P-1（讀者），我想借書時就知道哪天要還，以便不會不小心逾期

#### FR

**FR-1**  When 館員借出一本書, the system shall 把到期日定為借出當天加 14 天，遇休館日順延到下一個開館日。
- **AC-1.1**  週四借出 → 到期日是兩週後的週四
  - Given 一位讀者持有效讀者證，2026-10-08 不是休館日
  - When 館員在 2026-09-24 借給他一本書
  - Then 到期日是 2026-10-08
- **AC-1.2**  第 14 天剛好休館 → 順延一天
  - Given 一位讀者持有效讀者證，2026-10-10 國慶日休館、2026-10-11 開館
  - When 館員在 2026-09-26 借給他一本書
  - Then 到期日是 2026-10-11
- **AC-1.3**  順延後又碰上休館 → 順延到第一個開館日
  - Given 一位讀者持有效讀者證，2026-10-10 國慶日、2026-10-11 盤點、2026-10-12 週一都休館
  - When 館員在 2026-09-26 借給他一本書
  - Then 到期日是 2026-10-13
````

**編號在這裡定版**——在 `spec` 寫下的那一刻，之後不重排。`.feature` 的 `@example-<n>.<m>` tag 回指
`AC-<n>.<m>`，這是這條鏈唯一的接縫。

### 接縫：兩份產物各用母語

| `spec.md`（PRD 詞彙） | `.feature`（Gherkin 詞彙） |
| --- | --- |
| `FR-<n>` | `@rule-<n>` |
| `AC-<n>.<m>` | `@example-<n>.<m>` |

**兩個名字在這裡不是缺陷。** 同一份產物裡有兩個名字才是缺陷；兩份產物各自用母語、
接縫上寫明對應，那是設計。`.feature` 是 Gherkin 的產物，`@example` 是 Gherkin 的字。

MUST NOT: 重排既有的 FR／AC 編號。重排會讓那些引用**靜默**指向別的東西
——不會報錯，只會對錯。刪掉一條規則就留下空號（例如只剩 `FR-1`、`FR-3`，
沒有 `FR-2`），不要把後面的號碼往前遞補：**空號看得出來，重排看不出來。**

**把一條 FR 從一則 story 搬到另一則，編號不變。** 巢狀是給人讀的分組，編號是
給機器追的身分——搬家換分組，不換身分。搬完在版本修訂歷史留一列，因為 FORMULATION
可能已經照著舊分組寫過 `.feature` 了。

每條 FR 底下至少要有一個 AC——完全沒有例子的 FR，通常是規則還停在想像階段，
沒有從具體情境長出來。

## 用 EARS 寫規則

`FR-<n>` 的敘述用 EARS 句式寫，六個 pattern 見
[`docs/sdd.md`](../../../docs/sdd.md) 的 `## EARS`，這裡不重述。EARS 的 `shall` 就是 MUST；需求方明說
「最好、可以不必」的規則才用 `should`，並在行尾的來源那一題看得到這句話。

一個 Event-driven 的例子：

```
**FR-2**  When 讀者在到期日前申請續借, the system shall 把到期日從原到期日再延 14 天。
```

## AC 就是綠卡

v2 有兩層：`AC` 給 PM（不含數字）、`EX` 給 FORMULATION（含數字）。v3 只有一層。

`AC-<n>.<m>` 同時是驗收條件與具體例子：**一行摘要 ＋ 三行 Given/When/Then**。

````markdown
**FR-1**  When 館員借出一本書, the system shall 把到期日定為借出當天加 14 天，遇休館日順延到下一個開館日。 ← PRD §3、Q-6
- **AC-1.1**  週四借出 → 到期日是兩週後的週四 ← PRD §3
  - Given 一位讀者持有效讀者證，2026-10-08 不是休館日
  - When 館員在 2026-09-24 借給他一本書
  - Then 到期日是 2026-10-08
````

**為什麼合併。** 單行例子（`週四借出 → 到期日是兩週後的週四`）把前置狀態藏起來了：讀者證
有效嗎？兩週後那天有沒有休館？單行寫法讓這些不用回答，而 `formulation` 寫
`.feature` 時**必須**回答——於是它自己編一個。那不是 FORMULATION 不守規矩，是 DISCOVERY
沒把話講完。

**為什麼叫 AC 不叫 Example。** 產物是 PRD，讀者帶著 PRD 的詞彙來。Example Mapping
是手法，PRD 是產物，手法的詞彙不覆蓋產物的詞彙。

**一個詞義衝突要知道**：Matt Wynne 把藍卡描述成 "a business rule or acceptance
criterion"——在 Example Mapping 的血統裡 **AC 是藍卡**；在主流 PRD／Jira 用法裡 AC
是那串 Given/When/Then。這裡用 PRD 的。四色卡與 PRD 術語的完整對照 →
`example-mapping` skill。

**已知弱點**：G/W/T 與 `.feature` 的 `Scenario` 有字面重複。`spec.md` 的是**談定的**，
`.feature` 的是**可執行的**（還要套封閉步驟文法與 `Rule:` 結構）。沒有東西檢查兩者
一致——`check_spec.py` 只檢查 tag 對得上編號。

## Non-Functional Requirements 與 Constraints：怎麼分邊

一件事該進 `## User Stories` 底下的某條 FR，還是進
`## Non-Functional Requirements`，判準只有一條：

**舉得出具體例子（誰、什麼狀況、結果是什麼）的，它就是行為，該寫成
`FR-<n>`，不是 NFR。**

「查詢館藏兩秒內回應」舉不出「誰、什麼狀況」——它對每一條規則都一樣成立，
量得出來，進 `## Non-Functional Requirements`。**每條 NFR 都要有數字**：「要很快」「要穩定」不可驗證，
問答裡只有形容詞沒有數字的，進 `## Open Questions` 問到數字，不要自己填一個：

```markdown
## Non-Functional Requirements

- **NFR-2**  借閱紀錄保存至少一年 ← 推論
```

**只服務一則 story 的 NFR 不寫在這裡**，寫成那則 story 底下的 `#### NFR`。
判準是跨不跨 story，不是重不重要——「刷書兩秒內印出借書單」只跟借書那則有關，
「紀錄保存一年」對每一則都成立。

不可協商的外部限制（既有硬體、法規、已發包的規格）進 `## Assumptions /
Constraints`，跟未驗證的假設放同一節，但意思不同：**假設是「沒問過、先當真
的」，限制是「問過、答案是做不到或不准」。**

`spec` 寫這兩節時：`## Open Questions` 裡答得出來的量化屬性進 NFR、答得出來的不可協商
限制進 Constraints；問答裡沒有答案的進 `## Open Questions`，不勉強塞進 NFR 或
Constraints 湊數。

## Open Questions：表是索引，小節是決策史

這個 feature 問過的**每一題**都在這裡：`discovery` 開場與逐題問的（從紀錄整理過來，題號不變）、`spec` 與診斷 skill
寫規格時發現的洞。一節同時服務兩種讀者：`check_spec.py` 讀表查 `← Q-<n>`，人讀小節查來龍去脈。進度由 `status.py`
從紀錄算，不數這張表。

````markdown
## Open Questions

表是索引，給腳本讀；小節是決策史，給人讀。

| Q | 問題 | 面向 | 狀態 | 答案 |
| --- | --- | --- | --- | --- |
| Q-1 | 逾期罰款在不在範圍 | — | 已答 | 到期日與逾期在，罰款不在 |
| Q-2 | 總館規章對逾期讀者續借的規定 | 權限 | 待答 | — |
| Q-3 | 期刊與視聽資料的借期 | — | n/a | 本期只做圖書 |
| Q-4 | 同一位讀者辦兩張讀者證要不要都能借 | 重複 | n/a | 縣裡規定一人限一證，這次不改 |

### Q-2 總館規章對逾期讀者續借的規定

**狀態**：待答　**輪次**：3　**該問誰**：總館流通組、讀者證系統廠商

2026-09-09 問館長 → 「我知道規章有寫但背不出來，不敢猜」

**擋住**：renewal（讀者到期前上網續借）
````

**`面向` 欄不可省，照紀錄抄。** 下游靠它分題（下面），`status.py` 則從紀錄同一題的 `**面向**` 算追問覆蓋——十六個面向
各自掃過沒有。兩處的值不一樣，就是抄錯了。

小節的欄位：`**狀態**`、`**誰答的**`（已答時必填）或 `**該問誰**`（待答時，指向核心關係人表）、選填的
`**輪次**`／`**信心**`、`**來自**`（這一題從哪裡開的：`補問 —「…」`、`喚醒 —「…」`，見下）、答案原話、例子、被推翻的提案（決策史）。

**答案歸哪一節，由下游依 `面向` 判斷**——技術面向的題歸 `plan`，其餘歸 `spec`。小節裡不寫「這題要寫進哪一節」：
下游一改格式，那一行就跟著過期。

### `面向` 的值域

`面向` 不是自由文字。合法值只有兩組共十六個，或者 `—`：

- **業務面向（十一個）**：`discovery` 〈追問清單〉與〈非功能面向〉兩張表
  （[`../../discovery/SKILL.md`](../../discovery/SKILL.md)）列出的名稱
  ——空與零、邊界、重複、時序、權限、失敗、時間、規模、降級、時限、可觀測
- **技術面向（五個）**：
  [`../../discovery/references/technical-probes.md`](../../discovery/references/technical-probes.md)
  的五個章節標題——seam、模組邊界、介面與型別契約、排序契約／決定性、
  既有資產／測試慣例

機械可查核的清單以 `../../discovery/scripts/status.py` 的 `DIMS` 常數為準——這裡不重複列一份
會漂移的副本，兩邊不一致時以那支腳本為準（跟 `status.py` 自己處理
`TECH_DIMS`／`technical-probes.md` 落差的方式一樣）。

**紀錄的 `**面向**` 是 `status.py` 算追問覆蓋的唯一來源。** 填一個不在上面清單裡的值（例如
「範圍」「法規」）不會報錯——那一格就是不會被任何一個面向認領，覆蓋率因此會
**看起來永遠是 0**，而那正是這條鏈最容易靜默地錯的地方。

`—`：開場的範圍題、意圖陳述、寫規格時發現的洞，都不屬於任何一個探針面向——它們問的是會不會改變範圍、
角色清單或某條規則，不是十一個業務面向或五個技術面向裡的任何一個。上面 Q-1、Q-3 都是這種
範圍題，`面向` 填 `—`，不計入追問覆蓋。

### 狀態值

只有三種，不得混用同義詞：

| 狀態 | 意思 |
| --- | --- |
| `已答` | 有答案，答案欄已填；小節有答案原話與 `**誰答的**` |
| `待答` | 還沒有答案，答案欄填 `—` |
| `n/a` | 這個面向不適用、或被另一題取代（失效），答案欄要寫**為什麼不適用**或取代它的是哪一題，不能空著——空著跟「懶得問」在表格上長得一樣 |

### `輪次` 與 `信心`

問題有自己的小節時，可以在狀態列加這兩個欄位：

- **輪次**：這題被問了幾次還沒答定。用來判斷是不是該換個問法，或該停下來
  確認方向錯了——同一題問了好幾次還在待答，通常代表問錯層次
- **信心**：只在**已答**時才有意義，標這個答案有多篤定——`低`／`中`／`高`。
  「我知道有規定但背不出來，不敢猜」這種答案信心低，即使狀態已經是「已答」，
  也該讓下游知道這條可能要回頭確認

兩者都是選填：一題問一次就答完、答案篤定，不必特地寫。

### 寫規格時發現的洞：開一題，不是寫一句

`spec` 寫規格、或 `feature-mapping`／`example-mapping`／`spec-by-example` 診斷時發現問答推不出某條規則、
兩條 FR 打架、例子缺前置狀態——**開一題 `待答`**，跟 `discovery` 問的題用同一張表、同一個編號序列：

```markdown
| Q-6 | 到期日當天申請續借算不算「到期前」 | — | 待答 | — |

### Q-6 到期日當天申請續借算不算「到期前」

**狀態**：待答　**該問誰**：館長
**來自**：補問 —「FR-2 沒說到期日當天申請續借算不算『到期前』，AC-2.1 的 Given 寫不出來」
**影響**：AC-2.1 的前置狀態定不下來
```

`**影響**` 一行寫清楚**什麼定不下來**；`**來自**` 寫 `補問 —「<發現它的那句話，逐字>」`——`discovery` 續跑時
讀這些題、在紀錄追加同號的題先問，也靠這一行比對同一個洞有沒有開過。

**補問題**就是 `**來自**` 那一行以 `補問` 開頭的題；各 skill 的閘門說「待答的補問題」時只數它們。
`喊停` 帶過來、還 `待答` 的題（`discovery` 阻塞或沒問完的，包括它喊停時還沒問到的補問題）**不算**——那是使用者決定帶著走的。
影響到的那則 story，在 story 句子下面就地標一行，讓讀那則 story 的人不必翻到後面才知道它有洞；
`#### Q` 也放這一題的指標：

```markdown
[NEEDS CLARIFICATION: 到期日當天能不能續借 —— 見 Q-6]
```

這一行不是規則，也不進 `#### FR`；這一題答掉、規則寫成 FR／AC 之後刪掉它（題目本身留在表裡，狀態 `已答`）。

MUST NOT: 在這裡順手決定掉。寫規格的 skill 不訪談，洞只能開成題，並把狀態改回 `澄清中`；`discovery` 續跑時問它、記進紀錄，
`spec` 再跑時從紀錄把答案抄回這張表、寫成 FR／AC。表裡還有 `待答` 而結束方式不是 `喊停` 時，`example-mapping` 不提就緒問句。

**列是單向的。** `已答` 的一列記的是當時問了什麼、答了什麼；改主意靠**新開一題**，新題小節寫「取代 Q-<舊>」，
舊題狀態改 `n/a`、答案欄寫被哪一題取代。`Q-<n>` 全域唯一且不重排。

## 角色與詞義：兩條界線

**角色留在 `spec.md` 的 `## Personas`，不進 `docs/CONTEXT.md`。** 角色是這個
feature 流程裡誰在做事，換一個 feature 就換一批；詞彙不是。角色若日後真的
需要跨 feature 累積，套 rule of three 再建，不預先做。

**詞義的決策住 `## Open Questions`，定下來的詞住 `## Domain Concepts`。** DISCOVERY 發現
「讀者」有歧義時，那就是一題——答案進問答表與小節，跟其他問題一視同仁。`spec` 從已答的題把定義抄進
`### 詞彙`，每一列的來源指回那一題；這個 feature 做完時，`archive` 把它追加進 `docs/CONTEXT.md`。

## Domain Concepts

名詞與它們的定義——先把語言對齊，再談模型。只有 `### 詞彙` 一小段，這個 feature 定下來的詞，做完時 `archive` 追加進 `docs/CONTEXT.md`。聚合與不變條件在 `plan.md` 的 `## Domain Model` 設計（`../../plan/references/design-format.md`）。

**不含欄位型別。** 「書有借出日」是領域知識；「`borrowed_on DATE`」是技術決定，屬於 `plan.md`。

`### 詞彙` 欄位固定，`archive` 才能原樣追加進 `docs/CONTEXT.md`：

```markdown
### 詞彙

| 詞 | 定義 | 來源 | 為什麼要定義 |
| --- | --- | --- | --- |
| 到期日 | 借出當天加 14 天，遇休館日順延到下一個開館日 | Q-6 | 「兩週內還」的兩週不是 14 個開館日 |
```

第四欄不是裝飾——一個不需要解釋為什麼要定義的詞，通常本來就沒有歧義，列進來只是雜訊。
沒有要定義的詞就寫「（無）」，並接一句為什麼空。

## Edge Cases

失敗、併發、空值、重複、權限邊界——規格最常漏的就是這塊。**這一節是索引，不是第二份規則**：每一條
指向涵蓋它的 AC，規則與例子本身仍然只住在 `## User Stories`。

```markdown
## Edge Cases

- 還書日剛好是休館日 → AC-3.2
- 同一本書兩個人同時借 → AC-5.1、AC-5.2
- 讀者證已停用還來借 → （沒有 AC）見 `## Open Questions`
```

**找不到 AC 的邊界就是洞**：寫「（沒有 AC）」、在 `## Open Questions` 開一題 `待答`，不在這裡用一句「系統 MUST…」
把規則寫掉——那條規則會沒有例子、沒有來源，`check_spec.py` 也看不到它。

## 為什麼問答抄進 `spec.md`、紀錄另外留一份

`check_spec.py` 的雙向覆蓋稽核靠比對**兩份獨立的表述**工作：`spec.md`
`## User Stories` 段的 FR／AC 清單，與 `.feature` 的可執行場景。`spec.md`
有例子而對應 `.feature` 沒有 ＝ 漏做；`.feature` 指向 `spec.md` 沒有的
例子 ＝ 憑空發明。

`## Open Questions` 與 `## 原文` 不是第三份表述——它們沒有 FR、沒有 AC，是**來源**：規則的每一行行尾指回
某一題或某一段原文。它們抄進 `spec.md`，`check_spec.py` 只讀一份檔就查得完第 14 項——每一條 FR／AC 都要指得到一題
`已答` 的題。

`interview-log.md` 另外留著，理由是**誰問**（`discovery`）與**誰寫規格**（`spec`）要分開：問的人只記，寫的人只從記下的
抄。11-18 有一版讓 `discovery` 直接寫 `spec.md` 的問答那幾節——一份檔兩個寫入者，問的人還是在寫規格。現在每份檔
只有一個寫入者，紀錄只追加，`spec.md` 對不上時有原始證據可對。
