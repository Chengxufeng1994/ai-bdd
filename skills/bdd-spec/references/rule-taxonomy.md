# Rule 的四個象限 —— 分類與覆蓋

`Rule:` 不只是抄 map 的規則敘述。把每條規則歸到四個象限之一，
**空掉的象限就是一份規格的缺口**——而缺口平常完全看不見，因為沒寫的東西不會報錯。

讀這份的時機：把 map 的規則排進 `.feature` 之前，以及寫完之後做覆蓋盤點。

---

## 四個象限

沿兩條軸切：**操作前／後**，以及**狀態／輸入輸出**。

| | 操作**前** | 操作**後** |
| --- | --- | --- |
| **狀態** | **前置（狀態）**<br>系統要處於什麼狀態才允許這個操作 | **後置（狀態）**<br>操作成功後世界變成什麼樣 |
| **輸入輸出** | **前置（參數）**<br>輸入值要滿足什麼約束 | **後置（回應）**<br>回傳什麼內容 |

命名句型：

```
Rule: 前置（狀態）- <主詞>必須<單一條件>
Rule: 前置（參數）- <主詞>必須<單一條件>
Rule: 後置（狀態）- <主詞>應<單一條件>
Rule: 後置（回應）- <主詞>應<單一條件>
```

動詞跟著象限走：**前置用「必須」**（約束），**後置用「應」**（預期結果）。
一眼就分得出這條規則在講「不許」還是「會變成」。

### 原子化：一條 Rule 只講一件事

「必須已購買**且**已訂閱」是兩條規則，拆開之後每一條的失敗例子才指得出
**是哪一個條件沒滿足**。三個機械判準：

| 敘述裡出現 | 怎麼辦 |
| --- | --- |
| 「且」「和」「並且」 | **拆**成多條 Rule |
| 「或」 | **保留**在同一條——那是一個條件的數種滿足方式 |
| 同時混了前置與後置 | **拆**（`取消訂單後狀態應為已取消` 與 `只能取消已建立的訂單` 是兩條） |

再加一個語意判準：**兩半的錯誤訊息不同，就是兩條規則。**
`商品不存在` 與 `商品已下架` 是兩個獨立的檢查，合成一條的話規則敘述說不出
哪個例子在驗哪一半。

### 必要參數：每個 Feature 至少要有一條

MUST: 每個 Feature 至少有一條 `前置（參數）` 規則驗證必要參數。

這是**最常空著的一格**，而它擋掉的是最基本的錯誤。所有「缺少必要參數」的檢查
可以合併成一條規則，用 `Scenario Outline` 逐一列出：

```gherkin
Rule: 前置（參數）- 必要參數必須提供

  Scenario Outline: 缺少<缺少參數>時操作失敗
    When 用戶 "Alice" 將商品 <商品 ID> 加入購物車，數量 <數量>
    Then 操作失敗
    And 錯誤訊息應為 "必要參數未提供"

    Examples:
      | 缺少參數 | 商品 ID                              | 數量 |
      | 商品 ID  |                                      | 1    |
      | 數量     | 6f708192-a3b4-4c5d-8f60-718293a4b526 |      |
```

空格在這裡代表**沒有提供這個參數**——注意它跟播種表裡的空格意思不同
（那裡是「這一欄對這一列不適用」，見 `examples/6-query-product-list.md`）。
位置決定意思：`When` 的參數表用空格表示缺漏，`Given` 的播種表用空格表示不適用。

有**領域特定約束**的參數（進度 0–100、狀態值必須是既有的）仍然各自獨立成一條，
因為它們的錯誤訊息不同。

### 兩個參數的合法組合，也是一條規則

SHOULD: 一個動作吃兩個以上的參數時，問一次**它們的組合有沒有限制**。

`付款方式 = 信用卡` 配 `服務提供商 = 藍新金流`、`無卡分期` 配 `中租零卡分期`——
各示範一組成立的組合，**推不出 `ATM轉帳` 能不能配 `中租零卡分期`**。
每個參數各自合法不代表組合合法。

這一格屬於 `前置（參數）`，而且不是「兩條參數規則」——它是關於**關係**的一條規則。
空著的時候照樣寫進覆蓋表回報，不要自己補一個組合表。

## 命令與查詢的重心不同

| | 主要象限 | 通常沒有 |
| --- | --- | --- |
| **命令**（更新、提交、交付） | 前置（狀態）、前置（參數）、後置（狀態） | 後置（回應）——命令通常只回成敗 |
| **查詢**（查詢、列出） | 前置（狀態）、後置（回應） | 後置（狀態）——查詢不改變世界 |

所以 `.feature` 頂端的 `@command` / `@query` 不只是標籤：**它決定哪些象限該有東西**。
一個 `@query` 卻長出「後置（狀態）」規則，代表這個查詢有副作用——
那多半是設計問題，不是規格問題。

## 拿來做覆蓋盤點

把 map 的每條規則歸位之後，看哪一格是空的：

```
Feature: 交付課程            @command

  前置（狀態）  ✓ 2 條（權限、課程須已完成）
  前置（參數）  — 空
  後置（狀態）  ✓ 1 條（狀態轉已交付、發經驗值、升級）
  後置（回應）  n/a（命令）
```

`前置（參數）` 是空的——交付課程只吃一個課程 ID，沒有其他輸入，所以**這格空得合理**。

但如果是「更新影片進度」，`前置（參數）` 空掉就是缺口：進度值有沒有範圍？
接不接受小數？那正是 `examples/1-video-progress.md`
`Rule: 進度值必須在 0-100% 之間` 在填的格子。

### 空格子怎麼處理

MUST NOT: 自己補一條規則把格子填滿。規則來自 example map，補一條等於一個人
決定了驗收條件。

MUST: 空格子在 `.feature` 裡留一行註解，說明它是**合理地空**還是**沒問過**。

```gherkin
  # ========== 前置 ==========

  # 前置（狀態）：無。查詢商品不需要任何角色，未上架商品也看得到。

  Rule: 前置（參數）- 狀態篩選值必須是既有的商品狀態
    ...

  # ========== 後置 ==========

  # 後置（狀態）：n/a。查詢不改變任何東西。
```

沒有這行註解，讀的人只看到「這裡沒有權限規則」，**分不出是想過了還是漏了**——
而其他五份範例的查詢都要權限，這一份不要，那是一個決定。

段落分隔讓四個象限在檔案裡看得見，掃一眼就知道哪一格明確地空，
不必開另一份文件對照。完整示範見 `examples/6-query-product-list.md`。

覆蓋表仍然要寫，但它是**給現在的人看的**——會隨對話消失，檔案裡的註解才跟規格
一起活著：

```markdown
## 象限覆蓋

| Feature | 前置（狀態） | 前置（參數） | 後置（狀態） | 後置（回應） |
| --- | --- | --- | --- | --- |
| 交付課程 | 2 | — | 1 | n/a |
| 更新影片進度 | 1 | 2 | 2 | n/a |
| 查詢課程進度 | 1 | — | n/a | 1 |

**空格子的判讀**
- 交付課程／前置（參數）：只吃一個 ID，無參數可約束 → 合理
- 查詢課程進度／前置（參數）：課程 ID 不存在時怎樣？**沒問過** → 建議回 CLARIFY
```

`—`（合理地空）與**沒問過**是兩件完全不同的事，而它們在 `.feature` 裡長得一模一樣。
把區分寫出來，是這張表存在的唯一理由。

## 為什麼分類會改變你寫出來的東西

不分類的時候，規格會偏向**開發者當下想得到的**——通常是快樂路徑加一兩個明顯的
錯誤。四個象限強迫你每個方向都問一次：

- **前置（狀態）** 逼你想「什麼情況下這個操作根本不該被允許」
- **前置（參數）** 逼你想邊界值、格式、範圍——最容易漏的一格
- **後置（狀態）** 逼你想副作用：除了主要的改變，還有什麼被動到（發經驗值、升級、發通知）
- **後置（回應）** 逼你把回傳的形狀寫死，而不是「回傳課程資訊」這種說了等於沒說的話

`bdd-clarify` 的追問清單（空與零／邊界／重複／時序／權限／失敗／時間／規模）
問的是**同一種資料的極端值**；這四個象限問的是**操作的四個面向**。
兩者互補，都不能取代對方。
