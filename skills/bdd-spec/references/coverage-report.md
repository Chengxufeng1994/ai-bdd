# 覆蓋表怎麼寫

讀這份的時機：步驟 6，準備回報的時候。格式照抄即可。

---

MUST: 產出覆蓋表，缺的要列出來，不要只說「完成」。

| 規則 | 例子 | 場景 | 狀態 |
| --- | --- | --- | --- |
| Rule 1 | 1.1–1.3 | 3 | ✓ |
| Rule 2 | 2.1–2.8 | 1 Outline（8 列） | ✓ |
| Rule 6 | 6.1–6.3 | 2 | ✗ 6.3 沒寫——它標「暫定」，等定案 |

刻意不寫的要寫出**為什麼**。map 裡標「暫定」「待確認」的例子不該變成場景——
把還在討論的東西寫成驗收條件，是用規格的權威去掩蓋一個沒解決的問題。

MUST: 缺口除了寫進覆蓋表，也要**在 `.feature` 裡就地留一行註解**。

```gherkin
  Rule: 後置（狀態）- 課程進度達 100% 時狀態應轉為已完成

    # Example 6.3（逾時自動歸零）未寫成場景：map 標「暫定」，24 小時這個
    # 門檻沒有依據。定案後補。
```

覆蓋表講給**現在**的人聽，註解留給**之後**的人看。回報會隨對話消失，檔案會留著——
半年後有人拿 map 和 `.feature` 對一次，看到一個沒有解釋的洞，只有兩條路：
當成漏做去補上（於是把還在討論的東西變成驗收條件），或花半小時考古。

## 象限覆蓋也一起報

四象限的空格子同樣要區分「合理地空」與「沒問過」，格式與判讀見
`references/rule-taxonomy.md` 的「拿來做覆蓋盤點」。

兩張表回報的是同一件事的兩個切面：例子覆蓋看**這則 story 的例子有沒有漏**，
象限覆蓋看**這則 story 有沒有整類規則沒被問過**。前者 CLARIFY 已經替你列好了，
後者只有排完規則才看得出來。
