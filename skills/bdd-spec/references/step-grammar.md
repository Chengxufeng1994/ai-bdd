# 步驟文法 —— 每條規則的理由

SKILL.md 列出規則本身，這裡是每一條的**為什麼**與範例。

讀這份的時機：第一次用這個 skill；或某條規則你想不通為什麼要這樣，
準備破例之前。

> 規則的清單與四種形狀的定義在 SKILL.md 的「步驟文法」。這裡不重複，
> 只補理由——同一條規則寫兩處會漂移。

---

#### 播種與前置狀態的界線

界線是：**這個實體存不存在** vs **它現在是什麼狀態**。

`Background` 放**每個 Example 都成立**的世界：有哪些課程、哪些用戶、誰有什麼
角色。前置狀態放各自的 `Given`，因為那正是這個例子要驗的東西。

把前置狀態搬進 `Background`，Example 就看不出自己依賴什麼；把共用的世界留在
每個 Example，同一張表會抄十遍然後開始分岔。

**播種樣板在 Example 層也能用。** 某個例子需要一個 `Background` 沒有的實體
（例如另一個權限不同的用戶），就用同一個樣板寫在該 Example 的 `Given` 裡
（見 `examples/2-submit-assignment.md`）。形狀相同、位置不同——
同一支 step definition 兩處都能用。

判準：**讀者在讀一個 Example 時，不該為了理解它而回 `Background` 找只跟這個
Example 有關的資料。** 逐行檢查 `Background` 的每一列，只被一兩個例子引用的
就搬進那些例子。

SHOULD: 播種用資料表而不是一句一個實體。`系統中有以下課程：` 一支 step
definition 吃掉所有課程，`有一個叫 X 的課程` 則會隨欄位增加而不斷改簽章。

#### `Then` 一律先講成敗

`操作成功` ／ `操作失敗` 是固定的第一句，錯誤情況再加 `錯誤訊息應為 "…"`。

這兩句是整個測試套件裡被呼叫最多次的步驟——把它們統一，等於用兩支 step
definition 覆蓋每一個場景的第一個斷言。更重要的是它**強迫你想清楚這個例子在
驗成功還是失敗**，而 map 裡的例子常常只寫結果值，沒寫這件事該不該成立。

SHOULD NOT: 把成敗與狀態擠進同一句。

```gherkin
✗ Then 課程 1 交付成功，用戶 "Alice" 收到獎勵經驗值 300，新等級 3
✓ Then 操作成功
  And 用戶 "Alice" 在課程 1 的狀態應為 "已交付"
  And 用戶 "Alice" 的經驗值應為 300，等級應為 3
```

複合句要一支專屬的 step definition，而且**失敗訊息只會告訴你整句不成立**——
是狀態沒變、經驗值錯、還是等級沒升？拆開之後失敗的那一行就是答案。

#### 命令斷言狀態，查詢斷言結果

第四種形狀分兩種，取決於這個動作**改不改變世界**：

| | `Then` 接什麼 | 樣板 |
| --- | --- | --- |
| **命令**（更新、提交、交付） | 動作之後實體長什麼樣 | `<實體> 的 <屬性> 應為 <值>` |
| **查詢**（查詢、列出） | 回傳了什麼 | `<X>的查詢結果應包含：` ＋ 資料表 |

查詢的結果用資料表而不是一串 `And`：回傳的是一個**投影**，拆成六行斷言就看不出
它們屬於同一筆資料，六行還各要一支 step definition。一張表一支。
表只列**這條規則關心的欄位**——同一個查詢被兩條規則各自斷言不同欄位是對的，
`一條規則的例子只該因為那條規則被破壞而變紅`。

MUST: 清單查詢要有一個**空集合**的例子。

沒有資料時回 404、拋例外、還是回一個空清單，是三種不同的實作，而空集合的案例
常常被漏掉，因為它「沒東西可斷言」。`Then 操作成功` ＋ `結果應為空` 兩句一起，
才把「查得到，只是沒有東西」與「查不到」分開。範例見
`examples/11-query-user-roles.md`。

這是 `bdd-clarify` 追問清單「空與零」那一格在 SPEC 這一側的樣子。

MUST: 清單查詢用 `應恰好為`／`應依序恰好為`，不要用 `應包含`。

`應包含` 只檢查該有的在不在，**證明不了沒有多餘的**——一個把別的旅程的課程也
一起回傳的實作會通過。這跟命令「失敗時也要斷言狀態沒變」是同一類錯：
只驗該有的有，不驗不該有的沒有。

順帶：清單有順序時，順序**幾乎總是**規格的一部分，規則敘述要先講
（`依章節順序排列`），斷言才有依據。不在乎順序就用 `應恰好為` 並明說不保證——
沒講，下游會自己猜一個，然後某次改了索引就變了。

**巢狀結構分兩層斷言。** 清單裡每一筆又帶一個集合時，平表塞不下——先斷言清單，
再對**形狀不同的那幾筆**各下一句往下鑽。全鑽一遍只是把 `Background` 抄第二次。

**表格空格 = 這一欄對這一列不適用**，與「整欄不列」（回應沒這欄位）、
「填 0」（有欄位、值是零）是三件事。挑錯就是在發明業務上不存在的值。

範例：單筆 `4-query-progress`，清單 `5-query-course-list`，巢狀 `6-query-product-list`。

**斷言完整的樣子，不斷言差異。** 寫「進度 80%、狀態進行中」而不是「進度增加
10%」——差異式斷言在多個規則交互時會互相掩蓋。

MUST: 預期值是**算出來**的時候，計算規則要寫進 `Rule:` 的敘述，不能只藏在數字裡。

判準：**讀規則敘述，能不能自己算出同一個數字？** 不能就代表規則漏講了什麼。
`9800 × 0.9 − 1000 = 7820` 與 `(9800 − 1000) × 0.9 = 7920` 差在套用順序——
數字把順序釘死了，但沒有人讀得出來。範例見 `examples/7-create-order.md`。

MUST: 斷言表的每一格都是**字面值**。`18位數字`、`建立時間+3天` 是規格描述不是
資料，混進表格會逼 step definition 替每一欄各寫一套解析。這種東西各自寫成一句
（`訂單編號應為 18 位數字`），意圖清楚而且能重用。

#### 副作用改到集合時，斷言集合的完整內容

MUST: 動作往一個集合裡加東西時，斷言**集合該有的全部內容**，不是只斷言新加的那項。

續訂商品授予「旅程訂閱狀態」角色，如果只斷言 `應擁有旅程訂閱狀態`，
一個**授予新角色時把舊角色覆蓋掉**的實作會通過——使用者續訂之後失去購買權限。
斷言寫成 `角色應恰好為：[旅程購買, 旅程訂閱狀態]` 才擋得住。

這是「斷言完整的結果狀態」用在集合上。範例見 `examples/9-pay-order.md`。

#### 失敗案例：命令要斷言沒變，查詢不必

```gherkin
Then 操作失敗
And 用戶 "Alice" 在課程 1 的進度應為 70%，狀態應為 "進行中"   ← 命令：仍要斷言
```

命令的失敗案例要把狀態寫出來。只斷言「失敗」證明不了**沒有別的東西被改掉**——
一個回傳錯誤但已經寫進資料庫的實作，會通過只檢查錯誤訊息的測試。

查詢失敗則到 `操作失敗` 為止（必要時加 `錯誤訊息應為 "…"`）。查詢本來就不改變
任何東西，硬要斷言「狀態沒變」是在驗一件不可能發生的事——那種斷言永遠是綠的，
只會讓人以為有在驗。

#### 不要鋪陳預設狀態

SHOULD: `Given` 只寫**與預設不同**的部分。

`examples/4-query-progress.md`的「從未開始的課程」沒有任何 `Given`——
「未開始」就是 `Background` 播完種之後的樣子。多寫一行
`Given 用戶 "Alice" 在課程 2 的狀態為 "未開始"`，驗的就變成**自己的佈置**——
如果系統其實把新用戶初始化成別的狀態，這個例子會因為你先覆蓋掉而測不出來。

判準：這一行 `Given` 拿掉之後，例子還成立嗎？成立就拿掉。

#### 失敗案例要讓失敗原因唯一

MUST: 失敗案例的 `Given` 要把**其他會導致同樣失敗的原因排除掉**。

交付課程需要「有權限」且「課程已完成」。驗權限的例子若不先把課程設成已完成，
它一樣會失敗——但是因為沒完成，不是因為沒權限。**把權限檢查整段刪掉，測試照樣
是綠的。** 這是最難發現的壞測試：它從來不會紅，所以沒有人會去看它。

判準：**把這個例子要驗的規則從實作裡拿掉，測試會不會變紅？** 不會，
就代表它驗的是別的東西。

只有**存在競爭原因**時才需要這種鋪墊。對照
`examples/3-deliver-course.md`（需要）與 `examples/1-video-progress.md`（不需要）。

#### 動作預設只有一個

SHOULD: 一個 Example 一個 `When`。

多出來的 `When` 通常代表兩件事之一：這裡其實是兩個例子，或第一個其實是前提
（改成 `Given`）。失敗時你分不出是哪一個動作壞的，而那正是你最需要知道的事。

SHOULD: `Given` 用**狀態**表達。

「不能重複取消」寫成 `Given 用戶取消訂單 X` ＋ `When 用戶取消訂單 X` 很常見，
但那一行執行了一次取消：取消功能本身壞掉時，這個例子會**因為錯的理由變紅**——
而你要驗的是「已取消的訂單不能再取消」。改成 `Given 訂單 X 的狀態為 "已取消"`。

**例外：不變式複雜到直接設狀態會造出不可能的狀態。**

`Given 訂單 X 的總價為 8800` 看起來沒問題，但如果總價的不變式是
`Σ品項金額 − 折扣`，你設的 8800 可能對應不到任何一組品項與折扣。
**測試於是在驗一個真實系統到不了的狀態**——通過了也證明不了什麼。
這種情況用動作把系統推到那個狀態：

```gherkin
Given 用戶 "Alice" 建立訂單，包含以下項目：…
And 使用折扣券 …
```

| 情況 | 用哪一種 |
| --- | --- |
| 不變式簡單（列舉狀態、`0 ≤ 進度 ≤ 100`） | 狀態 |
| 不變式跨屬性計算，或有狀態流轉順序 | 動作 |
| 但鋪陳路徑需要五個以上動作 | 回頭用狀態，並在檔案裡註明為什麼 |

最後一列是取捨：五個動作的 `Given` 本身就是一個沒人讀得完的程式，
它帶來的耦合超過它防住的不可能狀態。

**例外：序列產生了新行為。** 判準是**這條規則講什麼**：

| 規則的內容 | 寫法 |
| --- | --- |
| **狀態守衛**（哪些狀態允許這個操作） | `Given <狀態>` ＋ 一個 `When` |
| **序列產生新行為**（累積、副作用疊加） | 多個 `When` |

「交付兩門課累積 600 經驗值、升到等級 5」是後者——那個數字**只有跑完兩次才存在**。
「做兩次會失敗」則幾乎總是前者。
對照 `examples/10-cancel-order.md` 與 `examples/3-deliver-course.md`。

#### 選用參數拆成獨立步驟，不要每種組合各造一句

SHOULD: 動作有選用參數時，主要形式用資料表，選用的部分接成獨立的 `And`。

`建立訂單，商品 ID 為 N` / `…，使用折扣券 N` / `…，使用折扣券 N 和 N` ——
一個命令三支 step definition，而且不會收斂：三張券要第四種。改成
`When 建立訂單，包含以下項目：`（表）＋ `And 使用折扣券 N`，
兩支覆蓋所有組合。**用行數換樣板數，在這個尺度上划算。**

接在 `When` 之後的 `And` 仍是同一個動作的一部分，不算「兩個 `When`」——
判準一樣：那是動作的參數，還是前置狀態？

#### 不寫操作方式

|     |                                                  |
| --- | ------------------------------------------------ |
| ✗   | `When 使用者點擊「更新進度」按鈕並輸入 80`       |
| ✓   | `When 用戶 "Alice" 更新課程 1 的影片進度為 80%`  |

按鈕、欄位、API 路徑都不在 example map 裡。它們出現在這裡代表是你加的——
而規格一旦綁死操作方式，換個介面就要重寫，即使規則一個字都沒變。

#### 一條規則不要為了分開斷言而切成多個 Example

MUST NOT: 同一個 `Given` ＋ `When`，只因為斷言不同欄位就拆成多個 Example。

四個 Example 驗同一次查詢的四塊欄位，代價是：場景數膨脹但覆蓋沒增加、同樣的
準備跑四遍、一個 bug 讓四條紅，而最關鍵的——**「這些欄位同時存在」這件事沒有
被驗到**。使用者拿到的是一個回應，斷言切開之後，一個要分次呼叫才湊得齊的實作
會全綠。

判準：**這幾個 Example 的 `Given` ＋ `When` 一模一樣嗎？** 一樣就該併成一個。

界線是**規則**：兩條不同的規則各自斷言自己關心的欄位是對的（`一條規則的例子只該
因為那條規則被破壞而變紅`）；同一條規則切成多個例子只為了分開斷言，是錯的。
對照 `examples/8-query-order.md`（錯）與 `examples/5-query-course-list.md`（對）。

SHOULD: 同一份檔案裡的斷言動詞要一致。`訂單資訊應為` 與 `訂單資訊應包含` 並存時，
讀者無從得知差別是刻意的還是隨手寫的。

#### 每個 Example 各自獨立

MUST: Example 之間不共享可變狀態、不依賴執行順序。

godog 預設並行跑（實測場用 `Concurrency: 4`），順序相依會變成**間歇性失敗**——
最貴的一種 bug，因為重跑一次可能就好了。判準：順序完全打亂，全部還會過嗎？

#### 步驟數量

SHOULD: 一個 Example 三到五步（不含 `Background`）。超過就檢查：`Given` 是不是
該提到 `Background`、多個 `Then` 是不是該合併成斷言表、還是這裡其實在測兩個行為。
步驟愈多，失敗時要排除的可能性愈多。

#### 套不進四種形狀時

SHOULD: 先當成設計訊號。套不進去通常代表這個 Example 混了兩件事。

真的需要第五種形狀時就寫，但**在檔案裡留一行註解說明為什麼**。
沒有理由的例外會擴散——下一個人看到它，就有了自己不遵守的理由。

## 指涉與引號的慣例

同一件事在不同檔案裡用不同寫法指涉，就是不同的 step definition。這幾條是為了
讓跨 feature 的重用真的發生。

### 用什麼當 Key

| 對象 | 用什麼 | 為什麼 |
| --- | --- | --- |
| **行為者**（用戶） | 名稱：`用戶 "Alice"` | 例子在講一個人做了什麼，讀者記得住名字，記不住 UUID |
| **其他實體** | ID：`課程 <uuid>` | 名稱會改，ID 不會。改名的規則本身也需要 ID 才驗得了 |

### 引號

字串加雙引號，數字不加：

```gherkin
When 用戶 "Alice" 更新課程 <uuid> 的影片進度為 80%
And 訂單 <uuid> 的狀態應為 "已取消"
```

這不是排版偏好——`"80"` 與 `80` 在 step definition 的 regex 裡是不同的捕捉，
混用會逼出兩支函式。

### 複合 Key 的連接詞

一個事實牽涉兩個實體時，連接詞決定讀起來是哪一種關係，**跨檔案要一致**：

| 連接詞 | 範例 | 複合 Key |
| --- | --- | --- |
| 在 | `用戶 "Alice" 在課程 <uuid> 的進度為 70%` | 用戶 ＋ 課程 |
| 對 | `用戶 "Alice" 對訂單 <uuid> 的評價為 5 星` | 用戶 ＋ 訂單 |

### `When` 的兩種形狀

| 類型 | 格式 |
| --- | --- |
| 命令 | `用戶 "<key>" <動詞＋參數>` |
| 查詢 | `用戶 "<key>" 查詢 <目標＋參數>` |

查詢一律帶「查詢」兩個字，掃一眼就分得出這個 Example 改不改變世界——
也就分得出 `Then` 該接狀態還是接結果。

### 錯誤訊息跨 feature 一致

同一類失敗在不同 feature 用同一條訊息。`權限不足` 在五個 feature 裡都是
`權限不足`，不要有一個寫成 `沒有權限`。

它們是同一支 step definition 的參數，訊息不一致等於憑空多出比對分支；
而且對使用者來說，同一件事在不同畫面講不同的話，本來就是 bug。

### 不要在資料表裡塞 JSON

```gherkin
✗ | 設定                          |
  | {"theme":"dark","lang":"zh"}  |

✓ | 主題 | 語言 |
  | dark | zh   |
```

JSON 字串要 step definition 自己解析，而且表格失去了欄位名——
diff 的時候看不出改了哪一個值。複雜到一張表放不下時，拆成多個 `Given`。
