## 這份示範的兩件事

### 1. 空集合是一個必要的例子

```gherkin
Example: 用戶沒有任何角色時回傳空清單
  When 用戶 "Charlie" 查詢用戶 "Charlie" 的角色清單
  Then 操作成功
  And 角色清單的查詢結果應為空
```

清單查詢的空集合案例常常被漏掉，因為它「沒東西可斷言」。但它擋掉的是一個很常見
的實作錯誤：**沒有資料時回 404 或拋例外，而不是回一個空清單**。

`Then 操作成功` 加上 `應為空` 這兩句話一起，才把「查得到，只是沒有東西」與
「查不到」分開。少了前一句，空清單和失敗長得一樣。

這是 `bdd-clarify` 追問清單「空與零」那一格在 SPEC 這一側的樣子——
CLARIFY 問「第一次使用時？」，SPEC 就要有一個對應的例子。

### 2. 弱動詞會逼出多餘的例子

原始檔案有四個 Example，其中兩個是這樣：

```gherkin
Example: 查詢自己的角色清單        →  角色清單的查詢結果應包含：（三列）
Example: 不應包含已撤銷的角色      →  角色清單不應包含角色 5
```

第二個之所以存在，**是因為第一個用了 `應包含`**。`應包含` 不排除多餘的資料，
所以「已撤銷的不該出現」得另外寫一句負向斷言。

改成 `應依序恰好為`，那三列就同時宣告了「只有這三個」——**負向斷言變成多餘的**，
兩個例子併成一個。

順帶把規則從 `應包含所有有效角色` 改成 `應回傳全部未撤銷的角色`：
讀者看到 `Background` 有五筆角色、斷言只有三列，會問「另外兩筆呢」——
一筆是 Bob 的，一筆是已撤銷的，而規則把後者講明了。

**強動詞讓規格變短。** 這跟 [`5-query-course-list.md`](5-query-course-list.md)
的理由是同一個，只是那裡的代價是漏掉 bug，這裡的代價是多一個例子。

## 移除的兩個 Example

### `Example: 角色清單應包含完整資訊`

```gherkin
Example: 角色清單應包含完整資訊          ← 已移除
  When 用戶 "Alice" 查詢角色清單
  Then 操作成功
  And 角色 1 的資訊應為： …（與上一個例子同樣的欄位）
```

跟 [`6-query-product-list.md`](6-query-product-list.md) 移除的那個**一模一樣的問題**，
而且是第三次出現在這批來源檔案裡：名字描述回應的屬性而不是情境，
內容與前一個例子重疊。

**同一個毛病在三份檔案裡出現，代表它不是手滑，是一種寫法習慣。**
`references/rule-taxonomy.md` 的「後置（回應）」象限本來就在講回傳的形狀——
那一格有規則的時候，就不需要再開一個叫「應包含完整資訊」的例子。

### `Example: 不應包含已撤銷的角色`

見上方第 2 點，改用強動詞後成為多餘。

## `When` 的形狀統一

原始檔案有兩種：

```
用戶 "Alice" 查詢用戶 "Bob" 的角色清單     ← 查別人
用戶 "Alice" 查詢角色清單                  ← 查自己
```

一個動作、兩支 step definition，差別只在「有沒有指定對象」。
統一成 `查詢用戶 "X" 的角色清單`，查自己就寫 `用戶 "Alice" 查詢用戶 "Alice" 的`。

看起來囉嗦，但**它讓「查自己」與「查別人」走同一條程式路徑**——
而那正是權限規則要驗的東西。兩種寫法時，實作可以有兩個入口，
其中一個忘記檢查權限，測試也不會發現。
