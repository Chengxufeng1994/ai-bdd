## 這份要注意的地方

### 「應包含」證明不了「沒有多餘的」

原始檔案用的是 `課程清單的查詢結果應包含：`。**那個動詞有洞**：

`Background` 播了五門課，其中課程「Scrum 入門」「Scrum 入門」屬於旅程「敏捷開發之旅」。
`查詢旅程「物件導向設計之旅」 的課程清單` 應該只回四門——但 `應包含` 只檢查那四筆在不在。
**一個把五門全回傳的實作，會通過這個測試。**

而這正是 `Background` 特地放一個旅程「敏捷開發之旅」 想擋的東西：測試佈置了正確的陷阱，
斷言卻沒踩上去。

改用 `應依序恰好為`，把三件事一次講清楚：

| 動詞           | 檢查什麼                       |
| ---            | ---                            |
| `應包含`       | 這幾筆在裡面                   |
| `應恰好為`     | 這幾筆在裡面，**而且沒有別的** |
| `應依序恰好為` | 上述，**而且順序如表**         |

這跟命令的「失敗時也要斷言狀態沒變」是同一類錯：
**只斷言「該有的有」，不斷言「不該有的沒有」。**

### 清單查詢一定要回答「順序算不算規格」

原始檔案的表是按課程 ID 排的，看起來有順序——但 `應包含` 不檢查順序，
所以讀者無從得知那是規格還是巧合。

清單有順序的時候，順序**幾乎總是**規格的一部分（這裡是章節順序再接課程順序），
而順序錯了使用者一眼就看得出來。所以規則敘述也一起改成
`依章節順序排列`——**斷言查得到的東西，規則要先講**。

真的不在乎順序時就用 `應恰好為`，並在規則裡明講不保證順序。
沒講，下游實作就會自己猜一個，然後某次改了資料庫索引就變了。

### 同一個查詢、兩張不同欄位的斷言表

Rule 2 的表列 `章節名稱 / 獎勵.經驗值`，Rule 3 的表列 `進度 / 狀態`——
同一個查詢結果，兩條規則各自只列**自己關心的欄位**。

這是對的。把所有欄位塞進一張表，Rule 2 的例子會因為進度欄變動而失敗，
但 Rule 2 根本不管進度。**一條規則的例子只該因為那條規則被破壞而變紅。**

### 一個未解決的不一致

課程「設計模式問卷」（問卷）與課程「實作練習」（挑戰題）沒有百分比概念，這裡填 `0`：

```
| …607182 | 設計模式問卷 | 問卷課程 | 0 | 已完成 |   ← ID 略去前段
```

但 [`4-query-progress.md`](4-query-progress.md) 查單筆挑戰題時是**整欄不列**。
同一個概念，兩種表示法。

哪一種對取決於 API 實際回什麼（`null`？`0`？欄位不存在？）——
而這是 CLARIFY 該問而沒問的一題。SPEC 遇到這種不一致**不要自己選一個**，
寫進覆蓋表回報。兩份規格各自都自洽，湊在一起才看得出來，
這正是「跨 feature 的規則只有並排時才看得見」。
