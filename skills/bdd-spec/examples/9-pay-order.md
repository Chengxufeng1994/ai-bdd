## 這份示範的三件事

### 1. 副作用的斷言要涵蓋「原本就有的還在」

```gherkin
Given 用戶 "Bob" 在旅程 X 的角色為：
  | 旅程購買 |                  ← 原本有一個
When 用戶 "Bob" 對續訂訂單付款
Then 用戶 "Bob" 在旅程 X 的角色應恰好為：
  | 旅程購買     |               ← 原本的還在
  | 旅程訂閱狀態 |               ← 新加的
```

如果只斷言「應擁有旅程訂閱狀態」，一個**授予新角色時把舊角色覆蓋掉**的實作會通過。
續訂之後失去購買權限——而這是使用者最不能接受的那種 bug。

這是「斷言完整的結果狀態」用在集合上：**列出集合該有的全部內容，
而不是只列出這次動的那一項。**

### 2. 七個 Example 收斂成兩個

原始檔案的 `後置（回應）` 底下有七個 Example，全部是同一個 `When`（或只差資料）：

| 原始 Example | 問題 |
| --- | --- |
| `成功提交付款請求` | 三個共用同一個 `When`（信用卡），只是各自斷言不同欄位 |
| `使用信用卡付款` | ← 見上，[`8-query-order.md`](8-query-order.md) 的同一個毛病 |
| `付款請求金額應等於訂單總價` | ← 見上 |
| `使用 ATM 轉帳付款` | 三個只差付款方式的值 → 這正是 `Scenario Outline` |
| `使用無卡分期付款` | ← 見上 |
| `使用藍新金流` | 多一個參數，仍然只差資料 → 併進同一張 Examples |
| `使用中租零卡分期` | ← 見上 |

前三個併成一個基準例子（用 `應恰好為` 一次驗完三個欄位），後四個併成一個
`Scenario Outline`。**七個變兩個，覆蓋沒有減少。**

判準沒有新東西，就是既有的兩條疊在一起：
`Given`＋`When` 一樣就是同一個情境（併），只差資料就用 Outline（併）。

### 3. `Background` 收攏世界，Example 只挑用得到的

原始檔案的三個授予角色例子，各自在 `Given` 裡播了商品、方案項目、旅程、訂單、
訂單項目——**每個例子六行以上的鋪陳**，而且結構重複。

改成 `Background` 一次把三種形狀的商品與對應訂單都播好，Example 只指名要用哪一筆。
每個例子從十五行降到五行，讀者看得見的是**差異**，不是重複的鋪陳。

界線仍然是 [`2-submit-assignment.md`](2-submit-assignment.md) 那條：
只有一個例子用得到的東西才留在該例子的 `Given`。這裡三個例子都需要「有方案項目
的商品」，只是需要不同形狀的——那屬於共用的世界。

## 一個沒被規則涵蓋的缺口

原始檔案把 `信用卡`＋`藍新金流`、`無卡分期`＋`中租零卡分期` 各寫成一個例子，
但**沒有任何規則說明哪些組合合法**。

`ATM轉帳` 能不能配 `中租零卡分期`？`無卡分期` 能不能配 `藍新金流`？
從例子推不出來——它們只示範了兩個成立的組合，沒有說其他組合會怎樣。

MUST（寫進 SKILL.md 的規則）：**兩個參數的合法組合本身是一條規則**，
屬於 `前置（參數）`，而不是兩條獨立的參數規則。

這一格在原始檔案是空的。我在上面的 Outline 裡照抄了原有的三組組合，
**沒有自己補一條組合規則**——那是 CLARIFY 該問的，寫進覆蓋表回報。
