## 改了什麼，為什麼

### 1. 五個 Example 併成一個

原始檔案是這樣的：

```gherkin
Example: 成功查詢自己的訂單        →  斷言 編號/狀態/總價
Example: 查詢訂單應包含訂單項目    →  斷言 訂單項目
Example: 查詢訂單應包含時間資訊    →  斷言 建立時間/付款期限
Example: 查詢已建立狀態的訂單      →  斷言 狀態
```

四個 Example、同一個 `When`、同一個前置狀態。它們不是四個情境，
是**一個情境被斷言切成四塊**。

代價：

- **場景數膨脹但覆蓋沒增加。** 四個 Example 驗的是同一次查詢。
- **同樣的準備跑四遍。** 播種、權限、查詢各執行四次。
- **一個 bug 讓四條紅。** 查詢壞掉時你看到四個失敗，得自己判斷是同一件事。
- **證明不了「一次回傳全部」。** 四次查詢各自檢查一部分，
  而使用者拿到的是**一個回應**。一個分次呼叫才湊得齊全部欄位的實作，會全綠。

最後一點是關鍵：斷言切開之後，**「這些欄位同時存在」這件事就沒有被驗到**。

### 2. 但「不同規則各自斷言不同欄位」是對的

這跟 [`5-query-course-list.md`](5-query-course-list.md) 的做法不衝突，界線是
**規則**：

|                                                  | 對／錯                                        |
| ---                                              | ---                                           |
| 兩條**不同的規則**，各自的例子斷言自己關心的欄位 | ✓ 一條規則的例子只該因為那條規則被破壞而變紅 |
| **同一條規則**切成多個例子，只為了分開斷言       | ✗ 那是一個情境，不是多個                     |

判準：**這幾個 Example 的 `Given` ＋ `When` 一模一樣嗎？** 一樣就是同一個情境，
該併。範例五的兩張表分屬 `後置（回應）- 清單內容` 與
`後置（回應）- 帶出進度狀態` 兩條規則，`When` 雖然相同，但它們回答的是不同的問題。

### 3. 斷言動詞在同一份檔案裡統一

原始檔案同時用了三種：

```
訂單資訊應為：        （精確）
訂單應包含以下項目：  （包含）
訂單資訊應包含：      （包含）
```

`訂單資訊應為` 與 `訂單資訊應包含` 同一個主詞、兩種動詞，讀者無從得知差別是
刻意的還是隨手寫的。全部改成 `應恰好為`——理由同
[`5-query-course-list.md`](5-query-course-list.md)：`應包含` 證明不了沒有多餘的。

### 4. 補上 Bob 訂單的項目

`Background` 定義了 Bob 的訂單，卻沒定義它的項目。查詢 Bob 的訂單時如果回應
包含項目，測試什麼都沒說。既然要斷言「完整內容」，兩筆訂單都要有項目可比。

### 5. 「查別人的訂單」的錯誤訊息改了

原始檔案：查別人的訂單回 `權限不足`，查不存在的訂單回 `訂單不存在`。

**這兩種訊息不同，等於告訴查詢者「這筆訂單存在，只是不是你的」。**
UUID 猜不到，所以這裡的洩漏不嚴重——但拿到一批編號（轉寄的通知信、日誌、
截圖）的人，可以逐一分辨哪些仍然有效。**訂單編號用 UUID 是為了讓人猜不到，
不是為了讓錯誤訊息可以偷懶。**

改成兩者都回 `訂單不存在`。**別人的訂單對你而言就是不存在。**

這跟 [`7-create-order.md`](7-create-order.md) 的折扣券是同一個問題的兩面：
那裡是兩種原因共用一個訊息（可能刻意），這裡是兩種原因用了不同訊息（洩漏存在性）。

**錯誤訊息的粒度是安全決定，不是文案問題。** 規則敘述該把它講出來，
而 SPEC 遇到這種情況不自己選——這一份我改了，是因為洩漏存在性的方向風險明確；
但正式流程裡它該是一張回報給 CLARIFY 的問題卡。

### 6. `When` 縮短

`查詢訂單編號為 "X" 的訂單` → `查詢訂單 "X"`。訂單本來就用編號指涉，
「訂單編號為…的訂單」是把型別名稱寫進了句子。短的版本一樣沒有歧義。

## 原始檔案裡做對的一件事

時間欄位用**具體值**寫在 `Background`，斷言也用具體值：

```gherkin
| 建立時間            | 付款期限            |
| 2023-12-15 14:30:22 | 2023-12-18 14:30:22 |
```

對照 [`7-create-order.md`](7-create-order.md) 原始版本把
`建立時間+3天` 當成一格資料塞進斷言表——**那是規格描述，不是值**。

正確的分工：**「付款期限 = 建立時間 + 3 天」這條規則寫在 `Rule:` 敘述裡，
例子用算好的具體時間。** 讀規則能自己算出 12-18，例子就成立。
