# CLARIFY LOOP — 把問題問到收斂

輸入是一疊未解的問題，輸出是「哪些解了、哪些還開著、還缺誰」。

跑幾輪不由題數決定，由**問題是否還在減少**決定。

## 使用時機

- `bdd-clarify` 產出了紅卡，要把它們逐一問掉
- 上一輪澄清之後又冒出新問題，需要再跑一輪
- 手上有一疊模糊的問題，想知道哪些能當場解決、哪些必須去問別人
- 想知道「還差多少才能開工」

## Skill Boundaries

- 要從零開始**找出**問題（切 story、抽規則、配例子）→ 改用 `bdd-clarify`，
  本 skill 接手它的產出
- 要把例子寫成 Gherkin → 改用 `bdd-spec`
- 通用的需求訪談、不涉及紅卡與就緒判定 → 環境中另有 `clarify-loop`，那個以
  「最多五題」為終止條件，適合快速收斂；本 skill 以「紅卡清空」為終止條件，
  適合必須把話講死的場合
- 本 skill **只問問題與記錄答案**，不做決定、不寫規格、不改程式碼

---

## 前置確認（Ask user）

Ask user: 若以下不明確，先問清楚。

1. **要收斂哪一疊問題**：狀態為「待答」的問題檔，兩層都算——`specs/questions/`
   （跨 feature）與 `specs/<feature>/questions/`。單獨使用時，一段模糊的描述
   也可以——本 skill 會先把它拆成問題並各自建檔
2. **這一輪想推進到哪**：全部問完，還是先清掉能當場決定的。**先知道範圍，
   才不會把一輪拖成沒有終點的訪談**

NEVER: 在沒有問題清單、也沒有描述的情況下自己編幾個問題來跑。憑空的問題會得到
憑空的答案，而它們看起來跟真的一模一樣。

## 一輪長什麼樣

### 1. 分類手上的問題

問任何人之前，先把問題分成三堆。這一步決定整個迴圈會不會空轉：

| 類別 | 判準 | 這一輪怎麼處理 |
| --- | --- | --- |
| **可解** | 使用者當場答得出來 | 問 |
| **阻塞** | 要另一個角色才答得出來 | 不問，記下「誰／問什麼」 |
| **失效** | 前面的答案讓它不再成立 | 標記關閉並寫明被哪個答案取代 |

IMPORTANT: 阻塞的題目**不要換句話說再問一次**。使用者答不出「業界怎麼算」不是
因為問法不好，是因為他不知道。重問只會換到一個猜測，而猜測被記成答案之後就沒有
人會回頭質疑它。

### 2. 先讀已填的答案

`questions/` 裝的是這個 feature 問過的**每一題**，狀態列分辨已答與待答。本 skill
的對象是狀態為「待答」的那些，每個檔都記了跳過的原因；先讀那個原因再決定怎麼問：

```bash
grep -L '狀態.*已答' specs/questions/*.md specs/*/questions/*.md   # 還開著的
```

根層那些是 CLARIFY 的 Pass 1 留下的跨 feature 問題。**它們最容易被漏掉**——
逐一處理 feature 時不會走到根層，而它們的答案影響的正是每一則 story。

| 跳過的原因 | 這一輪怎麼處理 |
| --- | --- |
| 之後再問 | 重問，這正是本 skill 的主要對象 |
| 這題不該問 | 先確認它真的不影響任何規則。是 → 刪掉它，不要留著佔位 |

MUST: 一個問題確定就**立刻**做兩件事：答案寫進問題檔、**狀態列由「待答」改為
「已答」**。

MUST NOT: 不要因為狀態改變就搬動或改名問題檔。指向它的引用（含跨 feature 的）
會全部斷掉，而那些引用正是這些檔案存在的理由。

不要累積到一輪結束才一次更新 map。剛答完那一刻你還記得它跟哪條規則有關；
隔了十題再回來併，漏掉的機率高得多。而且中途停下時，map 應該永遠是完整可用的。

沒有任何檔案還是「待答」即代表收斂完成。

### 3. 一次一題，四個選項

```
[3/5] 熱身組要不要計入總容量？

    1. 計入 —— 只要舉起來就算訓練量
    2. 不計入 —— 熱身的目的不是刺激
    3. 使用者自己標記哪幾組是熱身
    4. 低於當日最重組某個比例的自動視為熱身
    5. 不知道／先跳過          ← 選這個就維持「待答」

提案：2。多數訓練 App 這樣處理，因為熱身重量偏低卻會稀釋容量的可比較性。
但這是提案不是答案——你的判斷勝過慣例。
```

**組成是固定的 4＋1**：1–4 互斥且涵蓋光譜，第 5 個永遠是逃生口。

MUST: 最後一個選項永遠是逃生口「不知道／先跳過」，選它就維持狀態「待答」。

沒有逃生口時，人在不確定會挑一個看起來最合理的。**被記成決定的猜測比開著的問題
更糟**——它看起來已解決，之後沒人會回頭質疑。

### 提案要不要給

| 題目性質 | 給不給提案 |
| --- | --- |
| 有領域慣例可循（熱身組、四捨五入、單位） | **給**，並寫出慣例是什麼、為什麼 |
| 純業務價值取捨（要比較週與週還是同一動作的進步） | **不給**——這種題目沒有「常見答案」，給了只是把你的偏好偽裝成建議 |

給提案時姿態要清楚：**這是提案，請打我**。使用者回「都不是」時，那個更正比四個
選項加起來更有資訊量——把它記成答案，並寫明原本四個為什麼都錯。

SHOULD: 一輪 3–5 題。但真正的判準不是數字，是**回答品質**：使用者開始給
「都可以」「你決定」這類答案時就停下，那是疲勞不是共識。

### 4. 每輪結束給進度

```markdown
## 第 2 輪結束

| | 上輪 | 這輪 | 變化 |
|---|---|---|---|
| 已解決 | 1 | 4 | +3 |
| 開啟中 | 5 | 3 | −2 |
| 阻塞（等別人） | 0 | 2 | +2 |
| **新發現** | — | 2 | ← 回答揭露的新問題 |

### 這輪解決的
- Question 3 熱身組不計入 → 成為規則 Rule 4
- Question 5 單位一律存公斤 → 成為共用規則 Shared 1

### 還開著
| | 問題 |
|---|---|
| Question 7 | 單邊動作要不要乘二 | 你 |
| Question 8 | 業界怎麼定義「一次訓練」的時間邊界 | 教練 |

### 下一輪
Question 7 可解，繼續。Question 8、Question 9 阻塞——不會再問你，等你去問到答案再回來。
```

IMPORTANT: **「新發現」要單獨列，不要混進「開啟中」。** 前幾輪紅卡變多是正常的
——回答一題常會揭露兩題，那是迴圈在做對的事。混在一起顯示會讓人以為在倒退而喊停。

真正的警訊是**紅卡總數從頭到尾不下降**，那代表問題的層次不對，見下。

## 什麼時候停

四種結束方式，每一種都要**明講是哪一種**：

| 結束方式 | 條件 | 結論 |
| --- | --- | --- |
| ✅ **收斂** | 沒有開啟中的問題 | 就緒，可以進下一步 |
| ⏸ **停滯** | 剩下的都被標成「之後再問」 | 未就緒，說明卡在哪 |
| 🛑 **零進展** | 一整輪沒解決任何問題 | 停下，說明卡在哪 |
| 🛑 **喊停** | 使用者要求 | 立即停，**仍然寫檔** |

### 零進展的四種成因

一輪下來一題都沒解決時，不要再問一輪——先判斷是哪一種：

1. **問錯層次**：在問實作細節，而真正沒定的是上位目的。往回問一層
2. **問題其實是同一個**：三張紅卡是同一個未決定的不同面向。合併成一個問題再問
3. **使用者真的不知道**：全部轉成阻塞，列出要問誰
4. **story 太大**：問題多到問不完，是因為範圍本身沒收斂

第三種最常見，也最常被誤判成前兩種而繼續磨。**使用者連續兩題選逃生口，就該懷疑
整組問題都超出他的知識範圍**。

第四種最容易被漏掉，因為它偽裝成「還有很多問題要問」。判準來自 Example Mapping
的原始建議：一則大小合適的 story，三方應該在 **25 分鐘左右** map 完；map 不完
表示它太大或太不確定。對應到這裡：**問了兩三輪、紅卡總數卻不下降，就不是問法的
問題，是範圍的問題**。

此時正確的動作是回頭切 story，不是再問一輪。切的方式是沿著規則切——
"Rules make natural fault lines for slicing your story"
（[出處](https://cucumber.io/blog/bdd/example-mapping-introduction/)）。

## 產物

### 單獨使用時

寫入 `specs/<topic-slug>/clarify-log.md`：

```markdown
# Clarify Log: <主題>

**日期**: <YYYY-MM-DD>
**結束方式**: 收斂 / 阻塞 / 零進展 / 喊停 —— <一句話>

## 已解決
| | 問題 | 答案 | 輪次 |
|---|---|---|---|
| Question 1 | <問題> | <答案> | 1 |

## 還開著
| | 問題 | 狀態 |
|---|---|---|
| Question 7 | <問題> | 開啟中 | 你 |
| Question 8 | <問題> | 阻塞 | 教練 |

## 被推翻的提案
<我提過但使用者說「都不是」的，連同正確答案——這是最有價值的一段>
```

「被推翻的提案」那一段值得特別保留：它記錄的是**慣例在這個專案不適用的地方**，
而那正是外人最容易踩錯、文件最少提及的部分。

產物一律寫在 `specs/` 底下，不修改專案既有的任何檔案。

## 完成後

明講結束方式與下一步：

- **收斂** → 可以進 SPEC
- **阻塞** → 列出「誰要回答什麼」，並說明拿到答案後回來跑哪一輪
- **零進展** → 說明判斷是三種成因的哪一種，以及建議怎麼調整

不要在阻塞或零進展的情況下宣告完成。那會讓一份不完整的澄清看起來像完成品，
而它的缺口全藏在「看起來很專業」的表格底下。
