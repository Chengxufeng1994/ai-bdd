## description

模型在每次對話開始時只看得到 `name` 與 `description`，看不到本文——所有
「什麼時候用我」的資訊都必須寫在這裡。`description` 承擔其中絕大部分（`name`
也參與，但資訊量小得多）。

Check if: 一個 skill 明明 description 寫得很準卻不觸發，先確認任務複雜度。
`skill-creator` 指出，模型只會為**它無法輕鬆自行完成**的任務去查 skill；
單步驟的簡單請求即使完全符合描述也可能不觸發。這種情況不是 description 的問題。

| # | 強度 | 規則 |
| --- | --- | --- |
| F4 | `MUST` | 第一句說明用途，一句話講完 |
| F5 | `MUST` | 中文觸發詞用「」包住，逐一列出 |
| F6 | `SHOULD` | 英文觸發詞以 `English:` 起頭，逗號分隔 |
| F7 | `SHOULD` | 用 YAML 的 `>` 折疊多行 |
| F8 | `MUST NOT` | 在 YAML key 上使用全形「：」 |

```yaml
description: >
  自動分析客戶來信並產生專業回覆草稿。
  觸發詞：「幫我回這封信」「回覆郵件」「寫回信」「客戶郵件回覆」
  「Email 回覆」「信件草稿」。
  English: reply email, draft email response, email helper.
```

## 觸發詞：數量的取捨

參考教材依複雜度建議 5–20 個（單一功能 5–8、工作流程 8–12、多步驟 12–20）。
**這組數字在教材裡沒有給出依據**，當作起點參考即可，不要當成標準。

真正該納入考量、而教材沒提的是：`description` 是**每個 session 都付費的常駐
成本**，本文則是觸發時才付（數量級見 `../references/runtime-facts.md` 第 3 項）。
常駐成本隨 skill 數線性成長。

所以取捨的**方向**是：skill 數量越多，越該從「窮舉各種說法」轉向「精準涵蓋」。
我不給具體的 skill 數門檻——那需要實測不同規模下的觸發率與成本才說得準，目前
沒有這個資料。

可以操作的是逐一檢驗每個觸發詞：**去掉它之後，有沒有一種真實說法會漏掉？**
沒有就是冗餘。「做事情」這類通用詞永遠是冗餘，它只會製造誤觸發。

【推論】誤觸發比不觸發更難察覺，因為兩者的失敗訊號不對稱：不觸發時使用者會發現
「怎麼沒用到」而主動反應；誤觸發則是安靜地產出一份用錯方法的結果，沒有缺席訊號。
據此，**刪掉一個過於通用的觸發詞，通常比多加五個精準的更有價值**——但這是推論，
尚未實測。

## 觸發詞：涵蓋面

```
觸發詞 = 動詞 × 名詞 × 同義詞 × 中英文
```

| 維度 | 例 |
| --- | --- |
| 動詞變化 | 建立、產生、生成、製作、寫、做 |
| 名詞同義 | 會議記錄 ＝ 會議紀要 ＝ 開會內容 ＝ 會議摘要 |
| 口語 vs 正式 | 「幫我整理一下今天的會」vs「產生會議紀要」 |
| 英文 | meeting minutes, summarize meeting, meeting notes |

漏掉「口語」那一列是最常見的缺口。使用者實際打字時很少用正式說法。

## 選用欄位

| 欄位 | 效果 | 何時用 |
| --- | --- | --- |
| `disable-model-invocation: true` | 模型不會自動觸發，只能由使用者明確叫用 | 有副作用的操作（部署、送出、刪除） |
| `tools` | 限制該 skill 可用的工具 | 需要收斂權限時，罕用 |

IMPORTANT: `disable-model-invocation: true` 的 skill 不會出現在模型的可用清單裡。
若你的 skill「明明存在卻從來不觸發」，先檢查這個欄位。

## 常見錯誤

```yaml
# ✗ 太短，模型無從判斷何時觸發
description: 回覆 email
```

```yaml
# ✗ 全形冒號，YAML 解析失敗
name：my-skill
```

```yaml
# ✗ 只描述功能，沒有觸發條件
description: 這個 skill 會產生會議紀要。
```

最後一個最隱蔽：它文法正確、YAML 合法、意思清楚，但模型仍然不知道**使用者說什麼
的時候**該用它。描述功能不等於描述觸發條件。
