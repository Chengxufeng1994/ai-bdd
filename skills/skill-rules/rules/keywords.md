# 規則關鍵字

規則要標示**強度**。沒有強度分級的規範，讀的人只能一律當成硬性規定，或者一律當成
建議——兩種都會出事。

## 強度階梯

由強至弱：

| 關鍵字 | 中文 | 意義 |
| --- | --- | --- |
| `MUST NOT` / `NEVER` | 絕對不可 | 完全禁止。沒有例外，不接受「這次情況特殊」。 |
| `MUST` | 必須 | 硬性規定。沒有選擇餘地，違反即為錯誤。 |
| `IMPORTANT` | 高優先 | 強烈要求。比 `SHOULD` 重，但仍留有判斷空間。 |
| `SHOULD` | 應該 | 好建議，是正確的路，但不是法律。有正當理由可以偏離。 |
| `SHOULD NOT` | 不應該 | 不建議這樣做。有正當理由時仍可為之。 |
| `COULD` | 可以 | 軟性選項。做得到，但由執行者自行決定。 |

偏離 `SHOULD` 或 `SHOULD NOT` 時**必須說明理由**。這正是它與 `MUST` 的差別：
`MUST` 不接受理由，`SHOULD` 接受但要求你講出來。能不能講出理由，就是這兩級的
實際分界。

`IMPORTANT` 是階梯上的一級，和其他級別一樣衡量強制程度——它不是「顯著性標記」。
它的典型用途是那種**技術上不會報錯、但漏掉會安靜毀掉整件事**的規則，例如
「子目錄的檔案必須在 SKILL.md 裡指路」：不指路不會有任何錯誤訊息，那些檔案只是
永遠不會被讀到。這種規則需要比 `SHOULD` 更強的語氣，但仍存在合理例外，所以不是
`MUST`。

SHOULD NOT: 把 `IMPORTANT` 疊加在其他關鍵字上（`IMPORTANT: NEVER ...`）。
同一個階梯上的兩級疊加會讓強度變得無法解讀——讀的人不知道該當成 `NEVER` 還是
更強的什麼。要凸顯某條規則，用位置（放在段落開頭）或說明理由，不要疊關鍵字。

## 輔助標記

以下不表示強度：

| 關鍵字 | 用途 |
| --- | --- |
| `Check if:` | 條件判斷——特定情況才適用。 |
| `Ask user:` | 需要使用者確認才能繼續。 |

## 使用原則

**強度必須稀有才有意義。** 整份文件都是 `MUST` 時，讀的人分不出哪一條才是真的
不能違反，結果等同於全部都沒有標。

這不是統計觀察，是定義上的必然：強度標記的作用是**區分**，而區分需要對比。
所以與其記「應該只有一兩條 `MUST`」這種沒有依據的數字，不如每次都跑下面的檢驗，
讓數量自然落下來。

判斷一條規則該給什麼強度，問這兩個問題：

1. **違反會怎樣？** 產出錯誤、資料遺失、安全問題 → `MUST` / `NEVER`。
   只是品質差一點、後續要多花工夫 → `SHOULD`。
2. **有沒有正當的例外？** 想得出任何一種合理例外 → 就不是 `MUST`。

第 2 點是最好用的檢驗。多數被寫成 `MUST` 的規則，稍微想一下就能舉出合理例外，
那它本來就該是 `SHOULD`。

## 寫法

關鍵字放在句首，後面直接接規則本身：

```markdown
- MUST: 目錄名與 frontmatter 的 `name` 一致。
- NEVER: 把未經確認的路徑當成預設值寫入檔案。
- SHOULD: 觸發詞涵蓋口語與正式兩種說法。
- SHOULD NOT: 在 description 裡放「處理」「做事」這類通用詞。
- COULD: 為長流程加上進度回報。
```

SHOULD NOT: 用中文的「必須」「應該」取代英文關鍵字。理由不是英文天生比較精確，
而是**這份文件為這幾個英文詞定義了固定分級，中文語氣詞沒有對應的定義**——「應該」
有人當建議、有人當要求，而讀者無從查證作者是哪個意思。分級的共識來自上面那張表，
不是來自英文本身；沒讀過這張表的人看到 `SHOULD` 一樣會模糊。

所以規則的**說明文字**用繁體中文，**強度標記**用英文關鍵字，並確保任何會讀到
這些規則的人都能找到這張表。

## 常見錯誤

| 寫法 | 問題 |
| --- | --- |
| 整份都是 `MUST` | 等於沒有重點 |
| 只有規則，沒有理由 | 遇到未預見的情況時無法推論，只能照字面硬做 |
| `NEVER` 後面接的是品味問題 | 消耗最高強度的信用，真正的禁止事項就沒人當真了 |
| 中英文強度詞混用（「必須 SHOULD」） | 自相矛盾 |
