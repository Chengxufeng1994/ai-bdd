# 品質清單

稽核時逐項對照。機械可查的項目由 `../scripts/audit_skill.py` 處理，這裡列出的是
**需要讀過內容才能判斷**的部分。

## 基礎（不過就是不合格）

- [ ] `name` 是有意義的 kebab-case，且與目錄名一致
- [ ] `description` 有用途說明 ＋ 中英文觸發詞
- [ ] 有 `## 使用時機`
- [ ] 有 `## Skill Boundaries`
- [ ] 流程步驟具體可執行，沒有「分析一下」這類無法照做的指令
- [ ] 至少一條 `IMPORTANT:` 標出真正會出事的地方
- [ ] 輸出格式有明確說明

## 進階（決定它好不好用）

- [ ] 觸發詞涵蓋動詞變化、名詞同義、口語與正式、中英文
- [ ] 需要輸入才能開始的 skill，有 `## 前置確認（Ask user）`，且每項都寫了為什麼需要
- [ ] 前置確認只問「少了就做不對」的項目，其餘標為選填
- [ ] 有 `NEVER:` 擋住最嚴重的錯誤
- [ ] 長流程有使用者檢查點
- [ ] Skill Boundaries 指到的 skill 真的存在
- [ ] 有實際範例，不只有抽象說明
- [ ] 子目錄的每個檔案都被明確指路

## 品質訊號

以下是**未經驗證的設計判斷**，不是實測結果。它們有推理支撐，但沒有任何測試證明
遵守它們能產出更好的 skill。當成「值得停下來想」的提示，不要當成規則引用。

要讓它們可被證偽，需要 `skill-creator` 的 eval 迴圈：同一批測試提示，比較有無
套用的產出。

| 訊號 | 通常代表 |
| --- | --- |
| 整份都是大寫 MUST / NEVER | 沒有重點，模型分不出哪條真的不能違反 |
| 只有命令，沒有「為什麼」 | 遇到未預見的情況時模型無法推論，只能照字面硬做 |
| 例子全部來自同一個場景 | 過度貼合單一案例，換個情境就失效 |
| 本文超過 500 行 | 該把只有特定情況才需要的段落下放到子目錄 |
| Skill Boundaries 是空的或含糊 | 與其他 skill 的重疊還沒被面對 |
| 觸發詞裡有「處理」「做事」這種通用詞 | 會製造誤觸發，而誤觸發比不觸發更難察覺 |

最後一項的推導寫在這裡供檢驗：兩種失敗的**訊號不對稱**——不觸發時使用者會發現
「怎麼沒用到」而主動反應；誤觸發則安靜地產出一份用錯方法的結果，沒有缺席訊號。
若這個不對稱成立，刪掉一個過於通用的觸發詞就比多加五個精準的更有價值。

前提（訊號不對稱）本身也未經實測。

## 稽核輸出格式

逐項回報時用這個結構，讓人能直接照著修：

```markdown
## 稽核：<skill-name>

**機械檢查**：<通過 / N 項失敗>

### 必須修正
- <規則編號> <問題> —— <怎麼改>

### 建議
- <問題> —— <怎麼改>

### 通過
<簡短帶過，不逐條列出>
```

不要把通過的項目逐條列出。稽核報告的價值在於指出要動什麼，把 20 個 ✅ 攤開只會
淹沒那 3 個要修的。
