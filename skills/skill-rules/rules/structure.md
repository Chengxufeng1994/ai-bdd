# 結構規則

判定一份 skill 的結構合不合格。每一條都能拿來對照一個現成的 skill 回答是或否。

## 目錄

| # | 強度 | 規則 | 違反的後果 |
| --- | --- | --- | --- |
| S1 | `MUST` | 目錄內有 `SKILL.md`（大小寫完全一致） | 不會被辨識為 skill |
| S2 | `MUST` | 目錄名 = frontmatter 的 `name` | 引用與稽核對不上 |
| S3 | `SHOULD NOT` | 出現 `rules/` `references/` `examples/` `scripts/` 以外的子目錄 | 結構失控，找不到東西 |
| S4 | `SHOULD` | 子目錄有內容才建，不放佔位檔 | 空目錄 git 不追蹤，佔位檔是雜訊 |
| S5 | `MUST` | 子目錄內的每個檔案被 SKILL.md 或其他被引用的檔案指到 | 孤兒檔案，永遠不會被讀 |

S5 值得特別說明：**子目錄的檔案不會自動載入**。只有 SKILL.md 的本文在觸發時進
context，其餘一律要靠明確指路（「詳見 `rules/x.md`」）。沒指路的檔案對模型而言
不存在——它甚至不知道那個檔案有內容。

### S3 為何是 `SHOULD NOT` 而非 `MUST NOT`

參考教材列的輔助資料夾是 `scripts/` `references/` `assets/`，其中 **`assets/`
（範本、圖片、字型）不在本專案的四個目錄裡**。這是刻意的取捨，不是疏漏：本專案
的 skill 目前都是流程與規範型，沒有要產出的二進位資產。

但這個取捨有已知代價——真的需要放 HTML 範本或圖片時，四個目錄沒有一個對：
`references/` 是給模型讀的文件、`examples/` 是範例。

遇到這種情況時的作法：**跟隨 `~/.claude/skills/commit-message/` 的既有慣例，
用 `templates/`**（該 skill 的結構是 `SKILL.md` ＋ `references/` ＋ `rules/` ＋
`templates/`）。新增第五個目錄需要明講理由，這也正是 S3 是 `SHOULD NOT` 的原因：
它擋的是隨意增生，不是擋住有正當需求的例外。

## SKILL.md 章節

| # | 強度 | 規則 | 為什麼 |
| --- | --- | --- | --- |
| S6 | `MUST` | 有 `## 使用時機` | 讓人與模型判斷該不該用 |
| S7 | `MUST` | 有 `## Skill Boundaries` | 減少誤觸發，讓相關 skill 形成清楚生態 |
| S8 | `MUST` | 有可執行的工作流程 | 「分析一下」不是步驟 |
| S9 | `SHOULD` | 有輸出格式說明 | 否則每次產出長得不一樣 |
| S10 | `SHOULD` | 本文控制在 500 行內 | 超過表示該把細節下放到子目錄 |

| S14 | `SHOULD` | 需要使用者輸入才能開始的 skill，有 `## 前置確認（Ask user）` | 缺了它，模型會用假設的輸入產出真實的結果 |

> S14 編號接在後面而不是插進 S6–S10 之間：規則編號是**引用位址**，重新編號會讓
> 既有引用靜默指到別條規則。編號穩定優先於排列整齊。

## S14：前置確認

這是條件式規則——不是每個 skill 都需要。

判準要可操作，否則每個 skill 都能說「我有必要輸入」。用這個檢驗：
**若使用者完全沒提供這項資訊，模型只能猜；而猜錯時，產出會看起來正常卻整份無用。**

兩個條件都要成立。只滿足「只能猜」不算——很多東西猜錯只是細節有出入，改一下
就好；要到「整份無用」的程度，才值得擋在流程前面問。

有的話，在工作流程之前放一段：

```markdown
## 前置確認（Ask user）

Ask user: 若使用者未提供以下資訊，逐一詢問後才開始。

1. **<資訊項>**：<為什麼需要它>
2. **<資訊項>**：<為什麼需要它>（選填）

<一句話說明為什麼不能用預設值猜>
```

要寫出「為什麼需要它」，因為那決定了使用者該給多細的答案。只列項目名稱，得到的
回答通常太模糊而仍然要再問一輪。

IMPORTANT: 這個章節防的是 skill 最常見的失效方式——**用假設的輸入產出真實的
結果**。模型不會停下來說「我不知道」，它會挑一個合理的猜測繼續做，而產出看起來
完全正常，錯誤被藏在一份漂亮的成品裡。使用者往往到很後面才發現前提就錯了。

SHOULD NOT: 把所有可能的輸入都列成必填。只問**少了就做不對**的，其餘標為選填或
乾脆不問——每多問一題，使用者放棄的機率就高一分。

S10 的門檻不是硬性上限，而是訊號。接近時該問的是「哪些段落只有特定情況才需要
讀」，把那些下放，主檔留骨架。

## 章節順序

```markdown
---
name: ...
description: ...
---

# 標題

## 使用時機

## Skill Boundaries

## <工作流程：步驟或規則>

## <輸出格式>
```

`使用時機` 與 `Skill Boundaries` 放在最前面，因為它們回答「我是不是找錯地方了」。
模型讀到第三段才發現該用別的 skill，前兩段的 token 就白付了。

## 與 plugin 的關係

skill 放在 plugin 的 `skills/` 下時：

| # | 強度 | 規則 | 為什麼 |
| --- | --- | --- | --- |
| S11 | `SHOULD` | 扁平放在 `skills/<name>/`，不用巢狀分類 | `claude plugin validate` 不遞迴，巢狀的 skill 不會被驗證 |
| S12 | `MUST` | 名稱在**同一個 plugin 內**唯一 | plugin 內是扁平命名空間，目錄層級不存在 |
| S13 | `SHOULD` | 同組 skill 用共同前綴 | 扁平命名空間裡，字母排序是唯一還能保住分組的機制 |

S11 是 `SHOULD` 而非 `MUST`：證據只支持「巢狀不會被 validate 檢查」，不支持
「巢狀會壞」——`mattpocock-skills` 長期使用巢狀結構且運作良好。這是可驗證性的
取捨，不是正確性的紅線。

S12 **不要求全域唯一**。跨 plugin 同名可以共存，以 plugin 名前綴區分；本機
plugin cache 裡 `verification-loop`、`tdd-workflow` 等名稱各出現 44 次。

各項的證據等級與重現方式見 `../references/runtime-facts.md`。

## 數字門檻的出處

| 門檻 | 出處 |
| --- | --- |
| S10 的 500 行 | `skill-creator` 的指引（"Keep SKILL.md under 500 lines"） |

它是**訊號而非上限**。接近時該問的是「哪些段落只有特定情況才需要讀」，把那些
