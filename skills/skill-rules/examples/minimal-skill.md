# 合格範例

一個結構完整、篇幅最小的 skill。可以直接當範本改。

它刻意選了一個與本專案無關的領域（提案撰寫），因為範例若全部來自同一個場景，
讀的人會把場景細節誤當成規則的一部分。

```markdown
# 提案撰寫助手

## 使用時機

- 需要快速起草專案提案書或企劃書
- 想把零散的想法組織成結構化文件
- 要向客戶或上級呈報的提案需要初稿

## Skill Boundaries

- 要審查已有的提案 → 改用 `proposal-reviewer`
- 政府標案格式不同 → 本 skill 不涵蓋
- 本 skill 產出的是**初稿**，需人工審查後才可使用

## 前置確認（Ask user）

Ask user: 若使用者未提供以下資訊，逐一詢問後才開始撰寫。

1. **提案目的**：解決什麼問題？決定了整份文件的主軸
2. **目標受眾**：提案給誰看？決定了訴求角度與重點順序
3. **預算範圍**（選填）
4. **時程**（選填）

前兩項不能猜。提案的訴求角度完全取決於受眾——寫給財務長和寫給工程主管的同一份
提案，重點順序是相反的。缺了它寫出來的初稿通常要整份重來。後兩項標為選填，是
因為它們影響的只是細節，而每多問一題使用者放棄的機率就高一分。

## 撰寫流程

### 步驟一：決定訴求角度

依目的與受眾，從成本效益／創新性／風險降低／競爭優勢中選一個為主軸。

### 步驟二：依格式產出

## 輸出格式

    # [提案標題]

    ## 執行摘要
    [3-5 句話說明核心價值主張]

    ## 問題與機會
    ## 解決方案
    ## 執行計畫
    ## 預期成果
    ## 資源需求
    ## 風險評估

## 規則

- IMPORTANT: 執行摘要要能獨立閱讀。忙碌的決策者往往只讀這一段，其餘章節是
  給需要細節的人看的。
- NEVER: 捏造數據或競爭對手資料。
- NEVER: 在使用者未提供的情況下承諾具體 ROI 數字。
- SHOULD: 標題具體有力，避免「關於 X 的提案」這種格式。
```

## 這個範例示範了什麼

| 特徵 | 對應規則 |
| --- | --- |
| `description` 有用途 ＋ 中英文觸發詞 | F4–F6 |
| `## 使用時機` 在最前面 | S6 |
| `## Skill Boundaries` 指到具體替代方案 | S7 |
| 有 `## 前置確認（Ask user）`，且說明每項為什麼需要 | S14 |
| 步驟具體到能照做 | S8 |
| 輸出格式明確 | S9 |
| 只有兩條 `NEVER`，其餘是 `SHOULD` | 強度稀有才有意義 |
| `IMPORTANT` 用在「容易漏掉、漏掉代價高」 | 見 `../rules/keywords.md` |
| 規則附理由（為什麼先問受眾） | 讓模型能處理未預見的情況 |
| 沒有子目錄 | 這個 skill 簡單到不需要，因此 S4 根本沒被觸發——不是示範 S4 |
