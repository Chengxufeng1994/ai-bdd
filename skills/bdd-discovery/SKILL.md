# CLARIFY — 把需求逼問到收斂

一份 PRD 或一段模糊的敘述進來，出去的是一份 `clarify-log.md`：**問了什麼**、
**答了什麼**，以及**還開著什麼**。規則由 `bdd-spec` 從答案抽出，就緒判定
交給 `example-mapping`。

**分兩段跑。** Pass 1 對整個 feature，把它拆成目標／指標／邊界並揪出沒寫下來的假設；
Pass 2 對整個 feature，逐題問到收斂。

不寫 Gherkin。不談實作。不設計資料表。

## 使用時機

- 收到一份 PRD，要先找出它沒寫、但整份文件預設成立的假設
- 拿到一段需求或一則 story，但講得太抽象，不知道要做到什麼程度
- 需要判斷這則 story 該不該進 sprint
- 準備寫規格或 `.feature` 檔之前，先確認例子夠不夠
- 懷疑需求有沒想到的邊界情況

## Skill Boundaries

- 只是要把一則太大的 story 切開 → 改用 `story-splitting`
- 已經有一疊跳過的問題要再收斂 → 改用 `clarify-loop`
- 要把例子寫成 Gherkin → 改用 `bdd-spec`
- 要決定情境跑在哪一層測試、實作順序 → 改用 `bdd-plan`
- 要跑四色卡技巧、或判定這則 story 就不就緒 → 改用 `example-mapping`——它攤地圖、
  跑四條診斷，也是唯一寫「就緒值」的 skill；`clarify-log.md` 沒有這一欄，本 skill
  不碰它
- 產出是一份 `clarify-log.md`，**不是**規格、程式碼或資料模型

## 前置確認（Ask user）

Ask user: 若以下不明確，先問清楚再開始。

**要澄清的需求**：一段描述。這是唯一必要的輸入。

產物路徑不必問，見「產物」。

NEVER: 在需求還沒拿到時自行想像一則 story 來跑流程。那會產出一份看似完整、
實則憑空的 map，而錯誤全藏在專業的格式底下。

## 流程

```
PRD／一段敘述（新的）          或      繼續澄清（bdd-discovery [feature]）
        ↓                                          ↓
Pass 1 · 廣度 —— 對整個 feature                    （跳過 Pass 1）
  1. 拆成目標／成功指標／範圍邊界＋隱含假設         ↓
  2. 識別角色                                       ↓
  3. 只問「會改變範圍」的題目                       ↓
        ↓                                          ↓
Pass 2 · 深度 —— 對整個 feature ←──────────────────┘
  4. 澄清循環（每輪）
       ├─ 逐題問：一題一列記進 `clarify-log.md`
       └─ 還有未知？ → 下一輪
  5. 收尾：標記完成
        ↓
Pass 3 · 技術 —— 逐項掃過 technical-probes.md
  逐題問，答案一樣記進 `clarify-log.md`，面向欄填對應的技術面向
        ↓
一份 specs/<date>-<feature>/clarify-log.md，記下結束方式（收斂／阻塞／零進展／喊停）
```

### 續跑：什麼時候跳過 Pass 1

輸入不是新敘述、而是「繼續澄清」時，**Pass 1 已經跑過了，直接進 Pass 2**：

| 呼叫方式 | 範圍 |
| --- | --- |
| `bdd-discovery` | **預設：所有 `clarify-log.md` 裡『待答』表非空的 feature** |
| `bdd-discovery <feature>` | 只跑指定的那一個 |

**不要問對方要跑哪一個。** 預設全部，想限定的人自己會帶參數——多問一次等於把
決定推回去，而多數時候答案就是「都繼續」。

`clarify-log.md` 不存在時才回頭跑 Pass 1。存在就只讀不重跑——重跑會把已經問定
的邊界再問一次，而那正是最傷信任的一種重複。Pass 3 一樣：規則沒變，已經答過
的技術問題還算數，不必為續跑重新掃一遍 `references/technical-probes.md`。

開始每一個 feature 之前讀 `clarify-log.md` 的三張表：`已答` 看已經確定什麼、
`待答` 看還開著什麼、`n/a` 看跳過了什麼且為什麼——已答的問題就是目前確定的
規則。

IMPORTANT: 重問一題已經答過的，比漏問一題更傷信任——它證明你沒有讀既有產物。

換 feature 時明講「現在開始 X」，並在每一輪結束回報還剩幾個。跑多個 feature 時，
**跨 feature 的共用規則會浮現**——那是一次跑完全部的主要收穫，單獨跑一個看不到。

## Pass 1 · 廣度 —— 對整個 feature

### 為什麼需要這一段

Example Mapping 的原話是 "Rules make natural fault lines for slicing your story"
——沿規則切。但規則要到 Pass 2 才抽得出來，**在那之前硬切，切線永遠是猜的**。

實測過一次：一次停車場計費的澄清，15 題範圍題問下來，需求方三次改變答案的
形狀——入場從不擋到擋、出口不擋救護車變成入口反而進不來、容量從不存在變成
必答。若在第一批之後就切了 story，這些切線全部是錯的。

Pass 1 因此不切，只做切分將來需要、但現在就能定下來的那部分：**目標**（判斷
這個 feature 真的要交付什麼）、**邊界**（不要問進不該做的）、**隱含假設**
（每一條沒寫下來的假設都可能是一條範圍線，答案不同範圍就不同）。

MUST: Pass 1 刻意淺。**判準是「範圍講得出依據」，不是「問題都問完了」。**
能等到 Pass 2 再問的就等——那時規則已經浮現，答案會更準。

一個廣度階段最容易的失敗是變成整件事：對整份 PRD 一路問到底，永遠走不到例子。
**連續問了兩三題卻沒有一題改變範圍，就是該進 Pass 2 了。**

### 1. 拆成骨架

先不碰技術，把業務目標、成功指標、範圍邊界（In／Out）與隱含假設問過一輪，
答案記進 `clarify-log.md` 的 `已答`／`待答`／`n/a` 三張表——這幾類問題沒有
自己的章節，跟其他問題共用同一組表，`面向` 欄填 `—`（它們不屬於十一個業務
面向或五個技術面向）。

MUST: PRD 裡標題叫「假設」的那一段，**每一條都當成沒問過**，不要照抄成既定
事實——它是未驗證的斷言，不是前提。開一題進『待答』表；答案出來才移進
『已答』表。

**找隱含假設要靠機械掃描，不是靠讀。** 假設對寫的人而言是常識，常識不會被
寫下來。對 PRD 裡的每一個元素問同一句話：

| 掃什麼 | 問什麼 | 逮到的是 |
| --- | --- | --- |
| 每個**名詞** | 這是誰定義的？兩個人會不會算出不同的數？ | 沒定義的業務術語 |
| 每個**數字** | 這個數字從哪來？換成別的會怎樣？ | 拍腦袋的門檻與 SLA |
| 每個**「自動」「即時」「應該」** | 誰做？什麼時候做？沒做成怎麼辦？ | 沒列出來的 actor（多半是系統自己） |
| 每個**成功指標** | 這個指標要成立，哪些行為必須存在？PRD 有寫嗎？ | 指標與功能之間缺的那一段 |
| 每個**排除項** | 排除 A 是不是隱含要做 B？ | 被排除項推出來的隱藏需求 |

### 2. 識別角色

規則的敘述（EARS 的 `When <trigger>`）常常以角色當主詞，角色名稱不統一，
同一題會被問兩次、同一條規則會被記成兩種主詞，所以在深度追問前先定下來。

MUST: 每個角色問**是誰**／**怎麼取得這個身分**／**跟誰容易混**／**他要什麼**／
**現在什麼讓他痛**，答案記進 `clarify-log.md`，`面向` 欄填 `—`；最後兩項答不出來
就記「（無資料）」，不要編。判準、寫法與範例、別漏掉哪些角色 →
`../bdd-spec/references/persona-definition.md`。

### 3. 只問「會改變範圍」的題目

Pass 2 有一條篩選判準——「這題的不同答案，會不會導致不同的規則？」
Pass 1 的判準不一樣，而且更窄：

> **這題的不同答案，會不會改變範圍邊界、或角色清單？**

不會，就留給 Pass 2。這一關砍掉的比 Pass 2 那一關更多：大部分模糊點（怎麼四捨
五入、熱身組算不算）不管答案是什麼，範圍都不會變。

問法一樣是 **4 ＋ 1**（格式見 Pass 2 的「一題長什麼樣」），答與跳過的處理也一樣，
一樣記進 `clarify-log.md`——這題的 `面向` 欄填 `—`，它問的是範圍會不會變，
不屬於十一個業務面向或五個技術面向的任何一個。

## Pass 2 · 深度 —— 對整個 feature

### 4. 澄清循環 —— 一次一題，每輪記答案

**手法是 Example Mapping**——四色卡怎麼攤、四條診斷怎麼讀 → `example-mapping`。
本節只講這個 pass 的節奏（一次一題、每輪記答案），不重述手法。

從敘述裡找模糊點，**一題一題問**，不要一次列出全部。

逐題是刻意的：問題是樹不是清單。一個答案常會消掉三個問題、長出兩個新的——
一次列完會產生一批**本來不該存在的問題**，然後有人真的去回答它們。

#### 值不值得問

MUST: 問之前先過這一關——**這題的不同答案，會不會導致不同的規則？**

不會，就不要問。這條篩掉的通常是最多的：追問清單掃出來的候選裡，有一大半的答案
其實不影響任何行為。**問題少而準，比多而全有用得多**——三十個平等攤著的問題，
人的反應是一個都不動。

**追問清單**（找模糊點用，不是待辦清單）

| 面向 | 問法 |
| --- | --- |
| 空與零 | 沒有資料、空字串、零筆、第一次使用時？ |
| 邊界 | 剛好等於上限？超過 1 個單位？ |
| 重複 | 同一個動作做兩次？重送？ |
| 時序 | 兩件事同時發生？順序顛倒？ |
| 權限 | 換一個角色來做？沒登入？ |
| 失敗 | 外部系統掛掉？逾時？做到一半斷線？ |
| 時間 | 跨日、跨時區、日光節約？過期的定義？ |
| 規模 | 一次一萬筆？ |

**非功能面向**（行為級的那些；舉不出例子的產品級品質屬性留給 Pass 3）

| 面向 | 問法 |
| --- | --- |
| 降級 | 依賴不可用時**降級成什麼**？還是整個失敗？ |
| 時限 | 多久算太久？超過了怎麼辦——等、失敗、還是給舊資料？ |
| 可觀測 | 這件事出錯時怎麼會知道？留下什麼才查得出原因？ |

這三個跟上表的「失敗」不重複：**失敗問的是會不會壞，降級問的是壞了之後呢。**
兩者是不同的規則，只問前者的結果是規格寫了一半——寫了偵測，沒寫善後。
舉不出例子的那些（「所有操作三秒內」）留給 Pass 3 掃 `technical-probes.md` 時
處理，不會在這裡重複。

清單是起點不是全部——這個領域有什麼特有的失敗模式，一併找。

#### 一題長什麼樣

**4 ＋ 1**：四個具體答案，加一個逃生口。

```
單手啞鈴划船 20 kg，左右各做 8 下。次數欄要填多少？

  1. 填 8 —— 一邊算一組，另一邊不另計
  2. 填 16 —— 兩邊加總成一組
  3. 填 8，系統自動 ×2 —— 使用者不必自己換算
  4. 左右各記一組，共兩組 —— 分開記錄
  5. 不知道／先跳過

為什麼問：這直接讓總容量差兩倍，而幾種填法在畫面上長得一樣。
```

MUST: 1–4 **互斥且涵蓋光譜**，第 5 個永遠是逃生口。

四個具體選項比三個涵蓋得完整，但也更容易出現**湊數的那一個**。檢驗方法：
**把任一個選項拿掉，會不會少掉一種真實會發生的做法？** 不會，那它就是湊數的——
寧可只給三個，也不要用近義詞填滿版面。湊數的選項會稀釋真正的選擇，讓人隨便挑。

沒有逃生口時，人在不確定會挑一個看起來最合理的——而**被記成決定的猜測比開著的
問題更糟**：它看起來已解決，之後沒有人會回頭質疑。

選項本身是提案。對方回「都不是」時，那個更正比四個選項加起來更有資訊量——它往往
消掉一整類原本要問的問題，而不只是回答這一題。

#### 答了：兩件事一起做

MUST: 一題確定，以下事情跟著發生，缺一個就是不一致狀態：

| # | 動作 |
| --- | --- |
| 1 | 把這一列從『待答』表移到 `clarify-log.md` 的『已答』表，答案欄填上結論、誰答的欄填上回答者、歸屬欄填這個答案要進 `spec.md` 的哪一節（沒有單一節能歸屬就填 `—`） |
| 2 | 若這個答案消掉了其他還沒問的問題，說出來並跳過它們 |
| 3 | 使用者對四個選項全部回「都不是」時，把這四個選項連同正確答案一起記進『被推翻的提案』 |

第 1 項不可以留到最後一次補。剛答完那一刻你還記得為什麼；隔了二十題再回來補，
漏掉的機率高得多。而且澄清很少一次做完，**停在任何一輪，`clarify-log.md` 都該是
完整可用的**。

#### 跳過：要記為什麼跳

留在『待答』表，答案欄留 `—`，`為什麼還沒答` 欄記下**跳過的原因**。有用的
區分只有一個：**還會不會再問**。

| 原因 | 後續 |
| --- | --- |
| 之後再問 | 下一輪重問，`clarify-loop` 會接手 |
| **這題不該問** | 回頭確認它真的不影響任何行為。是 → 搬進『n/a』表，寫清楚為什麼不用問 |

只記「跳過」不記原因，`clarify-log.md` 就會變成一堆分不出輕重的待辦——而那
正是讓人一個都不想動的狀態。

Q 編號、`面向` 欄怎麼填、三張表的欄位 → `references/clarify-log-format.md`。

#### 每一輪結束：確認答案夠具體

MUST: 一輪問完就檢查這一輪的答案是不是還停在抽象層次，不要累積到最後。

一個答案在對話裡聽起來很明確，一旦要照著做事就會發現它缺條件——等全部答完
才發現，那些漏洞會一次湧出來，而且上下文已經冷了。

**答案要具體、含實際資料，不要只是換句話說：**

- ✗「一個無效的使用者」—— 這只是換句話說
- ✓「一個 token 在 3 秒前過期的使用者」

答案不夠具體，回頭追問一題，不要就這樣記下模糊的版本——**模糊的答案比誠實的
「待答」更危險**，它看起來已經解決了。

#### 什麼時候停

| 訊號 | 意義 |
| --- | --- |
| 一輪下來沒有新問題 | 收斂了，可以收尾 |
| 剩下的都被標成「之後再問」 | 停，這一輪問不動了 |
| **連續兩題被跳過** | 可能問錯層次，或整組問題超出對方的知識範圍。停下來確認 |
| 問了兩三輪但問題總數不下降 | 先用 Pass 1 的判準確認範圍有沒有抓錯：**沒抓錯**——這個 feature 本來就大，不是切小它，繼續問完，多大交給 SPEC 之後決定；**抓錯了**——回 Pass 1 補問「會改變範圍」的題目，重新定住邊界，再回來繼續 Pass 2 |
| **抽不出新規則** | 這一輪的答案沒有改變任何行為。問題選錯了，回頭看「值不值得問」那一關 |

### 5. 收尾：標記完成，`clarify-log.md` 全部保留

業務面向的『待答』列都清空之後（技術面留給 Pass 3 掃）：

1. **核對覆蓋**：十一個業務面向每一個都至少出現在某一列的 `面向` 欄——
   包含標 `n/a` 的。少了哪個面向，代表它根本沒被問過
2. **核對 persona**：Pass 1 列出的每個角色，`clarify-log.md` 裡至少有一輪
   問答問到它；問答裡講出來的角色也都在 Pass 1 的名單裡。兩個方向都要對得
   上——只對一邊會漏掉憑空的角色
3. **稽核分類是否窮盡**（見下）
4. **`clarify-log.md` 保留，不刪除**

核對不能跳過——它是「面向要嘛問過要嘛標 n/a」那條規則的驗收。若某個面向連
一列都沒有，代表它根本沒被想過，**先補一題**再往下走。

#### 稽核分類是否窮盡

MUST: 問答裡浮現的每一張**列舉型的表**（型別、狀態、角色、單位）拿出來問一次：
**這個領域裡有沒有一種真實存在的東西，這張表放不進去？**

追問清單的十一個面向問的都是**已知那件事的極端值**——空、邊界、重複、時序。問不到
**漏掉一整類資料**，因為漏掉的那類從來沒出現在對話裡，沒有極端值可問。

實測過一次：健身 App 的動作型別表有六種，全部以「次數」計量，於是棒式（60 秒，
沒有次數）無處可放，被迫和跑步機歸成同一類。三輪澄清都沒問到，是抽完規則後回頭
對照才發現的。

找到放不進去的東西，就開一題新的，記進『待答』表——不要自己塞進最接近的那一格。

#### 為什麼保留

`clarify-log.md` 記的是問答本身，不是規則——規則被 `bdd-spec` 抽走、寫進
`spec.md` 之後，這份記錄留著**為什麼**：問了什麼、答案怎麼來的、被推翻過
的提案。下次改動第一個會問的問題往往是「當初為什麼不選第二個選項」，答案
只在這裡找得到。

IMPORTANT: 保留不等於它是規則的定案來源——`spec.md` 寫出來之後，規則以
`spec.md` 為準；`clarify-log.md` 留著的是**為什麼**，不是規則本身。

## Pass 3 · 技術 —— 對開發者

Pass 2 收斂之後才跑。順序不能反：**技術問題有一半要看過 Pass 2 問出來的答案
才問得出來**（「這批行為要收在幾個服務裡」得先知道有哪些行為）。

問法跟 Pass 2 一樣——一次一題、四個選項、答不出來記成待答。
差別只有兩個：**對象是開發者不是產品方**，**面向清單換一份**。

逐項掃過 `references/technical-probes.md` 的每個面向，答案一樣記進
`clarify-log.md`，`面向` 欄填對應的技術面向名稱。答不出來的記進『待答』表，
標 `n/a` 的要寫理由，否則它跟「懶得問」分不出來。

IMPORTANT: **SPEC 那一步不會再問任何問題。** 它只讀 `clarify-log.md` 已經有
答案的東西。所以這一趟漏掉的面向，不會在下游被補起來——它會在 `clarify-log.md`
的『待答』表留下一列，SPEC 只會看見它還沒答，不會替你補問。

## 產物

└── clarify-log.md    CLARIFY  ★ 唯一產物

（spec.md 是 SPEC 的產物，本 skill 不得寫入）

這一條不是分工偏好：Discovery 是模型追問、使用者回答；Formulation 是模型書寫、

## 產物隔離

文件型產物**全部住在 `specs/`**，一個目錄裝完。專案的其他地方不會多出東西。

| 規則 | 強度 |
| --- | --- |
| 只寫入 `specs/` 底下 | `MUST` |
| 不修改專案既有的任何檔案 | `MUST` |
| 沒有 `docs/` 就建一個 | `SHOULD` |
| 專案明文用別的文件根目錄就跟隨，仍加 `bdd/` 這層 | `SHOULD` |

`.feature` 是唯一例外：它同時是規格與可執行測試，**位置由測試框架決定**，留在
框架的慣例位置。鏈的完整性靠引用維繫，不是靠同目錄。

## 完成後

在 `clarify-log.md` 的檔頭填上這一輪的結束方式，四選一：

- **收斂** → 三張表裡沒有『待答』的列，下一步跑 `bdd-spec`
- **阻塞** → 卡在等外部答案，寫清楚卡在誰身上、等什麼
- **零進展** → 連續幾輪答不出新東西，回頭檢查是不是問錯層次
- **喊停** → 使用者決定帶著還開著的問題往下走

不要不講就往下跑——收斂以外的三種結束方式都代表 `clarify-log.md` 還有洞，
跑 `bdd-spec` 之前要讓對方知道。
