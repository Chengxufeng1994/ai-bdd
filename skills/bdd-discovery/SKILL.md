# CLARIFY — 把需求逼問到收斂

一份 PRD 或一段模糊的敘述進來，出去的是一份 `clarify-log.md`：**問了什麼**、
**答了什麼**，以及**還開著什麼**。

**把需求攤成一棵設計樹。** 每個決定都會岔出依賴它的下一批決定。**前沿**是所有
**前提已經定案**的決定——現在就問得出口、不必先猜任何還沒聽到的答案的那些題。
一輪問完整個前沿，等答案，重算，再問下一輪。**前沿空了就結束**：每一條分支都
走過，沒有東西被默默假設。

不寫 Gherkin。不談實作。不設計資料表。

## 使用時機

- 收到一份 PRD，要先找出它沒寫、但整份文件預設成立的假設
- 拿到一段需求或一則 story，但講得太抽象，不知道要做到什麼程度
- 需要判斷這則 story 該不該進 sprint
- 準備寫規格或 `.feature` 檔之前，先確認例子夠不夠
- 懷疑需求有沒想到的邊界情況

## Skill Boundaries

- 只是要把一則太大的 story 切開 → 改用 `story-splitting`
- 已經有一疊跳過的問題要再收斂 → 改用 `clarify-loop`
- 要把例子寫成 Gherkin → 改用 `bdd-formulation`
- 要決定情境跑在哪一層測試、實作順序 → 改用 `bdd-plan`
- 要跑四色卡技巧、或判定這則 story 就不就緒 → 改用 `example-mapping`——它攤地圖、
  跑四條診斷，也是唯一寫「就緒值」的 skill；`clarify-log.md` 沒有這一欄，本 skill
  不碰它
- 產出是一份 `clarify-log.md`，**不是**規格、程式碼或資料模型

## 前置確認（Ask user）

Ask user: 若以下不明確，先問清楚再開始。

**要澄清的需求**：一段描述。這是唯一必要的輸入。

產物路徑不必問，見「產物」。

NEVER: 在需求還沒拿到時自行想像一則 story 來跑流程。那會產出一份看似完整、
實則憑空的 map，而錯誤全藏在專業的格式底下。

## 流程

```
新的需求敘述                        或    繼續澄清（bdd-discovery [feature]）
        ↓                                          ↓
開場（只做一次）                              （開場已經做過，直接進輪次）
  原文存檔 · 拆骨架 · 登記關係人 · 識別角色        ↓
        ↓                                          ↓
每一輪 ←──────────────────────────────────────────┘
  1. 算前沿：所有前提已定案的決定
  2. 一次問完，編號，每題附建議答案
  3. 等使用者回答
  4. 答案重塑這棵樹 → 回到 1
        ↓
前沿空了 → 收尾核對 → example-mapping 攤地圖、跑診斷、提就緒問句
        ↓
一份 specs/<date>-<feature>/clarify-log.md，記下結束方式（收斂／阻塞／零進展／喊停）
```

### 續跑

| 呼叫方式 | 範圍 |
| --- | --- |
| `bdd-discovery` | **預設：所有 `clarify-log.md` 裡『待答』表非空的 feature** |
| `bdd-discovery <feature>` | 只跑指定的那一個 |

**不要問對方要跑哪一個。** 預設全部，想限定的人自己會帶參數——多問一次等於把
決定推回去，而多數時候答案就是「都繼續」。

`clarify-log.md` 不存在才跑開場。存在就只讀不重跑，並且**用它重建設計樹**：
『已答』表的每一列是一個已定案的決定，『待答』是還開著的分支，『n/a』是走過
但判定不適用的。前沿從這三張表算得出來。

IMPORTANT: 重問一題已經答過的，比漏問一題更傷信任——它證明你沒有讀既有產物。

換 feature 時明講「現在開始 X」，並在每一輪結束回報還剩幾個。跑多個 feature 時，
**跨 feature 的共用規則會浮現**——那是一次跑完全部的主要收穫，單獨跑一個看不到。

### 開場：只做一次的四件事

#### 原文存檔

MUST: 問第一題之前，先把需求方帶來的原始輸入**逐字複製**進同目錄的 `input.md`
（那條 MUST 與它的理由見「產物」）。這不是收尾的歸檔動作，是這一步的第一個動作
——`bdd-spec` 的 `PRD §x` 來源標記回指的就是這份原文，晚一點補等於它中間那段時間
指向一份不存在的文件。

#### 拆骨架與隱含假設

先不碰技術，把業務目標、成功指標、範圍邊界（In／Out）與隱含假設問過一輪，
答案記進 `clarify-log.md` 的 `已答`／`待答`／`n/a` 三張表——這幾類問題沒有
自己的章節，跟其他問題共用同一組表，`面向` 欄填 `—`（它們不屬於十一個業務
面向或五個技術面向）。

MUST: PRD 裡標題叫「假設」的那一段，**每一條都當成沒問過**，不要照抄成既定
事實——它是未驗證的斷言，不是前提。開一題進『待答』表；答案出來才移進
『已答』表。

**找隱含假設要靠機械掃描，不是靠讀。** 假設對寫的人而言是常識，常識不會被
寫下來。對 PRD 裡的每一個元素問同一句話：

| 掃什麼 | 問什麼 | 逮到的是 |
| --- | --- | --- |
| 每個**名詞** | 這是誰定義的？兩個人會不會算出不同的數？ | 沒定義的業務術語 |
| 每個**數字** | 這個數字從哪來？換成別的會怎樣？ | 拍腦袋的門檻與 SLA |
| 每個**「自動」「即時」「應該」** | 誰做？什麼時候做？沒做成怎麼辦？ | 沒列出來的 actor（多半是系統自己） |
| 每個**成功指標** | 這個指標要成立，哪些行為必須存在？PRD 有寫嗎？ | 指標與功能之間缺的那一段 |
| 每個**排除項** | 排除 A 是不是隱含要做 B？ | 被排除項推出來的隱藏需求 |

#### 登記核心關係人

MUST: 同一趟把**核心關係人**登記進 `clarify-log.md` 的 `## 核心關係人` 表，
三欄：`關係人 ／ 負責什麼 ／ 決策權`。這是問問題的工作——每開一題就得知道該問誰
（『待答』表的 `該問誰` 欄），這張表是同一份資訊的彙整，加上那個人**能決定什麼**。
後面每冒出一個新的受訪者就補一列。

**`決策權` 這一格只有這裡寫得出來。** `bdd-spec` 不訪談，它把整張表原樣抄進
`spec.md` 的 `## Document Overview`；這裡沒登記，它就分不出哪些答案是定案、哪些
只是還要開會表決的提案，於是只能編——而編出來的內容正是下一步明文禁止的東西。

#### 識別角色

規則的敘述（EARS 的 `When <trigger>`）常常以角色當主詞，角色名稱不統一，
同一題會被問兩次、同一條規則會被記成兩種主詞，所以在深度追問前先定下來。

MUST: 每個角色問**是誰**／**怎麼取得這個身分**／**跟誰容易混**／**他要什麼**／
**現在什麼讓他痛**，答案記進 `clarify-log.md`，`面向` 欄填 `—`；最後兩項答不出來
就記「（無資料）」，不要編。判準、寫法與範例、別漏掉哪些角色 →
`../bdd-spec/references/persona-definition.md`。

## 前沿怎麼算

### 設計樹

每個已定案的決定會岔出依賴它的下一批決定。**前沿 ＝ 所有前提已經定案的決定。**

判準只有一句：**這題的答案，會不會因為另一題還沒答而改變？** 會，它屬於**後面**
的輪次，不是這一輪。

這取代了舊版開場那條「只問會改變範圍的題目」的篩選——那條規則在猜哪些題該先問，
前沿是**算**出來的。範圍題之所以先問，不是因為有人規定，是因為其他幾乎所有題
的前提都掛在它身上。

MUST NOT: 因為某題「感覺比較重要」就把它拉進這一輪。重要不等於前提已定案；
拉進來的結果是你拿到一個建立在還沒問到的答案上的回答。

### 十六個面向是前沿的檢查表

11 個業務面向（空與零／邊界／重複／時序／權限／失敗／時間／規模／降級／時限／可觀測）
與 5 個技術面向（seam、模組邊界、介面與型別契約、排序契約／決定性、既有資產／測試慣例）
不再是三趟掃描，而是**每輪算前沿時的檢查表**：

> 對每一個**已經定案**的決定問——這 16 個面向裡，有哪個還沒對它問過？

問得出來的就是這一輪前沿的題。技術面向多一條：**能自己查的先查**（見下一節）。

面向名稱與順序是 `../bdd-spec/scripts/status.py` 的 `DIMS` 與
`references/technical-probes.md` 的共用契約，**不得增減或改名**。每一題的
`面向` 欄照樣填——`status.py` 的追問覆蓋率完全靠那一欄，而它是這個 repo 裡
唯一看得出「有沒有真的問過邊界」的東西。

### 能自己查的事實不准問使用者

MUST: 前沿問題需要的**事實**若在環境裡查得到——既有測試怎麼寫、某個模組的介面
長怎樣、有沒有現成的 seam——**派 sub-agent 去查**，不要問使用者。
哪些面向該自己查、哪些該問人 → `references/technical-probes.md` 的第二欄。

MUST NOT: 因為 sub-agent 還在跑就停下來。**一個進行中的探查是一個未定案的前提**
——只有依賴它的問題要等，**前沿其餘的照問**。

**決定是使用者的，事實是你的。** 把事實問題丟回去，等於要對方做你做得到的功課，
而且他的答案未必比環境裡的真相準。

## 一題長什麼樣

格式固定，一輪裡每題都這樣：

```
❓ **Q1** - **<問題標題>**：<問題本體，可以多段，可以含選項>

➡️ <你的建議答案>
```

編號讓對方可以只回「Q2 選第二個、Q3 你的建議可以」，不必重述題目。

**建議欄是逃生口，不是裝飾。** 一個沒有建議的問題把全部認知負擔丟回去；一個
有建議的問題只要求對方判斷「對不對」。

MUST: **沒有站得住的預設時，建議欄要寫「這題我不建議猜——要去問 <誰>」**，
`<誰>` 指向 `## 核心關係人` 表裡的人。編一個聽起來合理的建議，比承認不知道更糟
——對方多半會直接接受，而那個答案從此看起來像是問過的。

一輪問完整個前沿。**不要一次只問一題**——前沿上的題彼此沒有依賴，分開問只是
多幾趟來回，而每一趟來回都是對方重新載入上下文的成本。

## 結束：前沿空了

**前沿空了之後**：

1. **核對覆蓋**：十一個業務面向每一個都至少出現在某一列的 `面向` 欄——
   包含標 `n/a` 的。少了哪個面向，代表它根本沒被問過
2. **核對 persona**：開場列出的每個角色，`clarify-log.md` 裡至少有一輪
   問答問到它；問答裡講出來的角色也都在開場的名單裡。兩個方向都要對得
   上——只對一邊會漏掉憑空的角色
3. **稽核分類是否窮盡**（見下）
4. **`clarify-log.md` 保留，不刪除**
5. **交給 `example-mapping`**：前沿空了之後，由它攤開四色卡、跑四條診斷、把就緒
   問句交給使用者。就緒判定不在本 skill——`clarify-log.md` 沒有就緒欄，本 skill
   不碰它

核對不能跳過——它是「面向要嘛問過要嘛標 n/a」那條規則的驗收。若某個面向連
一列都沒有，代表它根本沒被想過，**先補一題**再往下走。

### 稽核分類是否窮盡

MUST: 問答裡浮現的每一張**列舉型的表**（型別、狀態、角色、單位）拿出來問一次：
**這個領域裡有沒有一種真實存在的東西，這張表放不進去？**

追問清單的十一個面向問的都是**已知那件事的極端值**——空、邊界、重複、時序。問不到
**漏掉一整類資料**，因為漏掉的那類從來沒出現在對話裡，沒有極端值可問。

實測過一次：健身 App 的動作型別表有六種，全部以「次數」計量，於是棒式（60 秒，
沒有次數）無處可放，被迫和跑步機歸成同一類。三輪澄清都沒問到，是抽完規則後回頭
對照才發現的。

找到放不進去的東西，就開一題新的，記進『待答』表——不要自己塞進最接近的那一格。

### 為什麼保留

`clarify-log.md` 記的是問答本身，不是規則——規則被 `bdd-spec` 抽走、寫進
`spec.md` 之後，這份記錄留著**為什麼**：問了什麼、答案怎麼來的、被推翻過
的提案。下次改動第一個會問的問題往往是「當初為什麼不選第二個選項」，答案
只在這裡找得到。

IMPORTANT: 保留不等於它是規則的定案來源——`spec.md` 寫出來之後，規則以
`spec.md` 為準；`clarify-log.md` 留著的是**為什麼**，不是規則本身。

## 產物

```
specs/<date>-<feature>/
├── input.md           需求方帶來的原始輸入，開始澄清時逐字複製一次
└── clarify-log.md     CLARIFY  ★ 問答記錄

（spec.md 是 SPEC 的產物，本 skill 不得寫入）
```

格式 → `references/clarify-log-format.md`。

MUST: 開始澄清時把需求方帶來的原始輸入**逐字複製**進 `input.md`，之後不得
再改寫它。`bdd-spec` 的 `PRD §x` 來源標記回指的就是這份原文；改寫 `input.md`
等於讓那個標記從此指向一句不存在的話，而且不會報錯——它只是悄悄指錯。

MUST NOT: 寫 `spec.md`。**連 story 的定版句子都不寫**——那是 `bdd-spec` 的第一句話。
這一條不是分工偏好：Discovery 是模型追問、使用者回答；Formulation 是模型書寫、
使用者審閱。**兩者是方向相反的工作模式**，混在一起的結果是模型一邊問一邊自己補答案。

MUST NOT: 另存一份進度儀表板。進度是**算出來的**——`../bdd-spec/scripts/status.py`
從 `spec.md` 的 `## Open Questions` 直接數；`clarify-log.md` 階段還沒有 `spec.md`，
進度就看這份 log 的三張表。

---

## 產物隔離

文件型產物**全部住在 `specs/`**，一個目錄裝完。專案的其他地方不會多出東西。

| 規則 | 強度 |
| --- | --- |
| 只寫入 `specs/` 底下 | `MUST` |
| 不修改專案既有的任何檔案 | `MUST` |
| 沒有 `docs/` 就建一個 | `SHOULD` |
| 專案明文用別的文件根目錄就跟隨，仍加 `bdd/` 這層 | `SHOULD` |

`.feature` 是唯一例外：它同時是規格與可執行測試，**位置由測試框架決定**，留在
框架的慣例位置。鏈的完整性靠引用維繫，不是靠同目錄。

## 完成後

在 `clarify-log.md` 的檔頭填上這一輪的結束方式，四選一：

- **收斂** → 三張表裡沒有『待答』的列，下一步跑 `bdd-spec`
- **阻塞** → 卡在等外部答案，寫清楚卡在誰身上、等什麼
- **零進展** → 連續幾輪答不出新東西，回頭檢查是不是問錯層次
- **喊停** → 使用者決定帶著還開著的問題往下走

不要不講就往下跑——收斂以外的三種結束方式都代表 `clarify-log.md` 還有洞，
跑 `bdd-spec` 之前要讓對方知道。
