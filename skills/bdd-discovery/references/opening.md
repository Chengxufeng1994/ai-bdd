# 第 0 件事：建檔

`specs/<date>-<feature>/spec.md` 還不存在時，開場先把它建出來。**已經存在、而且有
`## User Stories` 的不重建**——告訴對方它在、狀態是什麼，跳過整份文件直接進開場的另外
三件事。建出來的是一份狀態 `澄清中` 的半成品：**原文逐字在裡面、
開頭幾節從原文抽出來、story 粗切好但底下是空的、需求方自己知道的開放問題已經是紅卡。**

這一件事是**書記**。需求方說、你記；原文沒講的留空並說它沒講。追問是輪次的事，
規則與例子是問出來才寫的。

## 前置確認（Ask user）

**唯一必要的輸入是需求本身**：一段描述，或一份文件的內容／路徑。

NEVER: 需求還沒拿到就自己想一個來跑。那會產出一份看似完整、實則憑空的
`spec.md`，而錯誤全藏在專業的格式底下。

Ask user: 這個 feature 的 slug（kebab-case，用來命名 `specs/<date>-<slug>/`）。
需求方沒有偏好就從原文的主詞取一個，講出來讓他改。

「存在就不重建」的唯一例外是 `clarify` 單獨模式留下的三節檔（只有 `## Document Overview`、
`## Open Questions`、`## 原文`，沒有 `## User Stories`）：那是一份還沒有開頭幾節的
`spec.md`，第 0 件事照樣要做，從它的 `## 原文` 補下面的第 2 到第 4 步，**不碰
`## Open Questions` 與 `## 原文`**——問答已經在那裡了，搬家只會弄丟 `Q-<n>`。

另一種半途：`spec.md` 有 story，但 `### 版本修訂歷史` 沒有「需求方確認建檔」那一列。
那是上一個 session 建完檔、需求方還沒點頭就結束了——從下面的「收尾」接著做，不重建。

## 建檔的四步，順序固定

### 1. 原文逐字進 `## 原文`

MUST: 這是第一個動作，不是收尾。需求方帶著文件來，整份貼進去；口述的，照講的記。
每一段加 `§<n>` 編號（原文自己有編號就沿用），這是之後每個 `← PRD §n` 指的東西。
需求方的檔案本身不搬、不改。

MUST NOT: 潤飾、補主詞、把「大概半小時」寫成「30 分鐘」。那個「大概」正是輪次
要問的題；改掉它，題目就消失了。

### 2. 從原文抽開頭幾節

照 `spec-format.md` 的順序填 `## Background`、`## Goal`、`## Scope — In / Out`、
`## Personas`、`## Assumptions / Constraints`、`## Success Metrics`。每一句行尾標
`← PRD §n`——這幾節在這一件事裡只能有兩種來源：原文（`PRD §n`），或第 3 件事那四題的
答案（`Q-<n>`）。出現 `推論` 就是你補了原文沒有的話。

原文抽不出來的節，保留標題、寫「原文沒提」。不要替它想一個。

`## Personas` 五欄照 `persona-definition.md`：原文有講的填，沒講的寫
「（無資料）」，**「他要什麼」與「現在什麼讓他痛」尤其不要編**。

`## Assumptions / Constraints`：原文裡標題叫「假設」或語氣像既定事實的數字、門檻、
SLA，都抄進來並標 `← PRD §n`——它們是**沒驗證過的**，開場掃描會逐條變成題。

### 3. 最多問四題，而且只在對應的節空著時問

| 節空著 | 問 |
| --- | --- |
| `## Background` | 這解決誰的什麼問題？現在怎麼做、哪裡痛？ |
| `## Personas` | 受影響的人與系統有誰？ |
| `## Goal` | 做成之後長怎樣？怎麼知道做成了？ |
| `## Scope — In / Out` | 什麼明確不做？ |

答案照講的記，行尾標 `← Q-<n>`，並在 `## Open Questions` 開對應的一列（狀態
`已答`、`面向` 填 `—`）。這四題是分析師開場會問的，不是十六個面向——後者是
輪次的事。

MUST NOT: 問第五題。問到第五題代表你已經在跑輪次；停下來，把它記成紅卡，
等需求方點頭之後再算前沿。

### 4. 粗切 story，底下留空

沿原文看得出的**使用者目標**切，一個目標一則：

```markdown
## User Stories

### US-1 · visitor-billing

身為 P-1（訪客），我想在出場前知道要付多少，以便付完就能開走 ← PRD §2

**切法**：暫定。沿原文 §2–§3 的訪客計費切；規則問出來之後可能重切。

#### FR

（空——規則在輪次問出來才寫）

#### NFR

（空）

#### Q

（空）
```

`### US-<n> · <slug>` 的形式與 `身為 P-<n>` 的要求見 `spec-format.md`——
slug 就是日後的 `.feature` 檔名，第一次就要是 kebab-case。

切不出來就只開一則，slug 用 feature 名。**標「暫定」**：這一刀是沿目標切的，沿規則
切要等輪次把規則問出來，那時 `story-splitting` 會重切。

MUST NOT: 替 story 填 FR 或 AC。你看到的只有原文，原文沒有規則；寫了就是編的，
`check_spec.py` 第 14 項會把沒有 `← Q-<n>` 或 `← PRD §n` 的規則抓出來。

## 收尾：需求方點頭才算建好

- `## Open Questions`：需求方自己列的「還不確定」每一條開一列，狀態 `待答`、`面向` `—`，
  小節寫 `**該問誰**`。原文裡的「假設」段**不**在這裡開題——那是開場掃描的工作，
  這裡只抄進 `## Assumptions / Constraints`
- `## Document Overview`：`**狀態**：澄清中　**最後更新**：<今天>　**結束方式**：—`；
  核心關係人表登記需求方自己與他點名的人，`決策權` 照他講的填，不知道就寫「（未問）」
- 把整份 `spec.md` 給需求方看一遍，改到他說「這是我的意思」為止。改的是開頭幾節的
  措辭，**不是 `## 原文`**
- 他點頭了，在 `### 版本修訂歷史` 記一列：版本 `0.1`、誰 `<需求方>`、改了什麼
  `需求方確認建檔`。**這一列是點頭的紀錄**——下一個 session 靠它分辨「建好了」和
  「建好了但他還沒看」

MUST: 這是**自己的一個回合**。需求方點頭之前不跑開場掃描、不算前沿——開頭幾節
沒經他確認就當成前提，第一輪問出來的題會建立在你的轉述上，而不是他的話上。

點頭之後告訴對方：粗切了幾則 story、切法為什麼是暫定、哪幾節原文沒提而留空、
`## Open Questions` 開了幾張紅卡（全部來自需求方自己列的）。然後進開場掃描。
