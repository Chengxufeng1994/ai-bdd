# red：建立失敗訊號

判定「這個紅燈有沒有資格驅動下一步」。讀這份的時機：進 `red` 入口之前。

| # | 強度 | 規則 | 違反的後果 |
| --- | --- | --- | --- |
| R1 | `MUST` | 動手前先講明：這一輪的 slice 是哪一個、用哪個窄範圍命令重跑 | 沒有目標的測試修改，紅了也不知道在驅動什麼 |
| R2 | `MUST` | 先**看到**對應這個 slice 的失敗，才算完成 red。骨架早就存在也要重跑一次確認 | 一寫就綠的場景沒有驗到任何東西——多半是步驟被別的場景定義過，而它的斷言沒抓到這個行為 |
| R3 | `MUST NOT` | 在 red 裡補產品行為。可以動的只有：step definition 骨架、fixture、斷言、讓測試跑得起來的最小通路 | red 變成事後驗證，不再是驅動入口 |
| R4 | `SHOULD` | 連續做幾個 slice 時，前一個紅燈穩定、來源清楚，才鋪下一個 | 一次六個 undefined step，每個失敗都失去辨識度 |
| R5 | `SHOULD` | 在起點就綠、或只紅在共同的接線失敗的 slice（斷言是 0、空、不變的「零值例子」；`Examples:` 表裡一開始就綠的那一列），轉綠後做一次**突變驗證**：暫時改壞它要驗的規則，看它變紅，再改回來 | 零值例子在空殼下天生就綠，它從來沒有因為自己的行為紅過，刪掉規則它照樣綠 |

## 什麼是「對的紅」

| 看到的失敗 | 算不算 |
| --- | --- |
| `step is undefined`——步驟還沒有定義 | 算。下一步是補骨架，再看一次它因為斷言而紅 |
| 斷言失敗：期望 30，得到 0 | 算。這是最好的紅——失敗訊息就是 green 的工作清單 |
| parse error、編譯錯誤、nil pointer | **不算**。先修到失敗落在這個 slice 的行為上 |
| 別的場景的失敗 | **不算**。重跑範圍太寬，或前一個 slice 沒收乾淨 |
| 每個場景都紅在同一個「路由不存在／404」 | 只證明**接線**還沒有，不證明這個 slice 的行為。接上路由之後再看一次它紅在哪；紅不起來的照 R5 做突變驗證 |

## R3：最小通路的界線

為了讓測試跑得到斷言，有時得先有一個空的型別或回傳零值的函式。判準：**這段程式的目的
是露出更真實的失敗，還是讓功能差一點就做好？**

```
可以：  func FeeFor(stay time.Duration) int { return 0 }     ← 讓斷言跑得到，然後紅在「期望 30，得到 0」
不可以：func FeeFor(stay time.Duration) int { 分段計費的實作 } ← 這是 green 的工作
```

red 的完成條件是「失敗訊號清楚」，不是「功能快做好了」。
