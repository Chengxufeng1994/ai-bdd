# DISCOVERY — 把需求問到完整，只記問答

| | |
| --- | --- |
| **職責** | 把一段需求（想法或別人寫的 PRD）收成逐字原文與粗切 story，再一輪輪問到前沿空了，每個答案逐題記下 |
| **讀** | 需求本身（描述、文件內容或路徑），或狀態 `澄清中` 的 `specs/ongoing/<date>-<feature>/discovery.md`；續跑時加同目錄 `spec.md` 的 `## 回 DISCOVERY 補問` |
| **寫** | `specs/ongoing/<date>-<feature>/discovery.md`（`澄清中` → `已收斂`） |
| **上游** | 無（可單獨使用）；`spec` 把它退回 `澄清中` 時再跑 |
| **下游** | `spec`（從這份紀錄寫 `spec.md`） |
| **不做** | 不寫 FR／AC／Gherkin／規則草稿、不自己填答案、不改寫 `## 原文`、不寫 `spec.md`／`plan.md`／`.feature` |

**把需求攤成一棵設計樹。** 每個決定都會岔出依賴它的下一批決定。**前沿**是所有
**前提已經定案**的決定——現在就問得出口、不必先猜任何還沒聽到的答案的那些題。
一輪問完整個前沿，等答案，重算，再問下一輪。**前沿空了就結束**：每一條分支都
走過，沒有東西被默默假設——每個答案記在 `## Open Questions` 並指得出是誰答的、『待答』零列。

**不寫規格。** 不寫 FR／AC、不寫 Gherkin、不談實作、不設計資料表——這一步只問、只記。
**不自己填答案**：`spec` 之後寫的每一條 FR 與 AC 都要指回這裡——`## 原文` 的某一段，
或某一題已答的紅卡；所以這裡記下的每一題都要有答案原話與 `**誰答的**`。

## 使用時機

- 有一個想法、或一份別人寫的 PRD／ticket／會議紀錄，要收進流程問到完整——找出原文沒寫、但整份預設成立的假設
- 拿到一段需求或一則 story，但講得太抽象，不知道要做到什麼程度
- 需要判斷這則 story 該不該進 sprint
- 準備寫規格或 `.feature` 檔之前，先確認例子夠不夠
- 懷疑需求有沒想到的邊界情況

## Skill Boundaries

| 情況 | 改用 |
| --- | --- |
| 只是要把一則太大的 story 切開 | `story-splitting`；本 skill 只改 `## 粗切 story` |
| 已經有一疊跳過的紅卡要逐題收斂 | `clarify`，本 skill 在對方一次跳過多題時呼叫它 |
| 要把答案寫成 FR／AC | `spec` |
| 要判就緒、攤四色卡 | `spec`，它寫完 `spec.md` 後呼叫 `example-mapping` |
| 要寫 seam、API、schema、測試層級 | `plan`（`spec.md` 已對焦、`.feature` 寫好之後） |

產出是 `discovery.md`，**不是** `spec.md`、`plan.md`、`.feature`、程式碼或資料模型。

## 參考檔案

- `references/opening.md` — 第 0 件事（建檔）的做法、四題的表、粗切樣板。**建檔時讀**
- `references/discovery-format.md` — `discovery.md` 的骨架、欄位、`面向` 的值域。**寫檔之前讀**
- `references/persona-definition.md` — 角色五欄的判準、寫法與範例。識別角色、或冒出新角色時讀
- `references/technical-probes.md` — 五個技術面向各問什麼、自己查還是問人。前沿碰到技術面向時讀
- `references/stand-in-mode.md` — 需求方不在場時怎麼代演。只在代演時讀
- `scripts/status.py` — 從 `## Open Questions` 算紅卡與面向覆蓋。收尾核對時跑

## 前置確認（Ask user）

**唯一必要的輸入是需求本身**：一段描述、一份文件的內容或路徑，或已經存在的
`specs/ongoing/<date>-<feature>/discovery.md`。沒有 `discovery.md`、或只有 `clarify` 留下的三節
（沒有 `## 粗切 story`），就先建（開場的第 0 件事，`references/opening.md`）；
建好的，它要有 `## 原文` 一節、`## 粗切 story` 至少一則、狀態 `澄清中`，而且
`### 版本修訂歷史` 有「需求方確認建檔」那一列——沒有就是他還沒點頭，第 0 件事從收尾接著做。
狀態 `已收斂` 的檔只在回頭清單裡有**還沒開過題**的條目時續跑（見〈續跑〉）。

NEVER: 還沒把原文逐字寫進 `## 原文` 就開始問。問出來的答案沒有地方寫、`← Q-<n>` 沒有
表可以指、`← PRD §x` 沒有話可以指，整場訪談會留在對話裡然後消失。

產物路徑不必問，就是那份 `discovery.md`；建檔時只問 feature 的 slug。

### 喚醒——要改的 feature 已經在 `specs/sleeping/`

做完的 feature 整個目錄住在 `specs/sleeping/<date>-<feature>/`。這次的需求是要**改它的 FR／AC**
（規則改了、交付有錯、加一條例外）時，不開新目錄，把它搬回來；這次的需求是**新的 story**、只是碰到
同一批程式碼時，照常開新的 `specs/ongoing/<date>-<feature>/`。

Ask user: 要不要喚醒 `<date>-<feature>`。搬回來是使用者的決定——不是本 skill 判斷「這個該改」。

| 回答 | 怎麼做 |
| --- | --- |
| 要 | `mkdir -p specs/ongoing && git mv specs/sleeping/<date>-<feature> specs/ongoing/<date>-<feature>`（目錄名不改：日期是它開始的日子；全部歸檔後 git 不留空的 `specs/ongoing/`，所以先建）；`discovery.md` 狀態改回 `澄清中`、`### 版本修訂歷史` 記一列「喚醒：<為什麼>」；這次要改什麼開成新題，小節的 `**來自**` 寫「喚醒 —「<需求方的原話，逐字>」」——`## 原文` 照舊不改；然後照〈續跑〉問 |
| 不要 | 開新的 feature 目錄，照常建檔 |

喚醒之後全部走現成的再跑規則：`spec` 修補（編號不重排）、`formulation`〈再跑：`spec.md` 改過之後〉、
`plan` 重寫被規格推翻的 Risks 與接合點、`task-breakdown` 重切（有勾的舊票不動）、`implement` 做新票。做完由 `archive` 再寫一次現況、搬回 `specs/sleeping/`。
「上一次交付了什麼」看搬回來那個 commit 的 `spec.md`（`git show <commit>:<路徑>`）。

### 代演模式——需求方不在場時

benchmark 實跑或離線試跑、沒有人可以答時，可以**代演**需求方與開發者，但每一個代演的
答案都要在檔案上看得出來（`**誰答的**` 寫 `代演（需求方）`／`代演（開發者）`）。登記方式、
推到 `已對焦` 的條件、實跑報告 → `references/stand-in-mode.md`。

## 流程

| 步驟 | 做什麼 | 要問使用者嗎 |
| --- | --- | --- |
| 0 | 建檔：原文逐字、粗切 story、最多四題、改到需求方點頭（只做一次，見〈開場：只做一次的四件事〉） | 要，給需求方看整份 |
| 1 | 開場其餘三件：掃原文找隱含假設、補核心關係人、識別角色——問出來的都開成『待答』題 | —（跟著輪次問） |
| 2 | 算前沿，過〈值不值得問〉；能自己查的事實派 sub-agent 查 | — |
| 3 | 一次問完整個前沿，編號，每題附建議答案（〈一題長什麼樣〉） | 要 |
| 4 | 答案回來：四件事一起記、確認夠具體、看停下來的訊號 → 回到 2 | — |
| 5 | 前沿空了：收尾核對，狀態翻 `已收斂`，交 `spec`（〈結束：前沿空了〉） | — |

續跑時開場已經做過，從步驟 2 接著做；有回頭清單就先開成新題。不論停在哪一步，結束方式
四選一（收斂／阻塞／零進展／喊停）寫在 `## Document Overview`（見〈完成後〉）。

### 續跑

| 呼叫方式 | 範圍 |
| --- | --- |
| `discovery` | **預設：所有狀態是 `澄清中` 的 `discovery.md`**——開場剛建好的、問到一半的、被 `spec` 退回來的都算 |
| `discovery <feature>` | 只跑指定的那一個 |

**不要問對方要跑哪一個。** 預設全部，想限定的人自己會帶參數——多問一次等於把
決定推回去，而多數時候答案就是「都繼續」。

**開場做過沒有，看 `## Open Questions` 有沒有任何一列的 `面向` 不是 `—`。** 第 0 件事只會
寫 `面向` 為 `—` 的列（它的四題與需求方自己列的開放問題），第一輪前沿一算就會冒出帶
面向的題——一列都沒有就是開場還沒跑。有，就只讀不重跑，並且**用它重建設計樹**：『已答』的每一列是一個已定案的
決定，『待答』是還開著的分支，『n/a』是走過但判定不適用的。前沿從這三種列算得出來。

**回頭清單先開成題。** 同目錄 `spec.md` 的 `## Open Questions` 有條目時（那是要送回來問的洞，不是這份檔的問答表），續跑的第一件事是把每一條**還沒開過題**的開成一題
『待答』，然後照常算前沿。

**判斷開過沒有靠 `**來自**` 這一行。** 開題時小節寫
`**來自**：補問 —「<那一條的原文，逐字>」`。只引原文，不寫它在哪份檔、哪一節——這份檔只記問答，
不必知道下游的格式。
續跑時，一條回頭清單的文字若已經被某一題的 `**來自**` 逐字引過，就是開過了——不論那題
是待答還是已答，都不再開。這份清單由 `spec` 在再跑時清掉答過的條目；
清掉之前它還在檔上，沒有這個比對就會一題問兩次。
這是 `spec` 把 `discovery.md` 改回 `澄清中` 的原因——不讀這份，退回來
的洞就沒有人問。`plan` 發現的需求洞也走這條路：它交回 `spec`，由 `spec` 寫進補問清單。

IMPORTANT: 重問一題已經答過的，比漏問一題更傷信任——它證明你沒有讀既有產物。

換 feature 時明講「現在開始 X」，並在每一輪結束回報還剩幾個。跑多個 feature 時，
**跨 feature 的共用規則會浮現**——那是一次跑完全部的主要收穫，單獨跑一個看不到。

### 開場：只做一次的四件事

#### 0. 建檔（`discovery.md` 不存在、或還沒有粗切 story 時）

原文逐字進 `## 原文`、沿使用者目標粗切 story（一句一則）、背景／角色／目標／範圍原文
沒講的最多問四題（答案記成 `面向` 為 `—` 的 `Q-<n>`）、需求方自己列的開放問題開成紅卡
——然後**把整份給需求方看一遍，改到他說「這是我的意思」**，點頭記成
`### 版本修訂歷史` 的一列「需求方確認建檔」。這是自己的一個回合：他點頭之前不掃描、
不算前沿；續跑時沒有那一列就回到收尾。做法、四題的表、粗切的樣板 →
`references/opening.md`；檔案格式 → `references/discovery-format.md`。

MUST NOT: 在這一件事裡寫 FR、AC、或任何規則。原文沒有規則；寫了就是編的。

#### 掃原文找隱含假設

第 0 件事是書記，收原文的時候不質疑。這一步對 `## 原文` 逐句質疑，問出來的題開進
`## Open Questions`，`面向` 欄填 `—`（它們不屬於十六個面向）。

MUST: 原文裡標題叫「假設」、或語氣像既定事實的數字、門檻、SLA，**每一條都當成沒問過**
——它是未驗證的斷言，不是前提。每一條開一題進『待答』，小節註明是原文哪一段
（`§n`）。`spec` 寫 `## Assumptions / Constraints` 時，問過的引 `← Q-<n>`，
沒問過的才引 `← PRD §n`。

**找隱含假設要靠機械掃描，不是靠讀。** 假設對寫的人而言是常識，常識不會被
寫下來。對 `## 原文` 裡的每一個元素問同一句話：

| 掃什麼 | 問什麼 | 逮到的是 |
| --- | --- | --- |
| 每個**名詞** | 這是誰定義的？兩個人會不會算出不同的數？ | 沒定義的業務術語 |
| 每個**數字** | 這個數字從哪來？換成別的會怎樣？ | 拍腦袋的門檻與 SLA |
| 每個**「自動」「即時」「應該」** | 誰做？什麼時候做？沒做成怎麼辦？ | 沒列出來的 actor（多半是系統自己） |
| 每個**成功指標** | 這個指標要成立，哪些行為必須存在？PRD 有寫嗎？ | 指標與功能之間缺的那一段 |
| 每個**排除項** | 排除 A 是不是隱含要做 B？ | 被排除項推出來的隱藏需求 |

#### 補核心關係人

第 0 件事登記了需求方與他點名的人。這一步每冒出一個新的受訪者就在 `discovery.md`
`## Document Overview` 的 `### 核心關係人` 表補一列，三欄 `關係人／負責什麼／決策權`。
『待答』題的 `該問誰` 只能指向這張表裡的人——指到表外就補一列，不要當筆誤略過。

**`決策權` 這一格只有這裡寫得出來。** `spec` 不訪談，它把整張表
原樣抄進 `spec.md`；這裡沒登記，它們就分不出哪些答案是定案、哪些只是提案。

#### 識別角色

規則的敘述（EARS 的 `When <trigger>`）常常以角色當主詞，角色名稱不統一，
同一題會被問兩次、同一條規則會被記成兩種主詞，所以在深度追問前先定下來。

MUST: 每個角色問**是誰**／**怎麼取得這個身分**／**跟誰容易混**／**他要什麼**／
**現在什麼讓他痛**，每個角色一題、五欄的答案原話記在那題的小節；最後兩項答不出來就記
「（無資料）」，不要編。`spec` 從這些小節寫 `spec.md` 的 `## Personas`。判準、寫法與
範例、別漏掉哪些角色 → `references/persona-definition.md`。

## 前沿怎麼算

### 設計樹

每個已定案的決定會岔出依賴它的下一批決定。**前沿 ＝ 所有前提已經定案的決定。**

判準只有一句：**這題的答案，會不會因為另一題還沒答而改變？** 會，它屬於**後面**
的輪次，不是這一輪。

前沿是**算**出來的，不是猜哪些題該先問。範圍題之所以先問，不是因為有人規定，是因為
其他幾乎所有題的前提都掛在它身上。

MUST NOT: 因為某題「感覺比較重要」就把它拉進這一輪。重要不等於前提已定案；
拉進來的結果是你拿到一個建立在還沒問到的答案上的回答。

### 十六個面向是前沿的檢查表

11 個業務面向（下面兩張表）與 5 個技術面向（seam、模組邊界、介面與型別契約、
排序契約／決定性、既有資產／測試慣例）不再是三趟掃描，而是**每輪算前沿時的
檢查表**：

> 對每一個**已經定案**的決定問——這 16 個面向裡，有哪個還沒對它問過？

問得出來的就是這一輪前沿的題。技術面向多一條：**能自己查的先查**（見下一節），
每個面向各自問什麼 → `references/technical-probes.md`。

**追問清單**（找模糊點用，不是待辦清單）

| 面向 | 問法 |
| --- | --- |
| 空與零 | 沒有資料、空字串、零筆、第一次使用時？ |
| 邊界 | 剛好等於上限？超過 1 個單位？ |
| 重複 | 同一個動作做兩次？重送？**同一個人把整個流程再走一遍**（出去再進來、退了再買）？ |
| 時序 | 兩件事同時發生？順序顛倒？ |
| 權限 | 換一個角色來做？沒登入？ |
| 失敗 | 外部系統掛掉？逾時？做到一半斷線？**每一種身分憑證各自遺失、讀不到、不在名單時**？ |
| 時間 | 跨日、跨時區、日光節約？過期的定義？ |
| 規模 | 一次一萬筆？ |

**非功能面向**（行為級的那些）

| 面向 | 問法 |
| --- | --- |
| 降級 | 依賴不可用時**降級成什麼**？還是整個失敗？ |
| 時限 | 多久算太久？超過了怎麼辦——等、失敗、還是給舊資料？ |
| 可觀測 | 這件事出錯時怎麼會知道？留下什麼才查得出原因？ |

這三個跟上表的「失敗」不重複：**失敗問的是會不會壞，降級問的是壞了之後呢。**
兩者是不同的規則，只問前者的結果是規格寫了一半——寫了偵測，沒寫善後。
舉不出例子的產品級品質屬性（「所有操作三秒內」）由技術面向那五個接手，
不會在這裡重複。

清單是起點不是全部——這個領域有什麼特有的失敗模式，一併找。

面向名稱與順序是 `scripts/status.py` 的 `DIMS` 與
`references/technical-probes.md` 的共用契約，**不得增減或改名**。每一題的
`面向` 欄照樣填——`status.py` 的追問覆蓋率完全靠那一欄，而它是這個 repo 裡
唯一看得出「有沒有真的問過邊界」的東西。

### 值不值得問

MUST: 前沿算完、問出口之前先過這一關——**這題的不同答案，會不會導致不同的規則？**

不會，就不要問。這條篩掉的通常是最多的：十六個面向對每個已定案的決定掃一遍，
掃出來的候選有一大半的答案其實不影響任何行為。**問題少而準，比多而全有用得多**
——三十個平等攤著的問題，人的反應是一個都不動。

**這一關刪題，不是把題排到後面的輪次。**〈設計樹〉答的是「哪一輪問」，判準是前提
定沒定案；這一關答的是「問不問」。少了它，前沿就只是一張把候選全部攤平的清單
——五個已定案的決定乘十六個面向，一次送出四十幾題，正好是上一段那個沒有人動得了
的場面。

篩掉的不會消失：跟〈跳過：要記為什麼跳〉的「這題不該問」走同一條路，在 `## Open Questions` 記一列、狀態 `n/a`、
寫清楚為什麼不用問。不記，收尾核對時那個面向會找不到任何一列。

### 能自己查的事實不准問使用者

MUST: 前沿問題需要的**事實**若在環境裡查得到——既有測試怎麼寫、某個模組的介面
長怎樣、有沒有現成的 seam——**派 sub-agent 去查**，不要問使用者。
哪些事實查得到、哪些是只有人能給的決定 → `references/technical-probes.md`
每一節的 **`自己查還是問人`** 那一段。

MUST NOT: 因為 sub-agent 還在跑就停下來。**一個進行中的探查是一個未定案的前提**
——只有依賴它的問題要等，**前沿其餘的照問**。

**決定是使用者的，事實是你的。** 把事實問題丟回去，等於要對方做你做得到的功課，
而且他的答案未必比環境裡的真相準。

## 一題長什麼樣

格式固定，一輪裡每題都這樣：

```
❓ **Q1** - **<問題標題>**：<問題本體，可以多段，可以含選項>

➡️ <你的建議答案>
```

編號讓對方可以只回「Q2 選第二個、Q3 你的建議可以」，不必重述題目。

**建議欄是逃生口，不是裝飾。** 一個沒有建議的問題把全部認知負擔丟回去；一個
有建議的問題只要求對方判斷「對不對」。

MUST: **沒有站得住的預設時，建議欄要寫「這題我不建議猜——要去問 <誰>」**，
`<誰>` 指向 `### 核心關係人` 表裡的人。編一個聽起來合理的建議，比承認不知道更糟
——對方多半會直接接受，而那個答案從此看起來像是問過的。

一輪問完整個前沿。**不要一次只問一題**——前沿上的題彼此沒有依賴，分開問只是
多幾趟來回，而每一趟來回都是對方重新載入上下文的成本。

## 一輪的答案回來之後

### 記錄：四件事一起做

MUST: 一輪的答案回來，以下四件事跟著發生，缺一個就是不一致狀態：

| # | 動作 |
| --- | --- |
| 1 | 每一題答定的，`## Open Questions` 那一列狀態 `待答` → `已答`、答案欄填上結論；小節補 `**誰答的**` 與**答案原話** |
| 2 | 答案帶出具體例子的（「停 29 分收 0 元」），例子原樣記進小節——`spec` 寫 AC 時要找得到它，不能從一句結論重建 |
| 3 | 若某個答案消掉了其他還沒問的問題，說出來並跳過它們 |
| 4 | 使用者對你的建議答案回「都不是」時，把那個提案連同正確答案記進該題的小節（決策史） |

欄位長什麼樣 → `references/discovery-format.md`。

**當場記，不要事後補。** 剛答完那一刻你還記得對方的原話與例子；隔了二十題再回來寫，
會寫成「大致上是這個意思」的版本，而 `spec` 會把那個版本當成定案寫成規則。澄清很少
一次做完，**停在任何一輪，`discovery.md` 都該是完整可用的**——session 斷了，下一次從它接著問。

MUST NOT: 在這一步寫 FR、AC，或把答案「先整理成規則草稿」放進任何檔案。規則只在
`spec` 寫，那裡才有 `check_spec.py` 第 14 項機械地查每一條的來源。

編號：`Q-<n>` 全域唯一且**不重排**。

### 跳過：要記為什麼跳

留在 `## Open Questions`，狀態 `待答`、答案欄 `—`，小節記下**跳過的原因**。有用的
區分只有一個：**還會不會再問**。

| 原因 | 後續 |
| --- | --- |
| 之後再問 | 下一輪重問，`clarify` 會接手 |
| **這題不該問** | 回頭確認它真的不影響任何行為。是 → 狀態改 `n/a`，答案欄寫清楚為什麼不用問 |

只記「跳過」不記原因，`discovery.md` 的紅卡就會變成一堆分不出輕重的待辦——而那
正是讓人一個都不想動的狀態。

### 確認答案夠具體

MUST: 一輪問完就檢查這一輪的答案是不是還停在抽象層次，不要累積到最後。

一個答案在對話裡聽起來很明確，一旦要照著做事就會發現它缺條件——等全部答完
才發現，那些漏洞會一次湧出來，而且上下文已經冷了。

**答案要具體、含實際資料，不要只是換句話說：**

- ✗「一個無效的使用者」—— 這只是換句話說
- ✓「一個 token 在 3 秒前過期的使用者」

答案不夠具體，回頭追問一題，不要就這樣記下模糊的版本——**模糊的答案比誠實的
「待答」更危險**，它看起來已經解決了。在前沿上它還更貴：一個糊的答案照樣被當成
定案，掛在它底下的一整批題會在下一輪被算進前沿，而那些題的前提其實還是糊的。

### 停下來的訊號

**前沿空了**是唯一的正常結束。以下四個訊號代表這一輪問不動了，出現就停下來講，
不要繼續往下問——四種結束方式怎麼寫見「完成後」：

| 訊號 | 意義 | 結束方式 |
| --- | --- | --- |
| **連續兩題被跳過** | 可能問錯層次，或整組問題超出對方的知識範圍。停下來確認 | 阻塞 |
| 剩下的都被標成「之後再問」 | 前沿非空，但這一輪沒有人答得出來 | 阻塞 |
| 問了兩三輪但前沿不縮 | 先確認範圍有沒有抓錯：**沒抓錯**——這個 feature 本來就大，不是切小它，繼續問完，多大交給 SPEC 之後決定；**抓錯了**——**開一題新的，重問那條邊界**，記進『待答』，下一輪照樣算前沿 | 零進展 |
| **答案沒有改變任何行為** | 這一輪問出來的都不影響系統怎麼做。問題選錯了，回頭看〈值不值得問〉那一關 | 零進展 |

**沒有「把答案收回去」這個動作。** `## Open Questions` 的列是單向的：『已答』的一列
記的是**當時問了什麼、答了什麼**，那件事確實發生過。定錯的邊界靠**新開一題**取代，
舊那一列留著不動，新那一題的小節寫「取代 Q-<舊>」；`spec` 再跑時把引用舊題的規則
改引新題。`Q-<n>` 全域唯一且不重排，整份 `discovery.md` 因此讀得出是哪一輪改了主意。

這不牴觸「重問一題已經答過的，比漏問一題更傷信任」——那條講的是**沒讀既有產物**就
重問。這裡是帶著理由回去重問，理由寫進新那一列的問題欄，對方看得出你為什麼再問一次。

「一輪下來沒有新問題」不是訊號——那就是**前沿空了**，正常結束。

## 結束：前沿空了

**前沿空了之後**：

1. **核對覆蓋**：跑 `python3 scripts/status.py <專案根>`。十一個業務面向每一個都至少
   出現在某一列的 `面向` 欄——包含標 `n/a` 的。技術那五個一樣各印一欄，但這一關
   不擋它們（理由見 `references/technical-probes.md` 開頭）
2. **核對角色**：`## 粗切 story` 每則的 `身為` 都有一題問過那個角色的五欄
3. **核對優先級**：`## 粗切 story` 有兩則以上時，有一題問過「哪則最重要、只做它能不能先上線」——
   答案是每則的 P1／P2／P3 與為什麼。沒問過就開這一題，這一輪還沒結束。`spec` 照它排 story 的優先級，
   `plan` 與 `task-breakdown` 照它排切片順序；沒有這一題，優先級只能由寫規格的人自己排
4. **稽核分類是否窮盡**（見下）
5. **狀態翻成 `已收斂`**：`## Document Overview` 的 `狀態` 由 `澄清中` 改 `已收斂`，
   `結束方式` 寫 `收斂`。這是本 skill 唯一寫狀態的時刻
6. **交給 `spec`**：它從這份紀錄寫 `spec.md`，並做只有寫出 FR 之後才做得了的檢查
   （角色是否都被規則用到、一則 story 是否混了命令與查詢、每條規則有沒有來源）

核對不能跳過——它是「面向要嘛問過要嘛標 n/a」那條規則的驗收。若某個面向連
一列都沒有，代表它根本沒被想過，**先補一題**再往下走。

### 稽核分類是否窮盡

MUST: 問答裡浮現的每一張**列舉型的表**（型別、狀態、角色、單位，**以及實體本身的種類**——車種、票種、卡種）拿出來問一次：
**這個領域裡有沒有一種真實存在的東西，這張表放不進去？**

追問清單的十一個面向問的都是**已知那件事的極端值**——空、邊界、重複、時序。問不到
**漏掉一整類資料**，因為漏掉的那類從來沒出現在對話裡，沒有極端值可問。

實測過一次：健身 App 的動作型別表有六種，全部以「次數」計量，於是棒式（60 秒，
沒有次數）無處可放，被迫和跑步機歸成同一類。三輪澄清都沒問到，是抽完規則後回頭
對照才發現的。

找到放不進去的東西，就開一題新的，記進 `## Open Questions`——不要自己塞進最接近的那一格。

### 決策史住在 `## Open Questions` 的小節

`spec` 把答案寫成規則之後，**為什麼**仍留在規則的 `← Q-<n>` 指向的那題小節裡：問了誰、
答案怎麼來的、被推翻過的提案。下次改動第一個會問的問題往往是「當初為什麼不選
第二個選項」，答案只在那裡找得到。

IMPORTANT: 小節不是規則的定案來源——規則以 `spec.md` story 底下那一行為準；小節留著的是
**答案原話與為什麼**。
