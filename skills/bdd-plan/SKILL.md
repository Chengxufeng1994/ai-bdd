# PLAN — SPEC 說做成什麼樣，PLAN 說怎麼做出來

一批已就緒的 `.feature` 進來，出去的是 `plan.md`：**要建哪些 API、哪些型別、
哪些資料表，每個場景怎麼驗，先做哪一個**，外加一張推不出來的清單。

不寫程式。不寫 `openapi.yaml`、不寫 migration——那是 IMPLEMENT 的事。

## 使用時機

- `.feature` 寫完了，要決定先做哪一個、怎麼做
- 想知道這批情境會長出哪些 API、型別、資料表
- 要決定哪些情境需要真的資料庫

## Skill Boundaries

- 規則還沒定案 → 回 `bdd-clarify`；還沒有 `.feature` → 先跑 `bdd-spec`
- 要實際寫 step definition 與產品程式碼 → 改用 `bdd-implement`
- 產出是 `plan.md`，**不是** `openapi.yaml`、migration 或任何可執行的檔案

---

## 只翻譯，不設計

MUST NOT: 發明規格裡沒有的端點、型別、欄位或資料表。

`.feature` 裡已經有設計了。`bdd-spec` 的封閉文法讓它可以機械抽取：

| `.feature` 裡的 | 翻譯成 |
| --- | --- |
| `@command` / `@query` | 改不改變世界 → 動詞與冪等性 |
| `Feature:` ＋ `When` 的動作 | 一個 API 操作 |
| `Background` 的播種表 | 實體與欄位 → domain 型別 ＋ schema |
| `前置（參數）` 規則 | request 的驗證約束 |
| `後置（回應）` 的斷言表 | response 的形狀 |
| `後置（狀態）` 規則 | 什麼必須被持久化 |
| 步驟樣板 | step definition 的清單（IMPLEMENT 的工作量） |

判準：**指著這個型別／欄位／端點，說得出它來自哪一條 Rule 或哪個 Example 嗎？**
說不出來就是缺口，寫進第 6 節，不要放進草圖。

這裡的誘惑比 `bdd-spec` 大——缺一個 `created_at` 看起來只是「顯然需要」。
但「顯然」的欄位正是沒有人討論過的欄位。

## 流程

### 1. 讀

範圍預設是**所有標 `@ready` 的 `.feature`**，`bdd-plan <feature>` 才限定。
`@draft` 的跳過並說明——替未定案的規格排順序，等於把不確定性變成一張看起來
可以開工的清單。

**一次讀完全部，不要一個一個規劃。** 跨 feature 的共用型別與端點衝突只有並排時
才看得見；分次規劃會各自長出一份，然後在 IMPLEMENT 才發現它們不一樣。

一併讀 `example-mapping.md`（規則編號，溯源要指得到）、`glossary.md`
（命名跟它一致，不要自創同義詞）與 `actor.md`（權限模型：誰能呼叫哪個端點，
以及那個身分怎麼取得——「怎麼取得」通常對應一個還沒被列出來的操作）。專案已有 `openapi.yaml` 或既有型別時也要讀——
計畫說的是「要**新增**什麼」。

### 2. 翻譯成結構

三樣東西一起做，因為它們讀的是同一批 `.feature`。

**API**：一個 `Feature:` 一個操作。`@command` → POST／PUT／DELETE，
`@query` → GET。`後置（回應）` 的斷言表逐欄變成 response 欄位；
多個規則各自斷言不同欄位時，回應是它們的**聯集**——那是唯一看得出完整回應的地方。

**Domain 元件**分三種，判準是**這條規則的邏輯屬於誰**：

| 元件 | 什麼時候是它 |
| --- | --- |
| **Entity／聚合** | 規則只用到一個實體自己的狀態 |
| **Domain Service** | 規則橫跨多個聚合，或不屬於任何一個 |
| **外部依賴（port/out）** | 規則需要系統自己給不出來的東西 |

`Background` 的播種表是實體清單，但播種表 ≠ domain 型別：只在斷言裡出現的欄位
（`旅程名稱`）是 read model 的投影，不是聚合的狀態。行為來自 `後置（狀態）` 規則。

**外部依賴最容易漏，但它們在 `.feature` 裡有明確的痕跡**：

| 場景裡出現 | 需要的 port |
| --- | --- |
| 具體日期、`當地時區`、`逾時` | 時鐘。**不可以直接呼叫 `time.Now()`**——那樣的場景不可能穩定 |
| 播種表有 ID 欄、`應為 UUID 格式` | ID 產生器 |
| `應寄出`、`應通知`、金流、回呼 | 對應的外部服務 |
| `第 N 頁`、`每頁 20 筆` | 分頁只是查詢參數，不是外部依賴 |

判準：**這個場景要能重跑一百次都一樣，有什麼東西必須被固定住？** 那就是一個 port。

**Schema**：判準是**跨兩次使用者操作之間，什麼必須還在**。場景之間不共享狀態，
但真實使用者的兩次操作之間要——那才是資料庫存在的理由。
全是 `@query`、沒有任何 `後置（狀態）` 規則時，就寫「這批情境還不需要資料庫」
並列理由。**提早建表是最容易被當成進度的浪費。**

### 3. 每個 Example 怎麼驗

`.feature` 的每個場景本身就是驗收測試，這一步決定它**底下**要什麼。

MUST: 一個**場景區塊**一行——`Example` 一個、`Scenario Outline` 也一個
（它的各列共用同一個內迴圈，所以編號寫成範圍）。

粗到「一條 Rule 一行」就看不出哪個場景需要內迴圈，而那正是這張表存在的理由。

| 場景 | 內迴圈（unit） | 需要資料庫 |
| --- | --- | --- |
| 2.1 進度不可倒退 | 單調遞增判斷 | ✗ |
| 3.1–3.3 值域內可更新（Outline） | 值域驗證 | ✗ |
| 6.1 查詢回傳完整內容 | — | ✓ |

**「需要資料庫」的判準**：這個場景要驗的行為**本身是否跨越一次操作的邊界**——
前一次操作寫進去的東西，要被這一次讀出來。是 → `✓`；否 → in-memory adapter 就夠。

不是「有沒有資料要存」。每個場景都有資料要存，但多數場景在同一次操作內就驗完了，
換成 in-memory 也一樣紅、一樣綠——那種場景掛上資料庫只是讓測試變慢。

`—` 代表沒有內迴圈（純轉發、純投影），那是正常的。
一個場景掛五個以上內層測試則是訊號：那條規則的邏輯可能該獨立成一個 domain 概念。

### 4. 技術風險

MUST: 列出**規格沒說、但實作一定會撞到**的東西，每一條指出它從哪條規則長出來。

這一節跟第 5 節的缺口不同：缺口是**還不知道要做什麼**，風險是**知道要做什麼，
但做對很難**。它們的處置也不同——缺口回 CLARIFY 問人，風險在 IMPLEMENT 解決，
但**現在就要知道**，因為它會改變實作順序與分層。

三種最常見的，都從規則直接讀得出來：

| 訊號 | 風險 | 為什麼現在就要知道 |
| --- | --- | --- |
| 規則含「唯一」「最多一筆」「不可重複」 | **併發寫入**。兩個請求同時通過檢查 | 決定要不要 DB 唯一索引／行鎖／樂觀鎖，那會改 schema |
| 同一個動作做兩次的規則（`不可重複交付`） | **冪等性**。重送、逾時重試 | 決定要不要冪等鍵，那會改 API |
| 一個動作改動多個聚合（`重算 36 筆訓練`） | **交易邊界**。跟「一個命令一個聚合」的分層原則衝突 | 決定同步重算還是事件驅動，那會改整個分層 |

SHOULD NOT: 把「用 Redis 還是 DB 行鎖」寫死在這裡。**風險要指出來，解法留給
IMPLEMENT**——選型需要知道實際的流量與既有基礎設施，而那些不在 `.feature` 裡。

寫成「這裡有併發風險，因為 Rule 1 要求最多一筆進行中；DB 唯一索引與應用層鎖
都可以，看部署形態」比寫「用 Redis」有用：後者看起來是決定，實際上是猜的。

### 5. 排順序

**① 走骨架先行。** 第一個要綠的是**最薄的完整路徑**——碰到每一層，邏輯最少。
它證明的是接線，不是行為。專案已經有骨架就跳過。

**② 垂直切片，不依技術層。**

MUST NOT: 排成「先做完所有 domain 型別 → 再做所有 repository → 再做所有 handler」。

水平切法的問題不是慢，是**每一層做完都無法驗證**——三層都做完才有第一個綠燈，
而那時錯誤已經疊了三層。垂直是「一個場景從 handler 到 domain 到 repository
全部做完，綠了，再下一個」。

**③ 同層內依「解鎖多少」排。** 判準：**哪一個綠了之後，最多其他場景變得容易？**
建立類的操作通常排在查詢之前——不是因為比較重要，而是查詢的測試需要有東西可查。

```
1. @example-2.1 進度不可倒退
   內迴圈：單調遞增判斷（unit）
   解鎖：2.2、2.3
   資料庫：不需要
```

第一項要說明**為什麼是它**。

### 6. 回報推不出來的

MUST: 分兩類——差別是**誰能回答**。

| 種類 | 例子 | 處置 |
| --- | --- | --- |
| **規格沒講** | 狀態列舉不全、`進度` 是整數還是小數 | 回 `bdd-clarify` 補問 |
| **技術決定** | 錯誤格式、分頁用 offset 還是 cursor | 留給 IMPLEMENT，但要列出來 |

混在一起，第一種會被當成第二種「順手決定掉」——那正是規格失效的方式。

## 產物

**一批一份** `docs/bdd/plan.md`，不是一個 feature 一份。

這一步讀的是全部 `@ready` 的 `.feature`，產出的東西也多半是跨 feature 的：
共用型別、端點衝突、實作順序——**順序尤其是排序關係，拆進五份檔案之後就不存在了**。

拆成「每 feature 一份 ＋ 一份共用」試過，會壞成兩種：共用檔把實質內容吸走
（各 feature 的 schema 一節全退化成「見共用檔」），而兩種檔案各用一套節號，
意思只對得上一半——**部分對齊比完全不對齊更危險**，讀的人會假設對齊。

完整骨架照抄 → `references/plan-format.md`。

MUST: 只寫入 `docs/bdd/`，**不修改專案既有的任何檔案**。
`openapi.yaml` 與 migration 由 IMPLEMENT 依這份計畫寫。

SHOULD: 空的節保留標題並寫**為什麼空**。刪掉空的節，計畫看起來很完整，
而缺口消失了——跟 `bdd-spec` 的空象限註解是同一條原則。

## 完成後

告訴對方：幾個 API、幾個型別、要不要資料庫；**缺口清單**（哪些回 CLARIFY、
哪些留給 IMPLEMENT）；第一個要綠的場景是哪一個、為什麼；下一步 `bdd-implement`。

IMPORTANT: 順序是提案。改可以，但**改了要說為什麼**——順序的依據是依賴與解鎖
關係，憑感覺調整會讓後面的場景卡在缺件上。
