# `plan.md` 的骨架

照抄即可。每一節的存在理由寫在節標題下方——沒有內容的節**保留標題並寫為什麼空**，
不要刪掉。空著的節跟被刪掉的節在檔案上長得一樣，而它們的意思完全不同。

讀這份的時機：步驟 3 之後，準備寫檔的時候。

```markdown
# 實作計畫

**來源**: `features/` 底下標 `@ready` 的全部——<列出檔名>
**日期**: <YYYY-MM-DD>
**跳過**: <slug> —— <理由>（`@draft`，或儀表板判定未就緒）

一份涵蓋整批。每一節裡按 feature 分小節，但**節號只有一套**。

## 1. API 操作

| 方法 | 路徑 | 來源 | request | response |
| --- | --- | --- | --- | --- |
| PUT | `/courses/{id}/progress` | Feature ＋ `When 更新影片進度` | `{progress: int}` | 204 |

**驗證約束**（來自 `前置（參數）`）

| 約束 | 來源 | 失敗回應 |
| --- | --- | --- |
| `0 ≤ progress ≤ 100` | Rule 3 | 400 · `"進度值超出範圍"` |

**錯誤訊息**（同一條訊息跨 feature 只列一次，`出現在` 欄寫出全部出處）

| 訊息 | 出現在 | HTTP |
| --- | --- | --- |
| `權限不足` | Rule 1 | 403 |

## 2. Domain 型別

每個型別與欄位都要有來源。推不出來的列進第 6 節，不要放在這裡。

```
CourseProgress
  courseID   CourseID     ← Background 播種表
  userID     UserID        ← Background 播種表
  percent    Percent       ← Rule 3（0–100）
  status     ProgressState ← Rule 2、Rule 4

ProgressState = 未開始 | 進行中 | 已完成 | 已交付
                ← Example 2.1、4.1、5.1、以及 4-query-progress 的「未開始」
```

**行為**（來自 `後置（狀態）` 規則，不是猜的）

| 方法 | 規則 | 說明 |
| --- | --- | --- |
| `Update(p Percent) error` | Rule 2、3、4 | 單調遞增、值域、達 100 轉已完成 |

**Domain Service**（規則橫跨多個聚合，或不屬於任何一個）

| 服務 | 規則 | 為什麼不放進聚合 |
| --- | --- | --- |
| `VolumeCalculator` | Rule 2、Shared 3 | 有效重量要讀動作型別與體重快照，橫跨三個聚合 |

沒有就寫「沒有——每條規則的邏輯都只用到單一聚合的狀態」，不要刪掉這一節。

**外部依賴（`port/out`）**

| port | 從哪看出來 | 為什麼不能直接呼叫 |
| --- | --- | --- |
| `Clock` | Rule 7 的歸屬日、`逾時自動結束` | 直接用 `time.Now()` 的場景不可能穩定重跑 |
| `IDGenerator` | 播種表的 ID 欄、`應為 UUID 格式` | 同上 |

判準：**這個場景要能重跑一百次都一樣，有什麼必須被固定住？**

## 3. Schema

判準：跨**兩次使用者操作**之間，什麼必須還在。

| 資料表 | 欄位 | 來源 |
| --- | --- | --- |
| `course_progress` | `course_id, user_id, percent, status` | Rule 2–5 的 `後置（狀態）` |

**這批情境還不需要資料庫時就這樣寫**，並列出理由：

> 五個 Feature 全是 `@query`，沒有任何 `後置（狀態）` 規則。
> 現階段用 in-memory adapter 即可，`infrastructure/` 維持空的。

## 4. 測試分層

一個**場景區塊**一行。`Scenario Outline` 算一個（各列共用內迴圈），編號寫範圍。

`需要資料庫` 的判準：這個場景要驗的行為**本身跨越一次操作的邊界**嗎？

| 場景 | 內迴圈（unit） | 需要資料庫 |
| --- | --- | --- |
| 2.1 進度不可倒退 | 單調遞增判斷 | ✗ |
| 3.1–3.3 值域內可更新（Outline） | 值域驗證 | ✗ |
| 5.1 已交付不改狀態 | 狀態轉移表 | ✗ |
| 6.1 查詢回傳完整內容 | — | ✓ 要讀得到前一次寫入 |

`—` 代表沒有內迴圈（純轉發、純投影），那是正常的。
一個 Example 掛五個以上內層測試則是訊號：那條規則的邏輯可能該獨立成一個
domain 概念。

## 5. 技術風險

規格沒說、但實作一定會撞到的。每一條指出從哪條規則長出來。
跟第 6 節的缺口不同：缺口是**還不知道要做什麼**，風險是**知道要做什麼但做對很難**。

| 風險 | 從哪條規則長出來 | 影響什麼 |
| --- | --- | --- |
| 併發：兩個請求同時通過「最多一筆進行中」的檢查 | log Rule 1 | schema（要不要唯一索引）、實作順序 |
| 冪等：交付重送 | deliver Rule 2.3 | API（要不要冪等鍵） |
| 交易邊界：一次改 36 個聚合 | cel Rule 9 | 分層——跟「一個命令一個聚合」直接衝突 |

**只指出風險，不寫死解法。** 「用 Redis 還是 DB 行鎖」需要知道實際流量與既有
基礎設施，而那些不在 `.feature` 裡。寫「兩種都可以，看部署形態」比寫「用 Redis」
有用——後者看起來是決定，實際上是猜的。

沒有風險就寫「沒有——沒有任何規則涉及唯一性、重送或跨聚合寫入」。

## 6. 實作順序

```
1. @example-2.1 進度不可倒退
   內迴圈：單調遞增判斷（unit）
   解鎖：2.2、2.3
   資料庫：不需要

2. @example-3.1 值域內可更新
   內迴圈：值域驗證（unit）
   解鎖：3.2、3.3
   資料庫：不需要
```

第一項要說明**為什麼是它**——通常是「最薄的完整路徑」或「解鎖最多」。

## 7. 規格裡推不出來的

分兩類，因為**誰能回答**不同。

**回 CLARIFY 補問**（規格沒講）

| 缺口 | 影響 |
| --- | --- |
| `進度` 是整數還是小數？例子只給整數 | 型別、驗證、資料表欄位都定不下來 |
| `已退款` 之類的狀態存在嗎？狀態列舉沒有窮舉 | 狀態轉移表可能缺一格 |

**留給 IMPLEMENT**（技術決定）

| 決定 | 為什麼現在不決定 |
| --- | --- |
| 錯誤回應格式 | 專案既有慣例（RFC 9457），不需要規格授權 |
| 分頁用 offset 還是 cursor | 規格只說「每頁 20 筆」，兩種都滿足 |
```

## 為什麼空的節要留著

`plan.md` 的七節對應七個問題。某一節空著，讀的人要知道是**問過了不需要**
還是**沒想到**——這跟 `bdd-spec` 的空象限註解、`bdd-clarify` 的追問覆蓋
`—` 與 `n/a` 是同一條原則。

刪掉空的節，計畫看起來很完整，而缺口消失了。

## 為什麼是一份，不是每 feature 一份

試過「每 feature 一份 ＋ 一份共用檔」，壞成兩種：

**共用檔把實質吸走。** 型別、schema、錯誤訊息大多是跨 feature 的，於是共用檔
變成真正的計畫，各 feature 的 §3 全退化成一句「見共用檔 §3」。

**節號互撞。** 兩種檔案都用 §1–§6，但意思只對得上一半（`plan.md` §1 是 API，
共用檔 §1 是型別）。**部分對齊比完全不對齊更危險**——讀的人會假設對齊，
然後在三個節上讀錯。

一份的代價是檔案長，但這一步本來就是一次讀完全部 `@ready` 才做得對：
端點衝突與共用型別**只有並排時才看得見**。

## 每一節裡怎麼分 feature

節號一套，節內按 feature 分小節：

```markdown
## 3. Schema

### 由 log-a-workout 建立
| workouts | ... |

### 由 workout-history 讀取，不新增
Rule 3 的分頁會需要 (lifter_id, started_at DESC) 的索引，
但那是效能決定不是規格要求。
```

「不新增」的小節要留著並寫理由——刪掉它，讀的人不知道那則 story 是**看過了不需要**
還是**沒被規劃到**。
