# `plan.md` 的骨架

照抄即可。讀這份的時機：步驟 3，準備寫技術節的時候。

一個 feature 一份，路徑 `specs/<date>-<feature>/plan.md`，跟同目錄的 `spec.md`、
`discovery.md` 配對——目錄名已經帶 feature 的識別資訊，檔頭不重複列。

它只裝**技術設計**（seam、模組、契約、schema、測試層級、風險）與 `## 缺口`；寫法見後面
〈技術節怎麼寫〉。票不在這裡——`bdd-tasks` 從這份設計拆到同目錄的 `tasks/`，格式見
`../../bdd-tasks/references/tasks-format.md`。
`plan.md` 是拋棄式快照，實作一開始就會過期；業務規則住 `spec.md`，活得比它久。

```markdown
# 實作計畫

**來源**: `spec.md`（已對焦，<日期>）＋ `features/` 底下標 `@ready` 的 <N> 個檔
**日期**: <YYYY-MM-DD>
**seam**: <照抄下面 Testing Decisions 的 seam>

### 核心關係人

<照抄 discovery.md 的表，不增列、不改寫決策權>

## Tech Preferences & Constraints
## Known Boundaries
## Implementation Decisions
## Testing Decisions
## Risks
## Parallel Work

## 缺口

`spec.md` 沒定案、但做技術設計時發現需要的；以及 `bdd-tasks` 拆票時發現技術節沒定案的。
技術節裡每個標 `推論` 的決定也列在這裡。
沒有就寫「沒有——`spec.md` 與技術節涵蓋了這批需要的一切」。

- <缺口>：<需求洞（回 DISCOVERY 問人），或技術選擇（留給 IMPLEMENT 決定）>
```

---

## 技術節怎麼寫

上面骨架裡 `## Tech Preferences & Constraints` 到 `## Risks` 五節的寫法。

**核心關係人**整張表照抄 `discovery.md` 的 `### 核心關係人`，不增列、不改寫 `決策權`。
缺那張表就寫一行說缺了、回 `bdd-discovery` 登記，不要自己補。

**技術節改了要留紀錄**：票已經切出去之後，任何動到 seam、介面、schema 的改動都在
`## Risks` 之後補一行「<日期> 改了什麼、為什麼」——實作者可能已經照舊的做了一半。

## 來源標記：三選一

`## Tech Preferences & Constraints` 的每條偏好與禁令、
`## Known Boundaries` 三張清單的每一條、
`## Implementation Decisions` 的每條決定、`## Testing Decisions` 的 Seam 決定，
行尾都要標來源，三選一：

| 標記 | 意思 |
| --- | --- |
| `PRD §x` | 同目錄 `discovery.md` 的 `## 原文` 這樣寫（引用它的章節或段落）——需求方帶來的原始輸入的逐字副本 |
| `Q-<n>` | 來自 `discovery.md` `## Open Questions` 某一題的答案（通常是技術面向、`歸屬` 指向這一節的題），`<n>` 對應那一列的 `Q` 欄 |
| `推論` | 兩者都不是，是從別的地方推導出來的 |

寫法：行尾加 `← <標記>`，例如：

```markdown
- **動哪些模組**：只新增計費模組；出場閘門沿用既有控制介面 ← Q-9
```

MUST: 這個標記不是裝飾。少了它，「這個決定是從某條 FR 或某題答案推出來的」跟
「這個決定是寫的人順手定的」在 `plan.md` 上長得一模一樣——完整範例見本文最後的
〈範例：技術節〉。整份文件的來源欄全是 `推論` 時，代表 DISCOVERY 的技術那一輪沒有真的
發生。`推論` 可以用，但每一條同時列進 `## 缺口`。

**已知缺口**：`plan.md` 的 `← Q-<n>` 目前沒有 script 檢查——`check_spec.py` 只查 `spec.md`。
等 `bdd-review` 做鏈稽核時接手。

`## 缺口` 不在這條規則的範圍內——它記的正是還沒有來源的東西。

`## Testing Decisions` 只有 **Seam** 的決定在範圍內，**「每個 Example 的
測試層級」那張表不在**——它的單位是場景，不是決定，而且它的標記永遠只可能是
`推論`：沒有任何 PRD 或澄清答案答得出「這個場景需不需要資料庫」。一格永遠
同一個值就沒有鑑別力，鑑別力正是下面這條 MUST 說這個標記存在的理由。

在範圍內的那條 **Seam** 決定，標記寫在那張表的 `來源` 欄，只寫標記本身、
不加 `←`——那一欄就是「行尾」在表格裡的位置。

唯一的豁免：**值本身就是在宣告「這裡沒有東西」（不論後面有沒有接一句為什麼
空），那就已經說明了來源狀態**——「沒問過」、「（無資料）」、「（無）」都是
這種值，不再疊 `←` 標記。其餘每一欄都要標。

## Tech Preferences & Constraints

三個具名區塊，每條照樣標來源：

```markdown
## Tech Preferences & Constraints

**語言與框架**
- Go 1.23，驗收層用 godog ← PRD §1

**不准引入的依賴**
- 不引入需要商業授權的套件 ← Q-6

**既有資產要沿用的**
- HTTP 層沿用既有的 chi router，不另起一套 ← 推論
```

**跟 `## Assumptions / Constraints` 怎麼分邊：限制的來源在不在我們的控制範圍內。**

| 這一條 | 進哪一節 |
| --- | --- |
| 區權會否決車牌辨識 | `## Assumptions / Constraints`——外部決定的，我們改不了 |
| 已發包的閘門硬體只吃某種訊號 | `## Assumptions / Constraints`——外部既成事實 |
| 不准引入需要授權費的套件 | `## Tech Preferences & Constraints`——我們自己的規矩 |
| 沿用既有的 router 不另起 | `## Tech Preferences & Constraints`——我們自己的選擇 |

判準是**誰有權改它**，不是它有多硬。外部限制改不了，只能記下來；自己的偏好
改得了，所以要寫清楚「現在的決定是什麼」，讓下一個人知道破例要先問誰。

MUST NOT: 在這一節寫「已經決定好的技術事項」——那是 `## Implementation Decisions`。
判準：這一條是在說**這個 feature 要怎麼做**（決定），還是在說**任何做法都不准
越過的線**（偏好與禁令）？

## Known Boundaries

三張清單。**這一節等於每個 feature 自帶一份 agent 約束**——它是這一版最值得加的東西。

```markdown
## Known Boundaries

**總是要做**
- 金額一律用整數分計算，不用浮點 ← Q-7

**要先問**
- 動到既有的出場閘門控制流程 —— 問管委會主委 ← 推論（那是已發包的設備）

**絕對不做**
- 寫入車牌辨識相關的任何欄位 ← PRD §5（區權會否決）
```

**三個分類的判準是誰承擔後果：** 自己做、問了再做、做了要負責的事不做。

| 分類 | 意思 | 判準 |
| --- | --- | --- |
| `總是要做` | 不用問就照做 | 做錯的後果落在這個 feature 內，而且改得回來 |
| `要先問` | 可以做，但動手前要有人點頭 | 做錯會影響這個 feature 以外的東西 |
| `絕對不做` | 不論理由 | 已經有人否決過，或後果不可逆 |

MUST: 每一條照樣標來源。`要先問` 的條目要寫**該問誰**——寫「要先問」而不寫問誰，
等於把一件事掛起來而沒有人接。該問誰要指向誰才算數，判準見前面
`## Document Overview 的三個部分` 那條 MUST，**不要在這裡抄一份**。

MUST NOT: 把 `## Scope — In / Out` 的「明確排除的能力」搬進 `絕對不做`。
兩者不同：Out of Scope 是**這次不做**，`絕對不做` 是**做了要負責**。
下一期可能會做的東西進 Out of Scope；下一期也不准做的才進這裡。

**空著的分類保留標題並寫為什麼空。** 三張清單都空的 feature 是存在的（純查詢、
沒有副作用），但那要寫出來——空清單與沒想過在檔案上長得一樣。

```markdown
**絕對不做**
（無）——這個 feature 是純查詢，沒有做了要負責的副作用
```

## Implementation Decisions

已經決定好的技術事項。每一條都要指得出理由，不准憑空——`推論` 合法，但推論
本身要指得出是從什麼推來的。標記寫法見 `## 來源標記：三選一`。

- **動哪些模組**：新增什麼、改什麼 ← <標記>
- **介面**：那些模組對外的形狀（函式名、參數、回傳型別） ← <標記>
- **API 契約**：方法、路徑、request、response、錯誤碼 ← <標記>
- **Schema**：資料表與欄位 ← <標記>
- **架構決定**：分層、交易邊界、同步或事件驅動 ← <標記>
- **互動**：跨模組的呼叫順序 ← <標記>

MUST NOT: 寫具體檔案路徑與程式碼片段——它們過期得比什麼都快。
例外：prototype 產出的、比散文更精確地編碼了某個決定的片段（狀態機、schema、
型別形狀），可以內嵌並註明來自 prototype，只留決定的部分。

MUST NOT: 在這裡做新決定。推不出來的寫進 `## 缺口`，不要順手
決定掉——那正是規格失效的方式。

## Testing Decisions

**Seam**（驗收測試打在哪一層）

| seam | 是既有的還是新的 | 為什麼是這一層 | 來源 |
| --- | --- | --- | --- |
| `application.WorkoutService` | 既有 | 規則全在 domain 與 application，HTTP 只是轉發 | 推論 |

判準見 `SKILL.md`「決定 seam」一節的那張表，**不要在這裡抄一份**。
seam 一旦寫在這裡就會往下傳：IMPLEMENT 照著打，REVIEW 把沒人同意過的 seam
當成 finding。

**每個 Example 的測試層級**

一個**場景區塊**一行。`Scenario Outline` 算一個，編號寫範圍。

| 場景 | 內迴圈（unit） | 需要資料庫 |
| --- | --- | --- |
| 2.1 進度不可倒退 | 單調遞增判斷 | ✗ |
| 6.1 查詢回傳完整內容 | — | ✓ 要讀得到前一次寫入 |

`需要資料庫` 的判準：這個場景要驗的行為**本身跨越一次操作的邊界**嗎？
不是「有沒有資料要存」——多數場景在同一次操作內就驗完了。

`—` 代表沒有內迴圈（純轉發、純投影），那是正常的。

**Prior art**

專案裡已經有的同類測試，寫路徑與一句話。新測試跟著它們的形狀寫，不另創。

## Risks

規格沒說、但實作一定會撞到的。每一條指出從哪條規則長出來。
跟 `## 缺口` 不同：缺口是**還不知道要做什麼**，風險是
**知道要做什麼但做對很難**。

| 風險 | 從哪條規則長出來 | 影響什麼 |
| --- | --- | --- |
| 併發：兩個請求同時通過「最多一筆進行中」 | log-a-workout FR-1 | schema（唯一索引）、實作順序 |

SHOULD NOT: 把解法寫死。「用 Redis 還是 DB 行鎖」需要知道實際流量與既有基礎
設施，而那些不在規格裡。寫「兩種都可以，看部署形態」比寫「用 Redis」有用——
後者看起來是決定，實際上是猜的。

## Parallel Work

這批票要不要同時做，以及同時做時哪些檔會在合回時相撞。`bdd-tasks` 照這一節標每張票的
`接合點`，不自己編路徑。

```markdown
## Parallel Work

**要不要並行**: 要 ← 使用者 2026-11-15

| 接合點 | 種類 | 為什麼會共用 |
| --- | --- | --- |
| `api/openapi.yaml` | 追加 | 每個 operation 都加在這份契約 |
| `internal/interfaces/http/apigen/api.gen.go` | 產生 | 由契約產生，內嵌整份 spec |
| `internal/application/port/in/parking_service.go` ＋ 實作它的測試 stub | 追加 | 每個 use case 在同一個驅動埠加方法 |
| `go.mod`／`go.sum` | 產生 | 第一個 path parameter 會帶進 runtime 套件 |
| `internal/application/usecase/command/`（新建） | 新建 | 至少兩張票的 use case 住這裡，交給一張前置票建 |
```

- **要不要並行**是 `Ask user`，不是推論。預設不要——並行換到的是時間，代價是每張票都要
  在合回時解衝突。選「不要」時只寫這一行，表格省略
- 種類三選一加一個 `新建`，定義與合回時怎麼解 →
  `../../bdd-tasks/references/tasks-format.md`〈接合點與同時跑〉。
- 從 `## Implementation Decisions` 推：**會長大的介面連同它的測試 stub**、**第一次用到的
  library 帶進來的依賴檔**、**兩個以上 use case 都要住的新 package**——這三類最常漏
- 兩張票會改同一段既有邏輯的地方標 `爭用`，寫明是哪一段；`bdd-tasks` 會把它們排成先後

## 為什麼一個 feature 一份，不是一則 story 一份

試過「每則 story 一份 ＋ 一份共用檔」，壞成兩種：共用檔把實質吸走（各檔的
schema 一節全退化成「見共用檔」），而且兩種檔案各用一套節號、意思只對得上一半
——**部分對齊比完全不對齊更危險**，讀的人會假設對齊然後在三個節上讀錯。

API 契約與 schema 天生跨 story，只有並排才看得見衝突。`spec.md` 的 story 再多，`plan.md` 仍然一個 feature 一份——story
是切分單位，不是檔案邊界。


## 範例：技術節

````markdown
# 實作計畫

**來源**: `spec.md`（已對焦，2026-09-14）＋ `features/` 底下標 `@ready` 的 2 個檔
**日期**: 2026-09-14
**seam**: `application.出場結帳`

### 核心關係人

| 關係人 | 負責什麼 | 決策權 |
| --- | --- | --- |
| 管委會主委 | 需求方 | 預算內、不動住戶權益的事可自行決定 |
| 區權會 | 住戶大會 | 動到住戶權益或預算外支出；兩個月開一次 |
| 消防設備師 | 消防法規 | 只答法規，不做決定 |
| 柵欄廠商 | 已發包的設備 | 只答技術現況，不做決定 |

## Tech Preferences & Constraints

**語言與框架**
- （無資料）——需求方沒有指定，技術選型由實作端決定

**不准引入的依賴**
- 不引入需要連外網的服務，停車場網路是封閉的 ← PRD §5

**既有資產要沿用的**
- 出場閘門的既有控制介面沿用，不另起 ← PRD §5

## Known Boundaries

**總是要做**
- 金額一律用整數元計算，不用浮點 ← 推論

**要先問**
- 動到既有的出場閘門控制流程 —— 問管委會主委 ← PRD §5（已發包的設備）

**絕對不做**
- 寫入車牌辨識相關的任何欄位 ← PRD §5（去年區權會否決）

## Implementation Decisions

- **動哪些模組**：只新增計費模組；出場閘門沿用既有控制介面、不改它——改它是「要先問」且還沒問 ← 推論
- **介面**：`計算應收金額(入場時間, 出場時間) -> 金額`——從 FR-1 與 AC-1.1–1.3 推來：它們只拿入場到出場的停留時長決定一個金額，沒有第三個輸入 ← 推論

## Testing Decisions

**Seam**（驗收測試打在哪一層）

| seam | 是既有的還是新的 | 為什麼是這一層 | 來源 |
| --- | --- | --- | --- |
| `application.出場結帳` | 新 | 出場閘門原本只有硬體控制介面，沒有既有 seam 可掛；FR-1（訪客計費）與 FR-2（月租戶跳過計費）在這裡合流，一個 seam 覆蓋兩則 story 的全部 AC——比只打 `計算應收金額` 高一層（不然漏掉 FR-2 那條分支），比出場閘門硬體低一層（不必為了驗收多開一個假物件） | 推論 |

**每個 Example 的測試層級**

| 場景 | 內迴圈（unit） | 需要資料庫 |
| --- | --- | --- |
| 1.1–1.3 費率邊界（29／30／31 分） | 分鐘數換算金額 | ✗ |
| 2.1 月租戶跳過計費 | — | ✓ 要讀到月租名單前一次寫入的資料 |
| 3.1 警報中柵欄常開 | — | ✗ 警報訊號用假物件餵 |

**Prior art**

（無）——虛構教學專案，沒有既有同類驗收測試可比照，新測試不套用任何既有形狀。

## Risks

| 風險 | 從哪條規則長出來 | 影響什麼 |
| --- | --- | --- |
| 警報期間出場一律不計費，警報頻繁或被誤觸發時收入流失 | monthly-pass FR-3 | 要不要記錄警報期間的每一次出場，留給 IMPLEMENT |

（缺口略——見本文開頭的骨架）
````
