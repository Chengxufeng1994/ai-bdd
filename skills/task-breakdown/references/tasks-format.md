# `tasks.md` 的骨架

照抄即可。讀這份的時機：票的清單跟使用者確認過，準備寫檔的時候。

一個 feature 一份 `specs/ongoing/<date>-<feature>/tasks.md`，跟同目錄的 `plan.md`、`spec.md` 配對。
開頭是來源與哪幾張可以同時開始，接著一波一節、每張票一個 `### <編號>` 小節——下文叫它**票節**。

```markdown
# Tasks

**來源**: `plan.md` 的技術決定 ＋ `plan.md`（<日期>）＋ `features/` 底下標 `@ready` 的 <N> 個檔
**日期**: <YYYY-MM-DD>
**可以同時開始**: 00 做完後，01 與 04（只共用 `追加`／`產生`）。02 與 03 都 `爭用` `due_date.go`，排成先後。

## 第 1 波

### 00 — <前置整理的標題>

（欄位同下）

### 01 — <票的標題>

**交付什麼行為**: 從使用者角度寫這張票做完之後**什麼事會動**。
不是分層清單。「新增 WorkoutRepository」不是行為，
「使用者可以記錄一次只有一個動作的訓練並讀回來」是。

**涵蓋場景**: `features/due-date.feature` 的 `@example-1.1`、`@example-1.2`
**Blocked by**: 00
**接合點**: `api/openapi.yaml`（追加）、`api.gen.go`（產生）
**模組**: <照抄 plan.md Implementation Decisions「動哪些模組」裡這張票碰的那幾個>
**契約**: `lendBook`（`plan.md` `## API 契約`）
**資料表**: `loans`（`plan.md` `## Database Schema`）
**大小**: M（一條功能切片）
**內迴圈**: <這張票底下要寫哪些 unit test，來自 plan.md Testing Decisions 的測試分層>

**驗收條件**

- [ ] <驗收條件 1>
- [ ] <驗收條件 2>
- [ ] 搬進 api/openapi.yaml 的 operation 與 plan.md 的片段一致

**驗證**

- [ ] 這張票的場景：`<跑場景的命令> <由涵蓋場景組成的 tag 運算式>`
- [ ] 閘門：`<專案的驗證閘門命令>`
- [ ] 手動：<只有自動測試驗不到的才寫；沒有就刪掉這一行>

#### 缺口

（無）

**檢查點**（00、01 都合回之後）：已勾完的票的場景全綠、閘門綠，使用者看過才開下一波

## 第 2 波

### 02 — <標題>
…
```

一波一節：同一波裡的票 `Blocked by` 只指向前面幾波。波與波之間是檢查點，見〈檢查點〉。

依賴序排列，blockers 在前。順序也要守 `plan.md` 的 `## 依賴圖`：一張票不得排在它依賴的節點之前（〈契約與資料表〉）。編號一旦寫出去就不重排——`implement 03` 靠它定位。票做到哪了看票節裡的勾，
不另外記。

**前置整理（prefactoring）也是票**，編號 `00` 起、排在所有功能票前面：「make the change
easy, then make the easy change.」它沒有 `涵蓋場景`，`交付什麼行為` 改寫 `改什麼`。
沒有前置整理就不要寫 `00`，在 `**可以同時開始**` 下面寫一行「沒有前置整理——現有結構直接容得下
這批行為」。

## 誰寫哪幾行

| 行 | 誰寫 |
| --- | --- |
| 開頭三行、`## 第 N 波`、檢查點那一行、每個票節的欄位（`交付什麼行為` 到 `內迴圈`）、驗收條件與驗證的文字 | `task-breakdown` |
| 自己那個票節的勾、`**檢查點**:` 那一行、`#### 缺口` 的內容 | 做這張票的 `implement` |

`#### 缺口` 是實作時發現的洞，`task-breakdown` 寫票時一律寫「（無）」。做票的 session **只改自己的
票節**，幾張票同時做時，合回 `tasks.md` 的衝突就只會是兩邊各改了自己的票節——取聯集即可
（`implement`〈合回主線〉）。

## 契約與資料表

兩行都從 `plan.md` 照抄，不自己編：

- `**契約**`：這張票涵蓋的 operation——OpenAPI 片段寫 `operationId`，程式碼層契約寫埠的方法（`借出`）。
  它用到的 `components` 不列，`implement` 跟著 operation 一起搬
- `**資料表**`：這張票要建或改的表，名字照 `## Database Schema`；`implement` 照那一節寫 migration

沒有就寫「無」（前置整理、只改 domain 規則的票）。一張票碰的 operation 或表，在 `## 依賴圖` 上的父節點（聚合、
表、查詢埠）要由這張或它 `Blocked by` 的票做出來；排不出這種順序，是圖或切法有一邊錯了，進 `plan.md` 的 `## 缺口`。

`## API 契約` 是 OpenAPI 片段時，有 `**契約**` 的票驗收條件**照抄**這一條：

```markdown
- [ ] 搬進 api/openapi.yaml 的 operation 與 plan.md 的片段一致
```

它在起點是紅的（operation 還不在 `api/openapi.yaml`），擋的是實作時順手改形狀、`plan.md` 與專案的契約從此分家。
程式碼層契約沒有要搬的檔，不加這一條。

兩張票都要建同一張還不存在的表，跟〈接合點與同時跑〉的新建的東西一樣：指定一張票擁有它，另一張 `Blocked by` 它。

## 接合點與同時跑

`接合點` 列的是**這張票會改、而別張票也可能改**的檔案，每一個標種類。路徑與種類照抄
`plan.md` 的 `## Parallel Work`，不自己編；那一節沒寫到、切票時才發現的，進 `plan.md` 的
`## 缺口`。只有這張票會碰的檔案不用列。沒有就寫「無」。寫法：`` `api/openapi.yaml`（追加） ``。

| 種類 | 是什麼 | 例子 | 擋不擋並行 | 合回時怎麼解 |
| --- | --- | --- | --- | --- |
| `產生` | 由工具產生、不手寫的檔 | `api.gen.go`、mock、`go.sum` | 不擋 | **不手動合**：合完原始檔後重新產生 |
| `追加` | 每張票各加一段、不改別人那段 | 契約加 operation、介面加方法、組裝函式加一行接線、store 加欄位 | 不擋 | 取聯集，再跑閘門 |
| `爭用` | 兩張票要改**同一段**既有邏輯 | 兩張票都改同一個函式的分支 | **擋** | 不該發生——排成先後 |

IMPORTANT: 這幾類最容易漏列，而漏列的正是合回時出事的：

- **會長大的介面，連同實作它的測試 stub**——介面加了方法，每個手刻的 stub 都要跟著加（`追加`）
- **依賴檔**——第一次用到某個 library 會改 `go.mod`／`go.sum`（`產生`）
- **會新建的 package 或共用的測試輔助函式**——見下
- **新的必填組裝欄位，連同每個組它的測試**——一張票在組裝用的 struct 加了必填欄位，另一張票新寫的
  測試組它時沒帶，合完 git 不報衝突、閘門卻紅（`追加`，兩張票都列）
- **按 feature 分的 mapper／presenter、共用的步驟檔**——各自加函式，git 會報衝突（`追加`）
- **跨 feature 共用的步驟句子**——`操作成功`、`逾期天數應為` 這類句子只能定義一次：指定一張票擁有它，
  其他票 `Blocked by` 它，跟新建的東西同樣處理；它們查的對照表（失敗原因、錯誤訊息的翻譯表）是 `追加`
- **產碼工具的整份輸出**——mockery 這類一次產一整個檔的設定（`all: true`），每加一個埠那個檔就過期（`產生`）
- **migration 目錄與它的序號**——兩張票各寫一支 migration，會搶同一個序號；目錄還不存在時兩張票各自新建也會撞。
  序號標 `爭用`，排成先後；目錄標 `新建`，指定一張票擁有它，其他票 `Blocked by` 它
- **位置參數的建構子**——每張票都在同一行加一個參數，git 可能自己合出錯的參數順序，只靠型別不同才被編譯器
  擋下（`爭用`）。建議 `plan.md` 的 Implementation Decisions 改成收一個 struct、一個依賴一個欄位，它就變成 `追加`

**新建的東西不屬於三種任何一種。** 兩張票都需要一個還不存在的 package（或同一個測試輔助
函式），各自新建就會撞：git 合得很乾淨，編譯壞在重複宣告。切票時指定**一張票擁有它**——
通常是 `00` 前置整理，只建 package 骨架與共用的輔助函式，不需要任何假實作——其他用到它的票
`Blocked by` 那一張。

兩張票可以同時跑，三個條件都要成立：

1. 各自的 `Blocked by` 都已完成（那些票節的驗收條件全勾）
2. 沒有共同的 `爭用` 接合點
3. 沒有兩張都要新建的東西

`Blocked by` 管的是先後；`接合點` 管的是合回時要做什麼。共同的 `產生`／`追加` 接合點不擋並行，
但合回時一定會衝突——由合回的那個 session 照上表解（`implement`〈合回主線〉）。

`接合點` 是切票時的預測，票還沒做。`追加` 與 `爭用` 拿不準時標 `爭用`：多標的代價是少一點
並行，少標的代價是合回時才發現兩張票改了同一段邏輯。

`plan.md` 的 `## Parallel Work` 選了「不要」時，`**可以同時開始**` 寫「不適用」，
`接合點` 照樣列——它決定合回時怎麼解，順序做的票一樣會用到。

## 大小

每張票標一個大小。這是切票時的估計，給人判斷票是不是太大，不是工時。**看這張票交付幾條規則、
幾個行為**，不看檔數——分層的專案裡，一條最薄的切片就會碰契約、產生碼、handler、mapper、port、
use case、domain、repository、步驟各一個檔，照檔數算每張都是 L：

| 大小 | 交付什麼 | 例子 |
| --- | --- | --- |
| XS | 不交付新行為：一個設定、一個型別 | 加一個欄位 |
| S | 一條規則的一兩個例子 | 週四借出，到期日是兩週後的週四 |
| M | 一條規則的全部例子，或兩條緊密相關的規則 | 到期日加 14 天、遇休館日順延 |
| L | 三條以上的規則，或兩個不同的行為 | 到期日加上續借 |
| XL | **太大，再拆** | — |

檔數只在**沒有分層樣板**的專案裡當參考：XS 一個檔、S 一兩個、M 三到五個、L 五到八個。

agent 在 S 與 M 做得最好。L 以上要拆的訊號：

- 一個全新 session 做不完
- 驗收條件三條寫不完
- 碰到兩個以上互不相干的子系統
- 標題裡有「和」——那通常是兩張票

## 驗證

`**驗證**` 寫的是**做完這張票要跑的命令**，讓 `implement` 照著跑，不用自己組：

- **這張票的場景**：把 `涵蓋場景` 的 tag 組成一個運算式，套進 `plan.md` `## Commands` 的「跑場景」（實測場：
  `go test -count=1 ./test/acceptance/ -v -godog.format=progress -godog.tags='@example-1.1,@example-1.2'`）。運算式要跟
  `涵蓋場景` 一一對應，多一個少一個都不行。「或」照 runner 的語法寫：實測場的 godog 用逗號，
  寫成 `||` 或 `or` 會選到 0 個場景卻照樣成功結束。命令要帶會印出場景數的旗標
- **閘門**：照抄 `plan.md` `## Commands` 的「閘門」（實測場是 `make verify`）；那裡寫「（沒有——要問
  使用者）」就照抄成「（問使用者）」，不要猜。閘門裡跑場景的那一段也要帶會印出場景數的旗標
- **手動**：自動測試驗不到、要人看的才寫；能寫成測試的就寫成驗收條件

前置整理的票沒有 `涵蓋場景`，只寫閘門。

## 檢查點

每一波（一組可以同時開始的票）結束時放一個檢查點；不並行時，每 2–3 張票放一個：

```markdown
**檢查點**（01、04 都合回之後）：已勾完的票的場景全綠、閘門綠，使用者看過才開下一波
```

檢查點不是一張票，沒有勾選框——檢查點那一行由 `task-breakdown` 寫，做票的 session 不改它。

**一波只跑一次，在主線上、開這一波任何 worktree 之前。** 跑的是開這一波第一張票的 `implement`
（或派工的人）：檢查點列的檢查跑完、使用者看過，才開這一波的票。看過了記在**每張開工的票自己的
票節**（`**驗證**` 之後），一行：

```markdown
**檢查點**: 2026-11-15 通過（`<跑的命令>`：24 個場景全綠、閘門綠），使用者看過
```

寫出跑的命令：它選到的場景數可能跟 `implement` 第 5 步第二行（只接已勾完的票）不一樣——例如
walking skeleton 的 `@smoke` 不屬於任何票。有命令，兩個數字才對得起帳。

同一波並行的其他 session 開工時，派工的人把這行帶進它們的開工說明，各自寫進自己的票節，
不再重跑。

## 為什麼一份 `tasks.md`

票曾經一張一個檔、外加一份 `index.md` 記順序，換到的是「同時做的 session 不會寫到同一份檔」。代價是
讀的人要在十幾個檔之間跳，`index.md` 與票檔的 `大小`、`Blocked by`、`接合點` 還得一字不差地同步。
改成一份之後，順序就是檔案由上而下的順序；並行的保護改由「只改自己的票節」承擔——各票節離得遠，
git 多半合得掉，合不掉時兩邊改的也一定是不同的票節。

## 三條切票規則

| 規則 | 破了會怎樣 |
| --- | --- |
| **垂直切片**：一張票穿過所有層（schema／API／UI／測試） | 依層切的實測案例：26 張票、每張平均跑 20 次 agent，四分之三是返工 |
| **自己可 demo**：做完當下就能展示 | 驗收條件會伸手進別張票擁有的工作，變成不可能獨立驗 |
| **塞得進一個全新 session**：撿起這張票的東西只看過這張票節、`tasks.md` 開頭三行與 `plan.md` 的技術決定 | 票太大時實作者會在中途失去脈絡，然後開始猜 |

檢驗每張票只要問一句：**做完之後我能 demo 什麼？** 答不出來的就是水平切片。

## 驗收條件要能失敗

每一條驗收條件，說得出「什麼觀察會顯示它是假的」，並確認**在實作者的起點
commit 上它是紅的**。

三種常見的失效寫法：

| 寫法 | 為什麼是壞的 |
| --- | --- |
| 起點就已經成立的條件 | 它不驗任何東西 |
| 只有別張票做完才可能成立 | 這張票不擁有它，等於把驗收外包 |
| 把需求原文抄一遍 | 沒有從產物推導，只是換句話說 |

垂直切片本身就擋掉大部分：**交付了原本不存在的行為的切片，在起點必然是紅的。**

例外：改既有規則的票（喚醒之後）常需要「舊行為不變」的條件（「AC-7.3 仍綠」）。它在起點本來就綠，
寫成驗收條件時行尾標「（防回歸，起點就綠）」；每張票仍至少要有一條在起點是紅的。

## wide refactor 的例外

一個機械性改動（改欄位名、換共用型別）影響面擴散到全 codebase 時，
沒有任何垂直切片能綠。這種改 expand–contract：

1. **expand** — 加新形式在舊的旁邊，什麼都不破
2. **migrate** — 呼叫端分批遷移，每批一張票、依 blast radius 分（每個 package、
   每個目錄），每張 blocked by expand。CI 保持綠，因為舊形式還在
3. **contract** — 沒有呼叫者之後刪掉舊形式，blocked by 全部 migrate 票

連分批都無法各自保持綠時，讓它們共用一條整合分支，全部 block 一張最後的
整合驗證票——綠只在那裡承諾。
