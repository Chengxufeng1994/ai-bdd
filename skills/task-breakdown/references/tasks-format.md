# `tasks/` 的骨架

照抄即可。讀這份的時機：票的清單跟使用者確認過，準備寫檔的時候。

一個 feature 一個 `specs/ongoing/<date>-<feature>/tasks/`，跟同目錄的 `plan.md`、`spec.md` 配對。
它裝一份 `index.md` 與一張票一個檔。

## `index.md` —— 順序只住這裡

```markdown
# 票

**來源**: `spec.md` 技術部分 ＋ `plan.md`（<日期>）＋ `features/` 底下標 `@ready` 的 <N> 個檔
**日期**: <YYYY-MM-DD>

| 票 | 標題 | 大小 | Blocked by | 接合點 |
| --- | --- | --- | --- | --- |
| [00](00-<slug>.md) | <前置整理的標題> | S | 無 | 無 |
| [01](01-<slug>.md) | <標題> | M | 00 | `api/openapi.yaml`（追加）、`api.gen.go`（產生） |
| [04](04-<slug>.md) | <標題> | M | 00 | `api/openapi.yaml`（追加）、`api.gen.go`（產生） |

**檢查點**（01、04 都合回之後）：已勾完的票的場景全綠、閘門綠，使用者看過才開下一波

| 票 | 標題 | 大小 | Blocked by | 接合點 |
| --- | --- | --- | --- | --- |
| [02](02-<slug>.md) | <標題> | M | 01 | `api/openapi.yaml`（追加）、`api.gen.go`（產生）、`internal/domain/parking/fee.go`（爭用） |
| [03](03-<slug>.md) | <標題> | S | 01 | `api/openapi.yaml`（追加）、`api.gen.go`（產生）、`internal/domain/parking/fee.go`（爭用） |

**可以同時開始**: 00 做完後，01 與 04（只共用 `追加`／`產生`）。02 與 03 都 `爭用` `fee.go`，排成先後。
```

一波一張表：同一張表裡的票 `Blocked by` 只指向前面幾波。表與表之間是檢查點，見〈檢查點〉。

依賴序排列，blockers 在前。`大小` 一欄跟票檔一字不差。編號一旦寫出去就不重排——`implement 03` 靠它定位。
`Blocked by` 與 `接合點` 兩欄跟票檔裡的同名欄位一字不差；改一邊就改另一邊。

`index.md` 只由 `task-breakdown` 寫。票做到哪了不記在這裡——那是票檔裡的勾。

## 票檔 —— `<編號>-<slug>.md`

```markdown
# 01 — <票的標題>

**交付什麼行為**: 從使用者角度寫這張票做完之後**什麼事會動**。
不是分層清單。「新增 WorkoutRepository」不是行為，
「使用者可以記錄一次只有一個動作的訓練並讀回來」是。

**涵蓋場景**: `features/visitor-fee.feature` 的 `@example-1.1`、`@example-1.2`
**Blocked by**: 無，可立即開始
**接合點**: `api/openapi.yaml`（追加）、`api.gen.go`（產生）
**模組**: <照抄 spec.md Implementation Decisions「動哪些模組」裡這張票碰的那幾個>
**大小**: M（一條功能切片）
**內迴圈**: <這張票底下要寫哪些 unit test，來自 spec.md Testing Decisions 的測試分層>

**驗收條件**

- [ ] <驗收條件 1>
- [ ] <驗收條件 2>

**驗證**

- [ ] 這張票的場景：`<跑場景的命令> <由涵蓋場景組成的 tag 運算式>`
- [ ] 閘門：`<專案的驗證閘門命令>`
- [ ] 手動：<只有自動測試驗不到的才寫；沒有就刪掉這一行>

## 缺口

（無）
```

**前置整理（prefactoring）也是票**，編號 `00` 起、排在所有功能票前面：「make the change
easy, then make the easy change.」它沒有 `涵蓋場景`，`交付什麼行為` 改寫 `改什麼`。
沒有前置整理就不要建 `00`，在 `index.md` 的表下寫一行「沒有前置整理——現有結構直接容得下
這批行為」。

票檔的 `## 缺口` 由做這張票的 `implement` 寫：實作時發現的洞。`task-breakdown` 建檔時
一律寫「（無）」。

## 接合點與同時跑

`接合點` 列的是**這張票會改、而別張票也可能改**的檔案，每一個標種類。路徑與種類照抄
`plan.md` 的 `## Parallel Work`，不自己編；那一節沒寫到、切票時才發現的，進 `plan.md` 的
`## 缺口`。只有這張票會碰的檔案不用列。沒有就寫「無」。寫法：`` `api/openapi.yaml`（追加） ``。

| 種類 | 是什麼 | 例子 | 擋不擋並行 | 合回時怎麼解 |
| --- | --- | --- | --- | --- |
| `產生` | 由工具產生、不手寫的檔 | `api.gen.go`、mock、`go.sum` | 不擋 | **不手動合**：合完原始檔後重新產生 |
| `追加` | 每張票各加一段、不改別人那段 | 契約加 operation、介面加方法、組裝函式加一行接線、store 加欄位 | 不擋 | 取聯集，再跑閘門 |
| `爭用` | 兩張票要改**同一段**既有邏輯 | 兩張票都改同一個函式的分支 | **擋** | 不該發生——排成先後 |

IMPORTANT: 這幾類最容易漏列，而漏列的正是合回時出事的：

- **會長大的介面，連同實作它的測試 stub**——介面加了方法，每個手刻的 stub 都要跟著加（`追加`）
- **依賴檔**——第一次用到某個 library 會改 `go.mod`／`go.sum`（`產生`）
- **會新建的 package 或共用的測試輔助函式**——見下
- **新的必填組裝欄位，連同每個組它的測試**——一張票在組裝用的 struct 加了必填欄位，另一張票新寫的
  測試組它時沒帶，合完 git 不報衝突、閘門卻紅（`追加`，兩張票都列）
- **按 feature 分的 mapper／presenter、共用的步驟檔**——各自加函式，git 會報衝突（`追加`）
- **跨 feature 共用的步驟句子**——`操作成功`、`應付金額應為` 這類句子只能定義一次：指定一張票擁有它，
  其他票 `Blocked by` 它，跟新建的東西同樣處理；它們查的對照表（失敗原因、錯誤訊息的翻譯表）是 `追加`
- **產碼工具的整份輸出**——mockery 這類一次產一整個檔的設定（`all: true`），每加一個埠那個檔就過期（`產生`）
- **位置參數的建構子**——每張票都在同一行加一個參數，git 可能自己合出錯的參數順序，只靠型別不同才被編譯器
  擋下（`爭用`）。建議 `spec.md` 的 Implementation Decisions 改成收一個 struct、一個依賴一個欄位，它就變成 `追加`

**新建的東西不屬於三種任何一種。** 兩張票都需要一個還不存在的 package（或同一個測試輔助
函式），各自新建就會撞：git 合得很乾淨，編譯壞在重複宣告。切票時指定**一張票擁有它**——
通常是 `00` 前置整理，只建 package 骨架與共用的輔助函式，不需要任何假實作——其他用到它的票
`Blocked by` 那一張。

兩張票可以同時跑，三個條件都要成立：

1. 各自的 `Blocked by` 都已完成（那些票檔的驗收條件全勾）
2. 沒有共同的 `爭用` 接合點
3. 沒有兩張都要新建的東西

`Blocked by` 管的是先後；`接合點` 管的是合回時要做什麼。共同的 `產生`／`追加` 接合點不擋並行，
但合回時一定會衝突——由合回的那個 session 照上表解（`implement`〈合回主線〉）。

`接合點` 是切票時的預測，票還沒做。`追加` 與 `爭用` 拿不準時標 `爭用`：多標的代價是少一點
並行，少標的代價是合回時才發現兩張票改了同一段邏輯。

`plan.md` 的 `## Parallel Work` 選了「不要」時，`index.md` 的「可以同時開始」寫「不適用」，
`接合點` 照樣列——它決定合回時怎麼解，順序做的票一樣會用到。

## 大小

每張票標一個大小。這是切票時的估計，給人判斷票是不是太大，不是工時。**看這張票交付幾條規則、
幾個行為**，不看檔數——分層的專案裡，一條最薄的切片就會碰契約、產生碼、handler、mapper、port、
use case、domain、repository、步驟各一個檔，照檔數算每張都是 L：

| 大小 | 交付什麼 | 例子 |
| --- | --- | --- |
| XS | 不交付新行為：一個設定、一個型別 | 加一個欄位 |
| S | 一條規則的一兩個例子 | 停留 30 分鐘以內免費 |
| M | 一條規則的全部例子，或兩條緊密相關的規則 | 訪客依停留時長計費 |
| L | 三條以上的規則，或兩個不同的行為 | 計費加上付款 |
| XL | **太大，再拆** | — |

檔數只在**沒有分層樣板**的專案裡當參考：XS 一個檔、S 一兩個、M 三到五個、L 五到八個。

agent 在 S 與 M 做得最好。L 以上要拆的訊號：

- 一個全新 session 做不完
- 驗收條件三條寫不完
- 碰到兩個以上互不相干的子系統
- 標題裡有「和」——那通常是兩張票

## 驗證

`**驗證**` 寫的是**做完這張票要跑的命令**，讓 `implement` 照著跑，不用自己組：

- **這張票的場景**：把 `涵蓋場景` 的 tag 組成一個運算式，套進 `spec.md` `## Commands` 的「跑場景」（實測場：
  `go test -count=1 ./test/acceptance/ -v -godog.format=progress -godog.tags='@example-1.1,@example-1.2'`）。運算式要跟
  `涵蓋場景` 一一對應，多一個少一個都不行。「或」照 runner 的語法寫：實測場的 godog 用逗號，
  寫成 `||` 或 `or` 會選到 0 個場景卻照樣成功結束。命令要帶會印出場景數的旗標
- **閘門**：照抄 `spec.md` `## Commands` 的「閘門」（實測場是 `make verify`）；那裡寫「（沒有——要問
  使用者）」就照抄成「（問使用者）」，不要猜。閘門裡跑場景的那一段也要帶會印出場景數的旗標
- **手動**：自動測試驗不到、要人看的才寫；能寫成測試的就寫成驗收條件

前置整理的票沒有 `涵蓋場景`，只寫閘門。

## 檢查點

每一波（一組可以同時開始的票）結束時放一個檢查點；不並行時，每 2–3 張票放一個：

```markdown
**檢查點**（01、04 都合回之後）：已勾完的票的場景全綠、閘門綠，使用者看過才開下一波
```

檢查點不是一張票，沒有勾選框——`index.md` 只由 `task-breakdown` 寫，做票的 session 不改它。

**一波只跑一次，在主線上、開這一波任何 worktree 之前。** 跑的是開這一波第一張票的 `implement`
（或派工的人）：檢查點列的檢查跑完、使用者看過，才開這一波的票。看過了記在**每張開工的票自己的
票檔**，一行：

```markdown
**檢查點**: 2026-11-15 通過（24 個場景全綠、閘門綠），使用者看過
```

同一波並行的其他 session 開工時，派工的人把這行帶進它們的開工說明，各自寫進自己的票檔，
不再重跑。

## 為什麼一張票一個檔

票原本住在 `plan.md` 裡，理由是「順序是排序關係，拆進 N 個檔案之後就不存在了」。
`index.md` 保住了順序；拆檔換到的是：做票的 session 只寫自己那張票檔，幾張票同時做時
沒有任何一份檔案被兩個 session 寫。

---

## 三條切票規則

| 規則 | 破了會怎樣 |
| --- | --- |
| **垂直切片**：一張票穿過所有層（schema／API／UI／測試） | 依層切的實測案例：26 張票、每張平均跑 20 次 agent，四分之三是返工 |
| **自己可 demo**：做完當下就能展示 | 驗收條件會伸手進別張票擁有的工作，變成不可能獨立驗 |
| **塞得進一個全新 session**：撿起這張票的東西只看過這張票檔與 `spec.md` 的技術部分 | 票太大時實作者會在中途失去脈絡，然後開始猜 |

檢驗每張票只要問一句：**做完之後我能 demo 什麼？** 答不出來的就是水平切片。

## 驗收條件要能失敗

每一條驗收條件，說得出「什麼觀察會顯示它是假的」，並確認**在實作者的起點
commit 上它是紅的**。

三種常見的失效寫法：

| 寫法 | 為什麼是壞的 |
| --- | --- |
| 起點就已經成立的條件 | 它不驗任何東西 |
| 只有別張票做完才可能成立 | 這張票不擁有它，等於把驗收外包 |
| 把需求原文抄一遍 | 沒有從產物推導，只是換句話說 |

垂直切片本身就擋掉大部分：**交付了原本不存在的行為的切片，在起點必然是紅的。**

## wide refactor 的例外

一個機械性改動（改欄位名、換共用型別）影響面擴散到全 codebase 時，
沒有任何垂直切片能綠。這種改 expand–contract：

1. **expand** — 加新形式在舊的旁邊，什麼都不破
2. **migrate** — 呼叫端分批遷移，每批一張票、依 blast radius 分（每個 package、
   每個目錄），每張 blocked by expand。CI 保持綠，因為舊形式還在
3. **contract** — 沒有呼叫者之後刪掉舊形式，blocked by 全部 migrate 票

連分批都無法各自保持綠時，讓它們共用一條整合分支，全部 block 一張最後的
整合驗證票——綠只在那裡承諾。
