# `tasks/` 的骨架

照抄即可。讀這份的時機：票的清單跟使用者確認過，準備寫檔的時候。

一個 feature 一個 `specs/<date>-<feature>/tasks/`，跟同目錄的 `plan.md`、`spec.md` 配對。
它裝一份 `index.md` 與一張票一個檔。

## `index.md` —— 順序只住這裡

```markdown
# 票

**來源**: `plan.md`（<日期>）＋ `features/` 底下標 `@ready` 的 <N> 個檔
**日期**: <YYYY-MM-DD>

| 票 | 標題 | Blocked by | 共用檔案 |
| --- | --- | --- | --- |
| [00](00-<slug>.md) | <前置整理的標題> | 無 | 無 |
| [01](01-<slug>.md) | <標題> | 00 | `api/openapi.yaml` |
| [02](02-<slug>.md) | <標題> | 01 | `api/openapi.yaml`、`test/acceptance/steps_停車.go` |
| [03](03-<slug>.md) | <標題> | 01 | 無 |

**可以同時開始**: 01 做完後，02 與 03（Blocked by 都只有 01、共用檔案沒有交集）。
```

依賴序排列，blockers 在前。編號一旦寫出去就不重排——`bdd-implement 03` 靠它定位。
`Blocked by` 與 `共用檔案` 兩欄跟票檔裡的同名欄位一字不差；改一邊就改另一邊。

`index.md` 只由 `bdd-tasks` 寫。票做到哪了不記在這裡——那是票檔裡的勾。

## 票檔 —— `<編號>-<slug>.md`

```markdown
# 01 — <票的標題>

**交付什麼行為**: 從使用者角度寫這張票做完之後**什麼事會動**。
不是分層清單。「新增 WorkoutRepository」不是行為，
「使用者可以記錄一次只有一個動作的訓練並讀回來」是。

**涵蓋場景**: `@example-1.1`、`@example-1.2`
**Blocked by**: 無，可立即開始
**共用檔案**: `api/openapi.yaml`
**內迴圈**: <這張票底下要寫哪些 unit test，來自 plan.md Testing Decisions 的測試分層>

- [ ] <驗收條件 1>
- [ ] <驗收條件 2>

## 缺口

（無）
```

**前置整理（prefactoring）也是票**，編號 `00` 起、排在所有功能票前面：「make the change
easy, then make the easy change.」它沒有 `涵蓋場景`，`交付什麼行為` 改寫 `改什麼`。
沒有前置整理就不要建 `00`，在 `index.md` 的表下寫一行「沒有前置整理——現有結構直接容得下
這批行為」。

票檔的 `## 缺口` 由做這張票的 `bdd-implement` 寫：實作時發現的洞。`bdd-tasks` 建檔時
一律寫「（無）」。

## 共用檔案與同時跑

`共用檔案` 列的是**這張票會改、而別張票也可能改**的既有或新增檔案：契約檔
（`api/openapi.yaml`）、按領域名詞分檔的 step definition、migration、共用的組裝函式。
只有這張票會碰的檔案不用列。沒有就寫「無」。

兩張票可以同時跑，要兩個條件都成立：

1. 各自的 `Blocked by` 都已完成（那些票檔的驗收條件全勾）
2. `共用檔案` 沒有交集

`Blocked by` 管的是先後；`共用檔案` 管的是能不能同時。兩張邏輯上互不依賴的票都要加
operation 進同一份契約檔，就不能同時跑——排成先後，或把共用的那一段切成一張前置票。

`共用檔案` 是切票時的預測，票還沒做。拿不準就列：多列的代價是少一點並行，漏列的代價是
兩個 worktree 合不回來。

## 為什麼一張票一個檔

票原本住在 `plan.md` 裡，理由是「順序是排序關係，拆進 N 個檔案之後就不存在了」。
`index.md` 保住了順序；拆檔換到的是：做票的 session 只寫自己那張票檔，幾張票同時做時
沒有任何一份檔案被兩個 session 寫。

---

## 三條切票規則

| 規則 | 破了會怎樣 |
| --- | --- |
| **垂直切片**：一張票穿過所有層（schema／API／UI／測試） | 依層切的實測案例：26 張票、每張平均跑 20 次 agent，四分之三是返工 |
| **自己可 demo**：做完當下就能展示 | 驗收條件會伸手進別張票擁有的工作，變成不可能獨立驗 |
| **塞得進一個全新 session**：撿起這張票的東西只看過這張票檔與 `plan.md` 的技術節 | 票太大時實作者會在中途失去脈絡，然後開始猜 |

檢驗每張票只要問一句：**做完之後我能 demo 什麼？** 答不出來的就是水平切片。

## 驗收條件要能失敗

每一條驗收條件，說得出「什麼觀察會顯示它是假的」，並確認**在實作者的起點
commit 上它是紅的**。

三種常見的失效寫法：

| 寫法 | 為什麼是壞的 |
| --- | --- |
| 起點就已經成立的條件 | 它不驗任何東西 |
| 只有別張票做完才可能成立 | 這張票不擁有它，等於把驗收外包 |
| 把需求原文抄一遍 | 沒有從產物推導，只是換句話說 |

垂直切片本身就擋掉大部分：**交付了原本不存在的行為的切片，在起點必然是紅的。**

## wide refactor 的例外

一個機械性改動（改欄位名、換共用型別）影響面擴散到全 codebase 時，
沒有任何垂直切片能綠。這種改 expand–contract：

1. **expand** — 加新形式在舊的旁邊，什麼都不破
2. **migrate** — 呼叫端分批遷移，每批一張票、依 blast radius 分（每個 package、
   每個目錄），每張 blocked by expand。CI 保持綠，因為舊形式還在
3. **contract** — 沒有呼叫者之後刪掉舊形式，blocked by 全部 migrate 票

連分批都無法各自保持綠時，讓它們共用一條整合分支，全部 block 一張最後的
整合驗證票——綠只在那裡承諾。
