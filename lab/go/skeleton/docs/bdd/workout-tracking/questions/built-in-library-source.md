# 內建動作庫裡本來有哪些動作？誰維護？更新時撞名怎麼辦？

**狀態**: 已答 · **輪次**: 4 · **信心**: 低（代答，見下）

`duplicate-exercise-name` 的規則要拿「內建動作」來比對，`custom-exercise-type-change`
的預設型別也預設了內建動作已經標好型別。但內建動作庫本身從哪來，沒有人說過。

## 選項
1. 有內建庫，隨 App 版本更新（打包在 App 裡，不動態下載）；更新新增的內建動作若與
   使用者既有的自訂動作同名，**使用者的自訂動作優先**，內建那一個不出現在他的清單
2. 有內建庫，隨 App 版本更新；撞名時**內建優先**，使用者的自訂動作被要求改名
3. 有內建庫，從伺服器動態下載，隨時可更新
4. 沒有內建庫，全部靠使用者自己建
5. 不知道／先跳過

## 答案
選 1。

## 為什麼
選項 2 的「內建優先」會直接破壞 `delete-referenced-exercise` 的答案：使用者的
自訂動作已經被三個月的歷史紀錄引用，一次 App 更新就要求他改名，等於**外部事件
改動了他的歷史**。而他完全不知道為什麼。

選項 3（動態下載）讓動作庫變成一個會自己變的東西，於是「昨天還在的動作今天不見了」
變成可能——那會需要一整組沒人問過的規則（下架的動作怎麼辦？離線時看得到嗎？）。
打包在 App 裡的代價是更新慢，但它讓動作庫在兩次 App 更新之間是**不變的**，
而不變的東西不需要規則。

選項 4 也是真的可能——但需求說「動作庫要讓使用者**自己**新增」，「自己」這個字
隱含有一個不是自己的庫。而且沒有內建庫的話，第一次使用要先建二十個動作才能記
第一次訓練，那個門檻高到會讓人放棄。

## 為什麼信心低
這是**代答**。三件事仍然沒有來源：初版收錄哪些動作、誰負責標型別（六種型別要
逐個標）、多久更新一次。這三件不影響任何行為規則，所以不擋就緒——但它們是實際
要有人做的工作，排期時不能當成沒有。

## 影響的規則
`custom-exercise-library` Rule 3（Example 3.2 成立）、Rule 7（新增）
