# CLARIFY 的固定測試提示

`prompts/` 收所有評估 ai-bdd skill 用的固定輸入，一個步驟一個檔。

每次評估都用同一段輸入，否則兩次執行的差異可能來自提問方式而不是 skill 本身。
**逐字複製，不要即興改寫。**

> 後續步驟多半不需要自己的提示——SPEC 吃 CLARIFY 的 `example-map.md`、PLAN 吃
> `.feature`，輸入就是上一步的產物。真正需要固定提示的是**鏈的起點**，也就是
> 這一個。等到第三個檔案出現時，再把共用的評估方法抽成 `prompts/README.md`。

---

```
市面上的健身 App 不少，但重訓的人普遍還是用試算表或紙本在記，練完自己
按計算機把訓練量加一加，很麻煩而且常常漏記。

我們想做一個給重訓者用的訓練追蹤 App。使用者每次進健身房，可以記錄當天
做了哪些動作、每個動作幾組、每組多重、做幾下。最重要的是要讓他看到這次
的總容量，因為總容量是公認衡量訓練量的主要指標，使用者靠它判斷自己有沒有
在進步。

另外還要能看歷史紀錄、跟前一週比較。動作庫要讓使用者自己新增，因為同一台
器材在不同健身房的叫法不太一樣。
```

---

## 為什麼是這樣措辭

| 特性 | 理由 |
| --- | --- |
| 是 epic，且夾雜相鄰功能 | 迫使 skill 切分並說明依據。切不動就是第一個失敗點 |
| **產品視角，不是某個人的需求** | 需求方是團隊而非單一使用者，紅卡該指向誰因此變成真問題（產品？教練？使用者研究？）——第一人稱版本會讓答案永遠是「你自己」 |
| 產品語言、口語、有雜訊 | 真實的需求提出就是這樣，不會自己寫成 user story 格式 |
| 提到「總容量」但不定義 | 模糊點的來源。定義了就沒東西可澄清 |
| **不給任何優先序** | 五則全部進範圍，逼 skill 面對「五則一起澄清」——而 `bdd-clarify` 自己的規則是一次不超過三、四則。它該推回來提議分批，而不是安靜地把五則都做淺 |
| 「**公認**衡量訓練量的主要指標」 | 一個被當成既定事實陳述的前提。比「網路上說」更難質疑，因此更能測出 skill 敢不敢問「所以要用它比較什麼」 |
| **陷阱**：「每組多重、做幾下」 | 隱含「每組都有重量」。自體重動作會撞破它——這是寫實，不是提示 |
| **不提**自體重、單邊、熱身組、單位、dropset | 最重要的一點 —— 見下 |

**提示絕不可暗示答案。** 一旦寫成「要考慮自體重動作怎麼算」，skill 就只是照抄
提示，測不出它會不會自己想到。及格標準列在
[README 的「Why this domain」](../README.md)，那十個模糊點**必須由 skill 自己
問出來**，不能出現在輸入裡。

## 及格標準

最低門檻（見 README）：一次執行若沒問到**自體重動作**與**單邊動作要不要乘二**，
就算失敗，不論產出多完整。

其餘八個模糊點問到幾個，用來比較不同版本的 skill。

## 怎麼比較兩次執行

固定輸入之後，看這幾項：

| 觀察項 | 好的樣子 |
| --- | --- |
| 切分 | 有把 epic 切成數則 story，且**沿著規則切**而非沿畫面切 |
| 並行 | 認出「至少兩則」要一起澄清，而不是自己挑一則 |
| 跨 story 規則 | 有發現某些規則同時約束多則（這是並行才看得到的東西） |
| 猶豫的處理 | 「還不確定要不要做」有被當場問，而不是安靜忽略 |
| 提問順序 | 先問人已知的，才提出自己的清單 |
| 問題形式 | 每題四個選項，第四個是逃生口 |
| 模糊點覆蓋 | 十個裡問到幾個 |
| 紅卡 | 答不出來的有沒有誠實記成問題，而不是自己填 |
| 儀表板 | 追問覆蓋列有沒有誠實標 `—` |
| 就緒判定 | 有沒有明講，還是含糊帶過 |

記錄每次執行的日期、skill 版本（git sha）與上表結果，才看得出改動是進步還是退步。
